Chat and messaging

Where should chat messages go, when there are billions of them and every conversation is read newest first?

Applications like this: chat apps, support conversations, comments on a document. This page is written the way I write a database design doc: the workload first, then where each kind of data goes and why, then how it grows, what breaks, and what I rejected.

The short answerAt small and medium scale, PostgreSQL with messages partitioned by time and indexed by (conversation_id, sent_at). At large scale, a wide-column store such as Cassandra or ScyllaDB, partitioned by conversation and bucketed by time.

1 · The workload

What the application asks of the database

DimensionThis application
WritesHigh and steady. Every message is an insert.
ReadsThe latest page of one conversation, very often.
Read to writeRoughly balanced.
ConsistencyPer conversation, in order. Across conversations, loose.
LatencyDelivery feels instant: tens of milliseconds to store.
GrowthFast and forever, unless you set retention.
2 · What goes where

Each kind of data, its store, and why

DataWhere it goesWhy
MessagesPostgreSQL with time partitions, then Cassandra or ScyllaDBOne conversation, newest first, is a range read on one partition. LSM stores take heavy insert rates well.
Conversations and membersThe relational databaseFew rows, many relationships, permissions.
Online status and typingRedis with a short TTLChanges every few seconds and does not need to survive a restart.
AttachmentsObject storageLarge and immutable.

3 · Data model

The core tables and the queries they serve

-- PostgreSQL
CREATE TABLE messages (
  conversation_id bigint NOT NULL,
  sent_at         timestamptz NOT NULL,
  id              bigint NOT NULL,
  sender_id       bigint NOT NULL,
  body            text,
  PRIMARY KEY (conversation_id, sent_at, id)
) PARTITION BY RANGE (sent_at);

-- Cassandra or ScyllaDB at scale
CREATE TABLE messages (
  conversation_id bigint, bucket int, sent_at timeuuid, sender_id bigint, body text,
  PRIMARY KEY ((conversation_id, bucket), sent_at)
) WITH CLUSTERING ORDER BY (sent_at DESC);
  • The key starts with conversation_id, so the latest page of a conversation is one range read.
  • The bucket (for example one per month) stops one busy conversation from becoming an unbounded partition.
  • Paging uses the last sent_at as the cursor, never OFFSET.
4 · How it grows

Start simple, change one thing at a time

  1. One relational databaseMessages table with the composite key above.
  2. Table too big to vacuum or back up comfortablyPartition by month and drop or archive old partitions.
  3. Insert rate beyond one primaryMove messages to a wide-column store. Keep conversations and members relational.
5 · What breaks first

The failures to plan for

What happensWhat you seeWhat I do
One huge group chatA hot partition and slow readsBucket by time inside the conversation.
Deleting old messages with DELETEBloat and long-running deletesDrop whole partitions, or use TTLs in the wide-column store.
Unread counts computed on every readCOUNT(*) over a conversation on every app openKeep a per-member last-read marker and a counter.
6 · Alternatives

What I considered and did not pick

  • MongoDB with one document per conversation and an array of messages. The document grows without bound and hits the 16 MB document limit. One document per message works; one array per conversation does not.
  • A message queue as storage. Queues deliver. They are not built to answer "show me page 3 of this conversation".

Cost. Storage grows forever. Set retention, or move old partitions to cheaper storage.
