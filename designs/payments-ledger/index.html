Payments and ledgers

Where should money movements live, and how do I make sure no cent appears or disappears?

Applications like this: wallets, payment processors, billing systems, loyalty points. This page is written the way I write a database design doc: the workload first, then where each kind of data goes and why, then how it grows, what breaks, and what I rejected.

The short answerA relational database with a double-entry ledger that is append-only, with idempotency keys and synchronous replication. Correctness first, speed second.
WorkloadWhat goes whereData modelHow it growsWhat breaksAlternativesWhere to run it
1 · The workload

What the application asks of the database

DimensionThis application
WritesSteady. Every movement is a write, never an update in place.
ReadsBalances, statements, reconciliation jobs.
Read to writeClose to 1 to 1 on the ledger.
ConsistencyStrict. A committed movement must survive any single failure, and the books must always balance.
LatencyTens to hundreds of milliseconds is fine. Correctness matters more.
GrowthForever. Ledgers are kept for years, often by law.
2 · What goes where

Each kind of data, its store, and why

Solid arrows: the application writes there. Dashed arrows: a copy fed from the source of truth (change data capture, an outbox, or a cache fill), which can be rebuilt from it.

DataWhere it goesWhy
Accounts and ledger entriesPostgreSQL or MySQL, with synchronous replicationTransactions, constraints, and a commit that waits for a standby, so a failover cannot lose an acknowledged payment. See what a commit waits for.
Idempotency keysThe same database, in the same transactionA retried request must find the key that the first attempt wrote, or the money moves twice.
Statements and reconciliationA replica or a column storeLong scans that must not slow down new payments.
Raw provider callbacksObject storage, plus a table that points to themLarge, rarely read, kept for audit.

3 · Data model

The core tables and the queries they serve

CREATE TABLE ledger_entries (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  transfer_id uuid   NOT NULL,
  account_id  bigint NOT NULL REFERENCES accounts(id),
  amount      bigint NOT NULL,      -- cents; debit negative, credit positive
  created_at  timestamptz NOT NULL DEFAULT now()
);
-- every transfer writes two rows that sum to zero, in one transaction

CREATE TABLE idempotency_keys (
  key         text PRIMARY KEY,
  transfer_id uuid NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

-- a balance is a sum, or a row updated in the same transaction
SELECT sum(amount) FROM ledger_entries WHERE account_id = $1;
  • Entries are never updated or deleted. A refund is a new transfer in the other direction.
  • The idempotency key insert and the ledger insert are in one transaction. A duplicate key fails the whole retry, and the API returns the first result.
  • If balances are stored as a column for speed, they are updated with a relative UPDATE in the same transaction, with a CHECK that they never go below zero, or with SELECT ... FOR UPDATE. See isolation.
4 · How it grows

Start simple, change one thing at a time

  1. One primary, one synchronous standbysynchronous_commit with a standby, or semi-synchronous replication in MySQL. Backups with point-in-time recovery, and a restore tested on a schedule.
  2. Volume growsPartition the ledger by month. Old partitions move to cheaper storage but stay queryable.
  3. Very high volumeShard by account. Transfers between shards need a two-step protocol with a pending state, which is the hardest part of the design and the reason to delay this step.

5 · What breaks first

The failures to plan for

What happensWhat you seeWhat I do
A retry without an idempotency keyDuplicate charges in reconciliationMake the key mandatory in the API, and unique in the database.
Async replication and a failoverPayments acknowledged, then missing on the new primaryUse synchronous replication for this database, and accept the latency.
A hot account, such as the platform fee accountLock waits on one balance rowSpread it over several sub-accounts and sum them, or derive the balance from entries.
6 · Alternatives

What I considered and did not pick

  • A document store with balances embedded in the user document. Every transfer touches two documents, and the history is easy to overwrite. The ledger pattern fits tables better.
  • An event-sourcing system with no database constraints. Possible, but the rules that keep the books balanced move into application code that you must then prove correct.

Cost. The synchronous standby is not optional here, so budget for it. Save money on the history instead: partition by month and move old partitions to cheaper storage.
