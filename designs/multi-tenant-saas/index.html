Multi-tenant SaaS

One database for all customers, one schema each, or one database each?

Applications like this: B2B software where each customer is a company with its own users and data. This page is written the way I write a database design doc: the workload first, then where each kind of data goes and why, then how it grows, what breaks, and what I rejected.

The short answerStart with a shared schema and a tenant_id on every row, enforced by row-level security in PostgreSQL or by a mandatory filter in the data layer. Move very large tenants to their own database when they need it.

3 · Data model

The core tables and the queries they serve

CREATE TABLE projects (
  tenant_id bigint NOT NULL,
  id        bigint NOT NULL,
  name      text NOT NULL,
  PRIMARY KEY (tenant_id, id)
);

ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON projects
  USING (tenant_id = current_setting('app.tenant_id')::bigint);

-- the application sets the tenant at the start of each request
SET app.tenant_id = '42';
  • tenant_id leads every primary key and index, so each tenant's data clusters together and every query starts with it.
  • Row-level security makes a forgotten WHERE clause return nothing instead of another customer's data. Superusers and roles with BYPASSRLS always bypass it, and so does the table owner unless the table has FORCE ROW LEVEL SECURITY, so the application must not connect as either.
  • MySQL has no row-level security, so the filter must be enforced in the data access layer, and tested.
4 · How it grows

Start simple, change one thing at a time

  1. Shared schemaCheapest and simplest. Fine for thousands of small tenants.
  2. A few tenants dominateMove them to their own databases, routed by the catalog table.
  3. Many large tenantsShard by tenant_id across several databases. Citus (for PostgreSQL) and Vitess (for MySQL) do this.

5 · What breaks first

The failures to plan for

What happensWhat you seeWhat I do
A missing tenant filterData leak between customersRow-level security, or a data layer that cannot build a query without tenant_id.
One tenant's heavy jobEvery other tenant slows downRate-limit per tenant and move heavy tenants out.
Schema per tenant at thousands of tenantsMigrations take hours, catalog bloatPrefer shared schema with tenant_id.
6 · Alternatives

What I considered and did not pick

  • Database per tenant from day one. Strong isolation, but thousands of databases to back up, monitor and migrate.
  • Schema per tenant. A middle ground that gets hard past a few hundred tenants.

Cost. Shared schema is the cheapest per tenant. Price large tenants that need their own database accordingly.
