IoT, metrics and telemetry

Where should millions of sensor readings per minute go?

Applications like this: device telemetry, application metrics, fleet tracking, smart meters. This page is written the way I write a database design doc: the workload first, then where each kind of data goes and why, then how it grows, what breaks, and what I rejected.

The short answerA time-series database (TimescaleDB, InfluxDB) or a column store (ClickHouse), with time partitioning, compression, downsampling and retention. Device metadata stays relational.

1 · The workload

What the application asks of the database

DimensionThis application
WritesVery high, steady, in time order. Mostly appends.
ReadsRanges of time for one device or a group, and aggregates per minute or hour.
Read to writeLow. Most data is written and rarely read.
ConsistencyLoose. A late reading is fine.
LatencyDashboards in a second or two.
GrowthHuge. Retention is the main design decision.
2 · What goes where

Each kind of data, its store, and why

DataWhere it goesWhy
ReadingsTimescaleDB, InfluxDB or ClickHouseTime partitions, compression of similar values, and dropping old partitions whole.
Devices, owners, locationsPostgreSQLFew rows, many relationships.
Latest value per deviceRedis, or a small table updated in place"What is the temperature now" should not scan the history.
Raw archiveObject storage in ParquetCheap, and readable later by analytics tools.

3 · Data model

The core tables and the queries they serve

-- TimescaleDB (a PostgreSQL extension)
CREATE TABLE readings (
  device_id bigint NOT NULL,
  ts        timestamptz NOT NULL,
  metric    text NOT NULL,
  value     double precision
);
SELECT create_hypertable('readings', 'ts');

-- per-minute averages for the dashboard
SELECT time_bucket('1 minute', ts) AS minute, avg(value)
FROM readings
WHERE device_id = 42 AND ts > now() - interval '1 day'
GROUP BY minute ORDER BY minute;
  • Data is partitioned by time, so old data is dropped as whole partitions, not deleted row by row.
  • Keep raw data for days or weeks, minute rollups for months, hourly rollups for years.
  • Batch inserts. Thousands of rows per insert, not one row per round trip.
4 · How it grows

Start simple, change one thing at a time

  1. PostgreSQL with time partitionsWorks for a modest number of devices.
  2. Write rate or storage growsA time-series extension or a column store, with compression and rollups.
  3. Very large fleetsA message queue in front to absorb bursts, and several ingest workers writing batches.
5 · What breaks first

The failures to plan for

What happensWhat you seeWhat I do
Row-by-row insertsCommit rate caps throughput long before disks doBatch. See what one commit costs in Notebook 2.
High cardinality labelsIndex size explodes in metric storesDo not use user IDs or request IDs as tags.
No retentionStorage bill grows every month without endDecide retention per resolution on day one.
6 · Alternatives

What I considered and did not pick

  • Plain MySQL or PostgreSQL tables without partitioning. Fine at first. DELETE-based retention later causes bloat and I/O spikes.
  • A document store with one document per reading. Large per-reading overhead and poor compression compared to columnar storage.

Cost. Compression and retention decide the bill. Column and time-series stores often compress telemetry many times over, so measure on your own data.

The one invariant: COMMIT means the log record is on disk. pg_wal in PostgreSQL, #innodb_redo/#ib_redo0 + mysql-bin in MySQL, journal/WiredTigerLog + the oplog in MongoDB. The data files (base/…, *.ibd, collection-*.wt) are where checkpoints place the result afterwards, on their own schedule. Every guarantee on this page, durability, replication, point-in-time recovery, is a consequence of that ordering, and every number on this page is checkable with the commands given beside it.
