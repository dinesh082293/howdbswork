Audit logs and event history

Where should an append-only history of everything that happened go?

Applications like this: audit trails, activity history, event sourcing, compliance records. This page is written the way I write a database design doc: the workload first, then where each kind of data goes and why, then how it grows, what breaks, and what I rejected.

The short answerAn append-only table partitioned by time in the relational database, or a stream (Kafka) with a long retention plus a copy in object storage. Never updated, rarely read, kept for years.

1 · The workload

What the application asks of the database

DimensionThis application
WritesSteady. One row per action.
ReadsRare: investigations, compliance exports, a user's activity page.
Read to writeVery low.
ConsistencyThe entry must be committed with the action it records.
LatencyWrites must be cheap. Reads can be slow.
GrowthForever, often by law.
2 · What goes where

Each kind of data, its store, and why

DataWhere it goesWhy
Recent historyA partitioned table in the same database as the actionWritten in the same transaction, so an action never happens without its record.
Old historyObject storage in Parquet, or a column storeCheap, and still queryable by analytics tools.
Event streams for other servicesKafka or a similar logOther systems consume the events without querying your database.

How each family of store behaves under traffic: Database families.

3 · Data model

The core tables and the queries they serve

CREATE TABLE audit_log (
  id         bigint GENERATED ALWAYS AS IDENTITY,
  at         timestamptz NOT NULL DEFAULT now(),
  actor_id   bigint NOT NULL,
  action     text   NOT NULL,
  target     text   NOT NULL,
  details    jsonb,
  PRIMARY KEY (at, id)
) PARTITION BY RANGE (at);

REVOKE UPDATE, DELETE ON audit_log FROM app_user;
  • The application user can insert but not update or delete. That makes the log append-only by permission, not by convention.
  • Partitions by month are detached and exported once they pass the online retention window.
  • Only the columns you search on are columns. The rest goes in details.
4 · How it grows

Start simple, change one thing at a time

  1. A table in the main databaseSame transaction as the action.
  2. The table dominates storage and backupsMonthly partitions, export old ones to object storage.
  3. Many services produce eventsA shared event stream, with the audit store as one consumer.
5 · What breaks first

The failures to plan for

What happensWhat you seeWhat I do
Audit written after the transaction commitsActions with no record when the process crashes in betweenWrite it in the same transaction, or use the outbox pattern.
One giant unpartitioned tableBackups and vacuum take hoursPartition by time.
Personal data in the logA deletion request you cannot honorStore references, not personal data, or plan how to redact.
6 · Alternatives

What I considered and did not pick

  • Logging to files only. Easy to lose, hard to query, not transactional with the action.
  • Updating rows with a history column. The history can be overwritten. Append-only rows cannot, if permissions say so.

Cost. Keep months online, years in object storage. The online part should be the smallest.

The one invariant: COMMIT means the log record is on disk. pg_wal in PostgreSQL, #innodb_redo/#ib_redo0 + mysql-bin in MySQL, journal/WiredTigerLog + the oplog in MongoDB. The data files (base/…, *.ibd, collection-*.wt) are where checkpoints place the result afterwards, on their own schedule. Every guarantee on this page, durability, replication, point-in-time recovery, is a consequence of that ordering, and every number on this page is checkable with the commands given beside it.
