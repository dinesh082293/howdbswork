Online store: orders and inventory

Where should an online store keep its orders, carts and stock counts?

Applications like this: A shop, a marketplace checkout, a food-ordering app. This page is written the way I write a database design doc: the workload first, then where each kind of data goes and why, then how it grows, what breaks, and what I rejected.

The short answerOrders, order lines, payments references and stock live in one relational database, PostgreSQL or MySQL. Carts can live in Redis. Product search goes to a search engine, and reporting goes to a column store.

1 · The workload

What the application asks of the database

DimensionThis application
WritesBursty. Quiet most of the day, then 10 to 50 times normal during a sale.
ReadsMostly by key: an order, a customer's orders, a product's stock.
Read to writeAround 10 to 1 on the order tables, much higher on the catalog.
ConsistencyStrict for stock and orders. Two customers must not buy the last item.
LatencyCheckout under a few hundred milliseconds end to end.
GrowthSteady. Orders are rarely deleted, so the tables only grow.
2 · What goes where

Each kind of data, its store, and why

DataWhere it goesWhy
Orders, order lines, customers, stockPostgreSQL or MySQLTransactions across several tables, foreign keys, and a check that stock never goes below zero. This is what a relational database is built for.
Carts and sessionsRedis or Valkey, or the same databaseA cart is read and rewritten on every click and can be rebuilt if lost. Keeping it out of the order tables keeps them small and hot.
Product searchElasticsearch or OpenSearchFull-text search with filters. The database stays the source of truth; the index is a copy.
Sales reportsA column store, fed by change data captureReports scan millions of order lines. Running them on the primary competes with checkout.

3 · Data model

The core tables and the queries they serve

CREATE TABLE orders (
  id          bigint PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers(id),
  status      text   NOT NULL,          -- placed, paid, shipped, refunded
  created_at  timestamptz NOT NULL DEFAULT now(),
  total_cents bigint NOT NULL
);
CREATE INDEX ON orders (customer_id, created_at DESC);

CREATE TABLE stock (
  sku       text PRIMARY KEY,
  available int  NOT NULL CHECK (available >= 0)
);

-- reserve stock inside the checkout transaction
UPDATE stock SET available = available - 1
WHERE sku = $1 AND available >= 1;   -- 0 rows updated = sold out
  • The stock decrement is relative and conditional, so two checkouts cannot both take the last item. See lost updates.
  • Money is stored as integer cents, never as floating point.
  • The index on (customer_id, created_at) serves "my orders, newest first" without a sort. See column order.
4 · How it grows

Start simple, change one thing at a time

  1. One primary and a standbyEverything in one database. Add a read replica only when reads, not writes, saturate the primary.
  2. Sales get bigger than the primaryMove carts to Redis, product reads to a cache, and reports to a column store. Put a connection pooler in front of the database.
  3. Writes outgrow one primaryShard by customer_id or by region. Orders for one customer stay on one shard, so their transactions stay local.
5 · What breaks first

The failures to plan for

What happensWhat you seeWhat I do
The hot SKU during a saleLock waits on one stock row, connection pool exhaustedKeep the stock transaction short, and reserve stock before payment, with a timeout to release it. See the lock pile-up lab.
Reports on the primaryCPU spikes at the top of the hour, checkout latency followsMove reports to a replica or a column store.
OFFSET paging in the admin order listPage 1 is fast, page 500 times outPage by key. See paging.
6 · Alternatives

What I considered and did not pick

  • MongoDB for everything. Works if an order is one document. Stock and payment updates across documents then need multi-document transactions, which is where a relational database is simpler.
  • A distributed SQL database from day one. Higher latency per commit and more to operate, to solve a scale problem most stores do not have yet.

Cost. Most of the bill is the primary and its standby. A read replica that nobody reads, and reports running on the primary, are the usual waste. See the cost page.
