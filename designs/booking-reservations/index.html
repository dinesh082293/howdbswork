Bookings and reservations

How do I stop two people from booking the same seat, room or time slot?

Applications like this: hotel rooms, flight seats, appointment slots, event tickets. This page is written the way I write a database design doc: the workload first, then where each kind of data goes and why, then how it grows, what breaks, and what I rejected.

The short answerA relational database with the rule enforced by the database itself: a unique constraint on (resource, slot), or an exclusion constraint on time ranges in PostgreSQL. Short holds with an expiry for the checkout window.

3 · Data model

The core tables and the queries they serve

-- discrete slots: a unique constraint is enough
CREATE TABLE seat_bookings (
  event_id bigint, seat text, booking_id bigint NOT NULL,
  PRIMARY KEY (event_id, seat)
);

-- time ranges in PostgreSQL: no two overlapping bookings per room
CREATE EXTENSION IF NOT EXISTS btree_gist;
CREATE TABLE room_bookings (
  room_id bigint NOT NULL,
  during  tstzrange NOT NULL,
  EXCLUDE USING gist (room_id WITH =, during WITH &&)
);
  • The database enforces the rule. Two transactions trying to insert the same seat cannot both commit, at any isolation level.
  • The exclusion constraint does the same for overlapping time ranges. MySQL has no equivalent, so ranges are split into discrete slots there.
  • A hold is a row with an expiry. A job releases expired holds. Do not hold row locks while a user types a card number.
4 · How it grows

Start simple, change one thing at a time

  1. One databaseConstraints do the work.
  2. On-sale spikesA waiting room or queue in front, and availability served from cache.
  3. Many venuesPartition or shard by event or venue, so one hot event stays on one shard.
5 · What breaks first

The failures to plan for

What happensWhat you seeWhat I do
Check-then-insert in application codeDouble bookings under loadUse the constraint. A SELECT then INSERT is exactly the write skew pattern.
Locks held during paymentPool exhausted during an on-saleUse a hold row with an expiry instead of an open transaction.
Availability computed from scratch on each searchCPU spikes on the primary during an on-saleCache availability and recheck at booking.
6 · Alternatives

What I considered and did not pick

  • Redis as the only record of bookings. Fast, but a failover can lose acknowledged bookings. Use it for holds or queues, and keep the booking in the database.
  • Optimistic retries without a constraint. The rule then lives only in application code, and every code path must get it right.

Cost. The on-sale spike decides the size. A queue in front lets you size for the steady rate instead of the peak.

The one invariant: COMMIT means the log record is on disk. pg_wal in PostgreSQL, #innodb_redo/#ib_redo0 + mysql-bin in MySQL, journal/WiredTigerLog + the oplog in MongoDB. The data files (base/…, *.ibd, collection-*.wt) are where checkpoints place the result afterwards, on their own schedule.
