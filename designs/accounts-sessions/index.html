User accounts, logins and sessions

Where should user accounts live, and where should sessions and tokens go?

Applications like this: any app with sign-in. This page is written the way I write a database design doc: the workload first, then where each kind of data goes and why, then how it grows, what breaks, and what I rejected.

The short answerAccounts in the main relational database. Sessions in Redis or Valkey with an expiry, or no server-side session at all if you use short-lived signed tokens.

1 · The workload

What the application asks of the database

DimensionThis application
WritesLow for accounts. High for sessions: every login, and often every request touches a session.
ReadsEvery authenticated request reads a session or validates a token.
Read to writeVery high on sessions.
ConsistencyStrict for accounts (a unique email). Loose for sessions: losing one means one more login.
LatencySession lookups must take about a millisecond, since every request pays it.
GrowthAccounts grow slowly. Sessions churn and expire.
2 · What goes where

Each kind of data, its store, and why

Solid arrows: the application writes there. Dashed arrows: a copy fed from the source of truth (change data capture, an outbox, or a cache fill), which can be rebuilt from it.

DataWhere it goesWhy
Accounts, credentials, rolesPostgreSQL or MySQLA unique constraint on email, and transactions for sign-up and role changes.
Sessions and refresh tokensRedis or Valkey with a TTL on each keyLookups by key in memory, and expiry is built in. Losing them costs a login, not data.
Login attempts and rate limitsRedis counters with a TTLA counter per user or per IP that expires on its own.
Audit of loginsAn append-only table or log, partitioned by timeKept for security reviews, rarely read.

3 · Data model

The core tables and the queries they serve

CREATE TABLE users (
  id            bigint PRIMARY KEY,
  email         text   NOT NULL,
  password_hash text   NOT NULL,      -- argon2 or bcrypt, never the password
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX ON users (lower(email));

# Redis
SET session:9f2c... '{"user_id":42}' EX 1800
INCR login_fail:42   ;  EXPIRE login_fail:42 900
  • The unique index is on lower(email), so Alice@x.com and alice@x.com are one account.
  • Sessions have a TTL, so the cache cleans itself.
  • If Redis is lost, users sign in again. Nothing in it is the only copy of anything important.
4 · How it grows

Start simple, change one thing at a time

  1. Everything in one databaseA sessions table with an expiry column works at small scale. Delete expired rows in a scheduled job.
  2. Session reads dominate the databaseMove sessions to Redis. Each login stops being a write to the primary.
  3. Many services need identityA dedicated identity service with its own database. Other services validate signed tokens without calling it.
5 · What breaks first

The failures to plan for

What happensWhat you seeWhat I do
Sessions in the main databaseA delete job for expired sessions causes bloat and I/O spikesMove sessions to a store with built-in expiry.
Redis without a memory limitRedis runs out of memory, or swapsSet maxmemory and an eviction policy that removes keys with a TTL first (volatile-lru).
Case-sensitive email lookupsDuplicate accounts for one personUnique index on lower(email).
6 · Alternatives

What I considered and did not pick

  • Stateless JWTs with no session store. Fewer lookups, but a stolen token stays valid until it expires. Keep them short-lived and keep refresh tokens server-side.
  • Sessions in a document store. Works, but you add a database to the stack for something Redis does with less to operate.

Cost. Sessions are small. A modest Redis node holds millions of them. The waste here is usually a large database instance sized for session traffic that a cache would absorb.

The one invariant: COMMIT means the log record is on disk. pg_wal in PostgreSQL, #innodb_redo/#ib_redo0 + mysql-bin in MySQL, journal/WiredTigerLog + the oplog in MongoDB. The data files (base/…, *.ibd, collection-*.wt) are where checkpoints place the result afterwards, on their own schedule. Every guarantee on this page, durability, replication, point-in-time recovery, is a consequence of that ordering, and every number on this page is checkable with the commands given beside it.
