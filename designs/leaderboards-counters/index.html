Leaderboards, counters and rate limits

Where should fast-changing counts go: views, likes, scores, rate limits?

Applications like this: game leaderboards, like counts, view counters, API rate limits. This page is written the way I write a database design doc: the workload first, then where each kind of data goes and why, then how it grows, what breaks, and what I rejected.

The short answerRedis or Valkey: sorted sets for leaderboards, INCR with a TTL for counters and rate limits. Flush totals to the database in batches if they must be kept.

1 · The workload

What the application asks of the database

DimensionThis application
WritesVery high, on a few hot keys.
ReadsTop N, my rank, the current count.
Read to writeBalanced or write-heavy.
ConsistencyApproximate is usually fine. A like count can be a second behind.
LatencySub-millisecond per operation.
GrowthSmall. One entry per player or per object.
2 · What goes where

Each kind of data, its store, and why

DataWhere it goesWhy
LeaderboardsRedis sorted setsRank queries are built in, and each update is O(log n) in memory.
Counters and rate limitsRedis INCR with EXPIREAtomic increments with no lock, and expiry built in.
Totals you must keepThe database, updated in batchesOne write per minute per object instead of one per event.

3 · Data model

The core tables and the queries they serve

# leaderboard
ZINCRBY lb:season7 50 player:42
ZREVRANGE lb:season7 0 9 WITHSCORES   # top 10
ZREVRANK lb:season7 player:42           # my rank

# fixed-window rate limit: 100 requests per minute per key
INCR rl:api:key123:202611181305
EXPIRE rl:api:key123:202611181305 60
  • Counting in a relational row means every like is an UPDATE of the same row, which serializes on that row's lock.
  • Redis runs commands on one main thread. That is why each operation is atomic, and also why one slow command blocks everyone.
  • If Redis is the only copy of a total, decide what happens after a failover. Batching to the database bounds the loss.
4 · How it grows

Start simple, change one thing at a time

  1. Counters in the databaseFine at low rates.
  2. Hot rowsMove counting to Redis, flush to the database every minute.
  3. Very large leaderboardsShard by season or region, and keep top N in one key.
5 · What breaks first

The failures to plan for

What happensWhat you seeWhat I do
UPDATE counters SET n = n + 1 on one hot rowLock waits, lock pile-upMove the counter to Redis, or spread it across several rows and sum them.
KEYS * in productionRedis stalls for everyoneUse SCAN.
Counters with no TTLMemory grows foreverExpire window keys.
6 · Alternatives

What I considered and did not pick

  • A column store for live counts. Great for counts over history, wrong for "my rank right now".
  • Approximate counters in the application only. Lost on every deploy.

Cost. Small. A modest Redis node handles very high operation rates. The cost risk is memory from keys that never expire.

The one invariant: COMMIT means the log record is on disk. pg_wal in PostgreSQL, #innodb_redo/#ib_redo0 + mysql-bin in MySQL, journal/WiredTigerLog + the oplog in MongoDB. The data files (base/…, *.ibd, collection-*.wt) are where checkpoints place the result afterwards, on their own schedule. Every guarantee on this page, durability, replication, point-in-time recovery, is a consequence of that ordering, and every number on this page is checkable with the commands given beside it.
