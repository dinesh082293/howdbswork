Search and AI retrieval

Where should full-text search and vector search for AI features go?

Applications like this: site search, document search, semantic search, retrieval for a chat assistant. This page is written the way I write a database design doc: the workload first, then where each kind of data goes and why, then how it grows, what breaks, and what I rejected.

The short answerStart in PostgreSQL: full-text search and pgvector, next to the data. Move to a dedicated search engine or vector database when the size, the query rate, or the ranking needs outgrow it.
WorkloadWhat goes whereData modelHow it growsWhat breaksAlternativesWhere to run it
1 · The workload

What the application asks of the database

DimensionThis application
WritesDocuments added and updated, each needing an embedding.
ReadsQueries by text and by similarity, often combined with filters.
Read to writeHigh.
ConsistencyLoose. A new document can take seconds to become searchable.
LatencyUnder a few hundred milliseconds, including the embedding of the query.
GrowthModerate to large. Embeddings are big: hundreds to thousands of numbers per item.
2 · What goes where

Each kind of data, its store, and why

Solid arrows: the application writes there. Dashed arrows: a copy fed from the source of truth (change data capture, an outbox, or a cache fill), which can be rebuilt from it.

DataWhere it goesWhy
Documents and metadataPostgreSQLThe record, permissions, and filters.
Embeddings, small to medium scalepgvector in the same databaseNo second system, and filters and permissions are just SQL.
Large scale or advanced rankingElasticsearch or OpenSearch, or a vector databaseDistributed indexes, hybrid text and vector ranking, more tuning knobs.

3 · Data model

The core tables and the queries they serve

CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (
  id        bigint PRIMARY KEY,
  doc_id    bigint NOT NULL,
  tenant_id bigint NOT NULL,
  body      text NOT NULL,
  embedding vector(1024)
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

SELECT id, body FROM chunks
WHERE tenant_id = $1
ORDER BY embedding <=> $2
LIMIT 10;
  • Approximate indexes (HNSW) trade a little recall for a lot of speed. Measure recall against an exact search on a sample.
  • Filters such as tenant_id interact with approximate indexes: a filter can remove most candidates. Test the filtered query, not just the unfiltered one.
  • Store the embedding model name and version next to the vectors. Changing models means re-embedding everything.
4 · How it grows

Start simple, change one thing at a time

  1. PostgreSQL full-text and pgvectorOne database, no sync problem.
  2. Index outgrows memory, or ranking gets complexA search engine or vector database, fed by the same outbox or CDC pattern as other copies.
  3. Many teams and sourcesA shared search platform with its own ingestion pipeline.

5 · What breaks first

The failures to plan for

What happensWhat you seeWhat I do
HNSW index larger than memoryLatency jumps as the index pages come from diskSize memory to the index, or reduce dimensions, or quantize.
Embeddings from mixed model versionsResults that quietly get worseRecord the model per row and re-embed in one pass.
Permission filters applied after searchUsers see snippets of documents they cannot openFilter inside the query.
6 · Alternatives

What I considered and did not pick

  • A dedicated vector database from day one. Another system to sync and secure, before you know the scale needs it.
  • LIKE queries for search. No ranking, no stemming, and a full scan.

Cost. Embeddings are large. Count vectors times dimensions times bytes per number, then add the index, before picking a server.
