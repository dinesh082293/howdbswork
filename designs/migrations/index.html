Migration playbooks

How do I change the design without an outage?

You will learn: step by step plans for four common changes, how to check each one worked, and the way back if it did not.

Most designs change after launch. These four changes come up in almost every growing system. Each plan ends with the way back, because a migration without one is a bet.

Migration

Add change data capture

Change data capture streams every committed change out of the database, so search indexes, caches and warehouses can follow it without polling or scanning the primary.

  1. Turn on the change streamPostgreSQL: wal_level = logical (needs a restart) and a replication slot per consumer. MySQL: binlog_format = ROW and binlog_row_image = FULL, with GTIDs on. MongoDB: change streams, which need a replica set.
  2. Take the initial snapshotThe tool (Debezium or a managed equivalent) copies the existing rows, then switches to the stream at a consistent point.
  3. Make the consumer idempotentThe same change can arrive twice after a restart. Apply changes by primary key so that applying one twice does no harm.
  4. Watch the slot or binlog positionA stopped consumer makes PostgreSQL keep WAL for its slot, and the disk fills. Alert on slot lag, and set max_slot_wal_keep_size as a safety limit.
  5. Plan for schema changesAdding a column is usually fine. Renaming or dropping one breaks consumers unless they are updated first.

How I check it worked

  • Row counts and a checksum of a few key columns match between source and target.
  • Lag stays in seconds under the peak write rate.
  • Stopping the consumer for an hour, then starting it, catches up without data loss.

The way back. Drop the replication slot or stop reading the binlog. The source database is unchanged, so turning CDC off is safe, as long as the slot is dropped and does not keep holding WAL.

Migration

Split one database into two

One database often holds several domains (orders, users, catalog). Splitting one out gives it its own scaling, its own failure domain and its own team.

  1. Stop the cross-domain joins firstIn code, before any data moves. The new service reads the other domain through an API or a copy, not through a join.
  2. Copy the tables with logical replication or CDCThe new database follows the old one while the application still writes to the old one.
  3. Avoid writing to both from the applicationTwo commits in two databases can disagree after a failure. If both must be updated for a while, use an outbox and one direction of copying.
  4. Switch writes in a short freezeStop writes to the moved tables, wait for the copy to catch up, point the application at the new database, resume.
  5. Keep the old tables read-only for a whileThey are the fallback, and they answer questions about what moved.

How I check it worked

  • Counts and checksums match before the switch.
  • After the switch, no writes reach the old tables (revoke the permissions to be sure).
  • Latency of the requests that used to join across domains is measured, not assumed.

The way back. Until the old tables are dropped, switch writes back and copy the new rows in the other direction. Decide in advance how long this window stays open.

Migration

Move from MySQL to PostgreSQL

The engines speak similar SQL, so most of the work is in the details that differ.

  1. Convert the schema by hand, then review itTINYINT(1) to boolean, DATETIME to timestamptz, AUTO_INCREMENT to identity, UNSIGNED columns to the next larger type. Case-insensitive comparisons from MySQL collations need citext or indexes on lower(column).
  2. Clean the data that PostgreSQL rejectsZero dates such as 0000-00-00, invalid UTF-8, and values that only fit because of an old SQL mode.
  3. Load and keep in syncpgloader for a one-time load, or a CDC tool or AWS DMS to keep PostgreSQL following MySQL until cutover.
  4. Change the application SQLBacktick quoting, LIMIT x, y, ON DUPLICATE KEY UPDATE (becomes ON CONFLICT), and GROUP BY queries that MySQL accepted without listing every column.
  5. Rehearse the cutoverTime a full run on a copy, including the final sync and the switch.

How I check it worked

  • Row counts and checksums per table match.
  • The top queries have plans checked on PostgreSQL, with their indexes.
  • The application test suite runs green against PostgreSQL.

The way back. Keep MySQL receiving the changes from PostgreSQL for a while after cutover, if your tooling supports reverse sync. If not, the way back is a restore, so rehearse it.

Migration

Add a cache in front of the database

A cache helps when the same data is read far more often than it changes. Added carelessly, it serves stale data and can take the database down when it empties.

  1. Cache-asideRead from the cache. On a miss, read the database and store the result with a TTL.
  2. Invalidate after commitOn a write, delete the cache key after the transaction commits, not before, or a reader can refill it with the old value.
  3. Add jitter to TTLsKeys created together expire together. A random few percent on each TTL spreads the refills.
  4. Protect against stampedesWhen a hot key expires, let one request refill it while others wait or get the stale value.
  5. Plan for a cold cacheAfter a restart, every read goes to the database. Size the database to survive that, or warm the cache before taking traffic.

How I check it worked

  • Hit ratio is measured per key pattern.
  • Stale reads are measured, for example by comparing a sample against the database.
  • A test restart of the cache does not overload the database.

The way back. Turn the cache off with a flag. If the database cannot take the load without it, the cache has become part of capacity, and the design should say so.

Your turn

You are moving a 2 TB MySQL database to a new cluster with under a minute of write downtime. Outline the steps.

Write your answer down first. Then open mine.

Show my answer

Copy: a physical copy, such as XtraBackup or a cloned replica, restored on the new cluster. Note its GTID position.

Catch up: make the new cluster a replica of the old one from that position. Let it catch up, then compare the data with checksums (pt-table-checksum or similar). Send some read traffic to it and compare answers.

Cut over: set the old primary read_only, wait until the new one has applied every GTID, then switch the application through the proxy or DNS you lowered the TTL on beforehand. Writes are paused only for those seconds.

Keep a way back: replicate from the new cluster to the old one for a while, so rolling back is another switch, not a restore.
