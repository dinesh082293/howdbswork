Decision 2 of 10 · Replication, failover and split-brain

Synchronous replication and failover

This page decides one thing: what a commit waits for before it returns, and what that choice costs when a server dies.

60-second layer

The decision: how many copies must confirm a write before the application hears "saved".

The rule of thumb: if losing one second of acknowledged writes is a data-loss incident, use synchronous replication with a quorum, not a single standby. If a few seconds of lag is acceptable, async is cheaper and faster. The price of sync is one network round trip plus one standby fsync on every commit. The price of async is write rate multiplied by lag, paid all at once on failover.

Decision record

Context: a payments ledger. A lost acknowledged payment is a data-loss incident, not a delay. Two availability zones, one region. Commit rate peaks at 800 commits/s from one service, spread across multiple sessions. One serial session caps at 500 commits/s cross AZ, so the 800 figure only works across sessions.

Options considered: async with a 2 s lag budget; PostgreSQL sync with one named standby; PostgreSQL sync with quorum ANY 1 (s1, s2); MySQL semi-sync; MongoDB w: "majority".

Choice: PostgreSQL sync, synchronous_commit = on, synchronous_standby_names = 'ANY 1 (s1, s2)', one standby per AZ. Commit p99 rises by about 2 ms. That is the price, measured before rollout, not discovered after.

Consequences: writes hang if both standbys are down. That is a known outage mode, and it needs an alert on sync_state and a written runbook step for removing a dead standby from the list. On failover, promote the standby with the highest flush LSN. With ANY 1, either standby may hold the latest commit, and promoting the other one loses acknowledged writes. The ledger never loses an acknowledged payment to a single server failure. That was the requirement. The latency is the cost.

10-minute layer · section 1 of 8

1. What

PostgreSQL

Synchronous replication means the primary's commit waits until a standby confirms the WAL. Two settings control it. synchronous_standby_names names the standbys that count. synchronous_commit sets how far the standby must get before the commit returns.

The levels, weakest to strongest:

  • off: the commit returns before the local WAL fsync. A primary crash inside the next few hundred milliseconds loses the transaction.
  • local: the commit returns after the local WAL fsync. Replica state is irrelevant. This is what on degrades to when no synchronous standby is configured.
  • remote_write: the standby has written the WAL to its OS buffers. Not fsynced. A standby OS crash before the flush can still lose it.
  • on (the default): the standby has flushed the WAL to its disk, and the primary has flushed locally. This is the level that gives RPO 0.
  • remote_apply: the standby has replayed the WAL. The commit is visible to reads on that standby.

Boundary: synchronous replication guarantees durability on the standby, not visibility, except at remote_apply. It does not guarantee the standby is caught up for reads. It does not protect against a bug that corrupts the primary and replicates the corruption. It is not a backup. RPO 0 holds for one failure at a time. If the primary and the standby holding the latest commit fail together, the acknowledged writes that only that standby held are lost with it.

synchronous_standby_names has three forms. A bare name, s1, waits for that one standby. FIRST 1 (s1, s2) waits for the first standby in priority order. ANY 1 (s1, s2) waits for any one of the two. Only the ANY form survives one standby going down. A bare list, s1, s2, means FIRST 1 (s1, s2), not both.

MySQL

Semi-synchronous replication makes the source wait for one replica to acknowledge receipt before the commit returns. It is a plugin, rpl_semi_sync_source on the source and rpl_semi_sync_replica on the replica. Both sides must have it installed, or replication stays async.

The wait point matters. rpl_semi_sync_source_wait_point = AFTER_SYNC is the default. The source writes the transaction to its binlog, syncs the binlog, sends it, and waits for the ACK. Only then does it commit to InnoDB and return. No other session can see a transaction that a replica has not received. AFTER_COMMIT commits to InnoDB first and waits after. Other sessions can then read data that a failover may still lose. Keep the default.

The ACK means the replica wrote the events to its relay log. It does not mean the replica applied them. Whether that relay log write is fsynced before the ACK depends on sync_relay_log, which defaults to 10000, meaning the relay log is fsynced every 10,000 events. With the default, a replica OS crash can lose a relay-logged transaction that was already ACKed. Set sync_relay_log = 1 if the ACK must mean durable.

Group Replication is a different mechanism. A group of servers agrees on every transaction before any of them commits it. In single-primary mode, one server accepts writes and the rest are secondaries. Each transaction is certified against the group's write sets, then a majority must agree. The commit returns after that agreement. No single replica ACK is the guarantee. The group is.

MongoDB

Write concern is set per operation, not per server. w: 1 waits for the primary alone. w: "majority" waits for a majority of data-bearing voting members to acknowledge, and a member acknowledges only after receiving and applying the write. j: true requires the journal fsync as well. Since MongoDB 5.0 the default write concern is w: "majority", except in a replica set with an arbiter where the data-bearing members only just reach a voting majority, for example two data members plus an arbiter, where the default drops to w: 1.

w: "majority" implies j: true when writeConcernMajorityJournalDefault is true, which is the default. So in a normal three-member replica set, the default write waits for two members to have the write durable.

Read concern is the other half. readConcern: "majority" returns only data at or before the majority commit point, the newest oplog entry a majority has. The default read concern is local, which can return data that is later rolled back.

Boundary: w: "majority" protects acknowledged writes. It does not make reads fresh. A secondary can still serve stale data unless the read uses readConcern: "majority" or reads from the primary.

2. Why

Async replication has a loss window, and the window is exactly write rate multiplied by lag. At 2,000 commits/s and 5 s of lag, a failover loses 10,000 acknowledged transactions. The lag is not a constant. It is milliseconds at idle and seconds at peak, because lag is set by standby apply throughput, not by the network. The loss window is largest at the moment the primary is busiest, which is the moment it is most likely to die.

Before synchronous replication, the options were a smaller window or a faster failover. Neither closes the window. A faster failover loses fewer transactions. It still loses some. Synchronous replication is the only mechanism in this list that makes the window zero, and the price is latency on every commit.

The price is paid in a specific place: the commit path. Nothing else slows down. Reads are unaffected. A single long transaction pays the wait once, at commit. A chatty application that commits once per row pays it once per row.

What came before it: file-based log shipping, where WAL files moved after commit and the window was minutes. Streaming replication shrank the window to milliseconds. Synchronous replication closed it. Each step cost latency and complexity, and each step was worth it only for data where the loss window was unacceptable.

3. How

PostgreSQL

The commit path, step by step:

  1. The backend writes the commit record to the WAL buffers and asks for a flush.
  2. The WAL writer fsyncs the local WAL. In parallel, the walsender streams the record to the standby.
  3. The standby walreceiver writes the record to its pg_wal and fsyncs it.
  4. The walreceiver sends back its flush LSN.
  5. The backend wakes and returns COMMIT to the client.

The two flushes run in parallel. The added latency is the standby side only: one network round trip plus the standby fsync. The backend waits with wait event SyncRep, visible in pg_stat_activity.

Sequence diagram, cross-AZ standby. Timings use the assumptions in section 4: RTT 1.5 ms, standby fsync 0.5 ms.

App                 Primary              Standby s1 (other AZ)

 |                      |    fsync local (0.5 ms, in parallel)
 |                      |                      |  write + fsync (0.5 ms)
 |                      | <-- ACK flush LSN --- |  t = 2.0 ms
 | <-- COMMIT ok ------- |                     |

MySQL

The semi-sync commit path, AFTER_SYNC:

  1. The source writes the transaction to its binlog and syncs the binlog.
  2. The source sends the events to the replica and waits.
  3. The replica I/O thread writes the events to its relay log and sends an ACK.
  4. The source commits to InnoDB and returns to the client.

Group Replication replaces this path. The transaction is broadcast to the group, certified against the write sets of transactions already in the group, and committed only after a majority agrees. In single-primary mode the primary is the only writer, so certification rarely conflicts. The commit returns after the majority agreement, which costs roughly two network round trips inside the group, not one.

MongoDB

The write path for w: "majority", j: true:

  1. The primary applies the write and records it in the oplog, in the same storage transaction as the change.
  2. Secondaries tail the oplog and apply the entry.
  3. Each secondary journals the entry.
  4. Once a majority has it, the primary advances the majority commit point and returns the ACK.

4. When

Assumptions, stated before the arithmetic. Standby fsync 0.5 ms, a small WAL record on SSD. Same-AZ round trip 0.3 ms. Cross-AZ round trip 1.5 ms. Cross-region round trip 40 ms. These are the inputs. The outputs follow from them.

Added latency per commit is one round trip plus the standby fsync:

  • Same AZ: 0.3 + 0.5 = 0.8 ms. Well under a millisecond.
  • Cross AZ: 1.5 + 0.5 = 2.0 ms.
  • Cross region: 40 + 0.5 = 40.5 ms. Tens of milliseconds.

A single session committing serially is capped at about 1 / (RTT + fsync):

  • Same AZ: 1 / 0.8 ms, about 1,250 commits/s.
  • Cross AZ: 1 / 2.0 ms, 500 commits/s.
  • Cross region: 1 / 40.5 ms, about 24 commits/s.

Group commit helps concurrent sessions, not that one. The WAL writer fsyncs once per batch, so ten sessions committing at once share one fsync and one round trip each. Aggregate throughput rises with concurrency. A single session stays capped.

Use synchronous replication if:

  • The RPO is 0. Losing acknowledged writes is a data-loss incident, not a delay. Payments, ledgers, anything auditable.
  • The commit rate per session is under the cap above, or the application can batch commits. 800 commits/s from one service, across several sessions, fits cross-AZ sync. 5,000 commits/s from one session does not.
  • There are at least two standbys in different failure domains, so one standby loss does not stop writes.

Avoid it if:

  • One session commits more than about 500 times per second across AZs and cannot batch. The break point is the serial cap. Past it, the options are batching (fewer, larger transactions), more sessions, or async with a stated loss budget.
  • The standby is in another region and the application commits serially. At 24 commits/s per session, the application will feel it in every request.
  • There is only one standby and no quorum. The availability cost exceeds the durability gain. One standby failure stops all writes.

RTO and RPO, stated together:

  • PostgreSQL sync: RPO 0 for one failure at a time, RTO is the five steps below. Tens of seconds with Patroni on defaults, minutes by hand.
  • MySQL semi-sync: RPO 0 only if the ACKing replica is promoted. RTO is promotion time with Orchestrator, seconds.
  • MySQL Group Replication: RPO 0 for certified transactions, RTO is election plus backlog apply, seconds.
  • MongoDB majority: RPO 0 for acknowledged writes, RTO is election, median about 12 s with defaults, plus catch-up.

RTO for PostgreSQL with Patroni, step by step, on defaults. Patroni documents ttl 30 s, loop_wait 10 s, and retry_timeout 10 s. Patroni docs

  • Detect: 20 to 30 s. The primary renews its leader key every loop_wait, 10 s, and the key lives for ttl, 30 s, so it expires 20 to 30 s after the primary stops renewing it. Derived from the documented defaults, not measured.
  • Decide: a few seconds, one Patroni loop. Assumption, to measure.
  • Promote: seconds, plus the time to replay the standby backlog. Depends on backlog size, to measure.
  • Redirect: seconds for the proxy or DNS to move traffic to the new primary. Depends on health check settings, to measure.
  • App reconnect: depends on the connection pool and retry settings. To measure.

Total on defaults is tens of seconds, dominated by detection. One more documented default can stretch it: primary_start_timeout is 300 s by default, and the Patroni docs give the worst case as loop_wait plus primary_start_timeout plus loop_wait. The 20 to 30 s figure above is the leader key expiry alone, not that worst case.

5. What breaks

PostgreSQL

Failure 1: the synchronous standby goes down. Blast radius: all writes hang. Every commit waits for an ACK that never comes. Reads continue. Detection: pg_stat_activity fills with SyncRep wait events, and pg_stat_replication shows no row with sync_state = 'sync'. First metric to move: count of sessions waiting on SyncRep. Mitigation: quorum ANY 1 (s1, s2) so one standby loss does not stop writes, or remove the dead standby from synchronous_standby_names and reload.

Failure 2: the standby is up but slow. A saturated disk makes the standby fsync take 50 ms instead of 0.5 ms. Blast radius: commit p99 rises by the same 50 ms on every session. Detection: flush_lag and replay_lag in pg_stat_replication grow. First metric to move: commit p99 latency. Mitigation: the standby needs the same disk performance as the primary. A slow standby is a slow primary.

Failure 3: synchronous_standby_names is empty. The commit returns after local flush only. Blast radius: the deployment believes it has RPO 0 and has RPO equal to the async window. Detection: SHOW synchronous_standby_names returns empty, and no row in pg_stat_replication has sync_state = 'sync'. First metric to move: none. That is the danger. Mitigation: check the setting and the view in the deploy checklist, not the config file.

Failure 4: the old primary comes back after failover and accepts writes. Blast radius: two primaries, divergent data, a manual merge. Detection: two servers both report pg_is_in_recovery() = false. Mitigation: fence the old primary. Patroni does this through the distributed consensus store. By hand, it means stopping the old primary and confirming it is stopped before promoting the new one.

Failure 5: failover promotes the wrong standby. Blast radius: acknowledged writes the other standby held are lost, even though the deployment runs sync with RPO 0. With ANY 1 (s1, s2), either standby may be the one that ACKed the latest commit. Detection: compare flush_lsn across standbys before promoting. The standby with the highest flush LSN is the most advanced. First metric to move: the LSN gap between standbys. Mitigation: promote the most advanced standby by LSN. Patroni picks from the synchronous set. By hand, it means comparing LSNs before promoting, not picking the standby that answers first.

Failure 6: the old primary comes back and needs to rejoin as a standby. Blast radius: it cannot just follow the new primary, because its timeline forked at promotion. Any writes it took after the fork sit on a timeline the new primary does not have. Detection: the old primary reports a timeline the new primary has moved past. Mitigation: pg_rewind. Stop the old primary, run pg_rewind against the new primary, and it copies back only the blocks that changed since the timelines diverged, then the old primary restarts as a standby. That is far faster than a fresh base backup on a large database. It needs wal_log_hints on or data checksums set at initdb, and full_page_writes on, and WAL back to the divergence point, or the -c flag to fetch it from the archive. If the rewind fails halfway, the data directory may not be recoverable, so rebuild it from a fresh backup. Patroni runs pg_rewind for a rejoining old primary when use_pg_rewind is set. PostgreSQL 18 pg_rewind docs

MySQL

Failure 1: semi-sync times out. Blast radius: the source reverts to async for the whole server. Every dashboard still says semi-sync is enabled, because the enabled variable is still ON. The protection is gone and nothing pages. Detection: Rpl_semi_sync_source_status reads OFF. First metric to move: that status variable. Mitigation: alert on the status variable, not the enabled variable.

Failure 2: failover promotes a replica that is not the one that ACKed. Blast radius: the transactions the ACKing replica held are missing on the new source. Detection: compare gtid_executed on the old source and the new source. The difference is the gap. First metric to move: the GTID set difference. Mitigation: promote the most advanced replica. Orchestrator does this by GTID. By hand, it means comparing sets before promoting.

Failure 3: a minority partition in Group Replication. Blast radius: the minority members stay in the group and their writes block. They do not leave on their own, and they do not enter the ERROR state on their own. Transactions the minority accepts sit blocked because the group cannot reach quorum, until an operator stops Group Replication on those members or the unreachable majority timeout fires. Detection: members report UNREACHABLE in performance_schema.replication_group_members. First metric to move: group size. Mitigation: odd member counts, three or five, so a majority is always clear. Set group_replication_unreachable_majority_timeout to a value the team can live with. It defaults to 0, which means wait forever. When it fires, the pending transactions on the minority roll back and the members move to ERROR, then auto-rejoin tries to bring them back. MySQL 8.4 manual

Failure 4: AFTER_COMMIT is set instead of AFTER_SYNC. Blast radius: other sessions can read data that a failover loses. Detection: SHOW VARIABLES LIKE 'rpl_semi_sync_source_wait_point'. Mitigation: keep the default. Verify it at deploy time.

Failure 5: errant GTIDs block a replica from rejoining. An errant GTID is a transaction in a replica's gtid_executed set that the source never ran. It gets there when someone writes directly to the replica, when a replica is briefly promoted during a failed failover and takes writes, or when maintenance runs on the replica without disabling the binlog. Blast radius: the replica cannot rejoin cleanly, because the source has no binlog for those GTIDs and cannot send them, and the other replicas cannot take them from the promoted replica either. In Group Replication the same shape shows up as a member that cannot rejoin because it has more executed transactions than the group. Detection: GTID_SUBTRACT of the replica set minus the source set returns a non-empty set. That is the errant set. First metric to move: the GTID set difference. Mitigation: if the errant writes are few and harmless, commit an empty transaction on the source for each errant GTID so the sets line up again. If the writes mattered or the set is large, rebuild the replica from a fresh copy of the source. RESET MASTER wipes the GTID history and the binlogs, so use it only on a server with no replicas, never as a shortcut on a live one.

MongoDB

Failure 1: the primary loses its majority. Blast radius: it steps down. Writes stop until a new primary is elected. Reads from the primary stop too. Detection: the logs show an election, and rs.status() shows no PRIMARY. First metric to move: election count in the logs. Mitigation: three voting members, in different failure domains, so one loss leaves a majority.

Failure 2: a w: 1 write is rolled back. Blast radius: the write disappears from the new primary and lands in rollback/ files on the old primary as BSON. Inserts and updates are saved there. Deletes and drops are not. Detection: the old primary enters ROLLBACK state on rejoin, and files appear in the rollback directory. First metric to move: rollback files on disk. Mitigation: w: "majority" for anything that cannot be lost.

Failure 3: a secondary falls behind the oplog window. Blast radius: it cannot catch up by tailing the oplog and needs a full initial sync. During the sync it is not available as a failover target. Detection: rs.printReplicationInfo() shows the oplog window in hours, and the secondary lag exceeds it. First metric to move: the oplog window. Mitigation: size the oplog for the longest planned downtime, and watch the window, not just the lag.

6. Alternatives rejected

Async replication. Rejected where RPO is 0. It is the right choice where a few seconds of lag is acceptable, and it is the cheapest choice in latency. The break point is the loss budget: if the business accepts losing up to 5 s of writes, async with a 2 s lag alert is the simpler system.

MySQL semi-sync. Rejected for MySQL where the timeout fallback is unacceptable. Semi-sync bounds loss only while it is active. After a 10 s timeout it is async, silently. Pick it when one ACK is enough and the team alerts on the status variable. Pick Group Replication when the fallback itself is the risk.

MySQL Group Replication. Rejected where the team does not want the operational weight of a group: certification, quorum management, and the consistency level to tune. Pick it when failover must be automatic and split-brain must be impossible by construction, not by runbook.

MongoDB w: "majority". Rejected for high-volume telemetry and click events, where losing two seconds of events in a rare failover is a fair trade for throughput. Pick w: 1 there, and say so in writing. Pick majority for payments, ledgers, and anything auditable.

Two-phase commit across databases. Rejected. It makes every commit wait for every participant and turns one slow participant into a global outage. Use the outbox pattern instead: write the event to a local table in the same transaction as the business row, then relay it. The local commit is the atomic unit. The relay is async and retryable.

Read-your-writes routing instead of sync. Rejected as a durability mechanism. Routing a read to the primary after a write fixes stale reads. It does nothing for a primary that dies with unreplicated writes. It is a read-consistency fix, not a durability fix. Use both when both problems exist.

10-minute layer · section 7 of 8

7. Operating it

Three metrics, per engine. These are the only three to alert on first. Everything else is diagnosis.

PostgreSQL

  1. sync_state in pg_stat_replication. Alert when no row has sync_state = 'sync' for more than 30 s. That means the safety feature is off.
  2. Commit p99 latency, before and after enabling sync. Alert when p99 rises more than 2x the pre-sync baseline. That is the price moving.
  3. replay_lag at peak write load. Alert over 2 s. That is the failover gap for the async replicas.

MySQL

  1. Rpl_semi_sync_source_status. Alert the moment it reads OFF. That is the protection silently gone.
  2. Seconds_Behind_Source on the replica that would be promoted. Alert over 2 s.
  3. GTID set difference between source and replica. Alert on any non-zero difference at failover time. That is the exact loss.

MongoDB

  1. Replica set member states in rs.status(). Alert when there is no PRIMARY for more than 30 s, or when a member is not in SECONDARY or PRIMARY state.
  2. Oplog window from rs.printReplicationInfo(). Alert when the window drops under 24 hours.
  3. Rollback files in the rollback directory. Alert on any file appearing. That is a lost write, found after the fact.

Alert thresholds, in one place: sync missing for 30 s, commit p99 2x baseline, replay lag 2 s, semi-sync status OFF immediately, oplog window under 24 hours, rollback files any.

Runbook, PostgreSQL sync standby down

  1. Confirm: SELECT application_name, state, sync_state FROM pg_stat_replication; No row shows sync.
  2. Check the standby: is the process up, is the disk full, is the network up. pg_stat_activity shows how many sessions wait on SyncRep. That is the blast radius, counted.
  3. If the standby is recoverable in minutes, wait. Writes hang, reads work. Say so in the incident channel.
  4. If it is not recoverable, remove it from synchronous_standby_names and reload. With ANY 1 (s1, s2), the other standby takes over and writes resume. With one named standby, removing it drops the deployment to async. Say that in the incident channel too.
  5. Verify: sync_state = 'sync' returns, and commit p99 returns to baseline.
  6. Record the change and the time to revisit it. A standby removed from the list and never added back is a deployment running async while the runbook says sync.

Runbook, MySQL semi-sync OFF

  1. Confirm: SHOW STATUS LIKE 'Rpl_semi_sync_source_status'; OFF with the enabled variable ON means a timeout.
  2. Find why the replica stopped ACKing: replica down, network partition, or replica I/O thread stuck.
  3. Fix the replica. Semi-sync returns on its own once a replica catches up.
  4. Check what was lost while it was async: compare gtid_executed on source and replica.
  5. If the timeout recurs, the timeout is wrong for the network, not the network for the timeout. Raise it, or move to Group Replication.

Runbook, MongoDB election storm

  1. Confirm: rs.status() shows elections in the logs and no stable PRIMARY.
  2. Check heartbeats: a member that cannot reach the primary for electionTimeoutMillis, 10 s by default, calls an election. Flapping network causes repeated elections.
  3. Fix the slow member or the network, not the election settings first. Lowering the timeout makes elections faster and more frequent. It does not fix the cause.
  4. Check for rollback files on the old primary after it rejoins. Any file there is a write the new primary never saw.

Topology: sync inside the region, async to a remote region

The common shape is a sync quorum in one region, two standbys in different AZs, plus an async replica in a remote region for disaster recovery. The remote replica hangs off a sync standby by cascading replication, or off the primary as a plain async standby. In PostgreSQL, cascading replication is async: the primary's sync settings do not wait for a cascaded standby, so the remote replica adds no commit latency. The tradeoff is the RPO split. A failover inside the region is RPO 0. A failover to the remote region loses whatever the async lag was at the time, and the remote region then has to rebuild the in-region quorum before sync protection is back. Treat the remote replica as disaster recovery, not high availability: it saves the data when the whole region is gone, and it is not the failover target for a single dead server.

Capacity formula. The sync standby must keep up with the primary's WAL rate, or lag grows without bound. Required standby apply throughput is greater than the primary's peak WAL generation rate, with headroom. In numbers: if the primary generates 50 MB/s of WAL at peak, the standby must apply more than 50 MB/s, sustained, on its own disk. The formula for the serial commit cap is in section 4: 1 / (RTT + fsync) per session. The formula for aggregate throughput is sessions multiplied by that cap, bounded by the WAL writer's batching and the standby's apply rate. Measure both before rollout: commit p99 with sync off, then with sync on, at the same load. The difference is the price. The standby's disk throughput is the ceiling.

10-minute layer · section 8 of 8

8. Version notes

PostgreSQL 10 added quorum commit, the ANY and FIRST forms of synchronous_standby_names. Before that, the setting was a plain list and only the first standby counted. PostgreSQL 17 moved checkpoint counters from pg_stat_bgwriter to pg_stat_checkpointer, which changes where the checkpoint numbers in the operating section come from, not the replication mechanism. PostgreSQL 18 adds nothing to synchronous replication itself.

MySQL 5.7 made AFTER_SYNC the default wait point. Before that, AFTER_COMMIT was the default, and other sessions could read data a failover would lose. MySQL 8.0.14 added the group_replication_consistency levels, including BEFORE_ON_PRIMARY_FAILOVER, which holds reads and writes on a new primary until it applies its backlog. The default is still EVENTUAL. MySQL 8.0.30 changed the redo log files to #innodb_redo/#ib_redoN. That changes the file names in the crash story, not the replication protocol.

MongoDB 5.0 made w: "majority" the default write concern. Before that, the default was w: 1, and an application that set nothing got primary-only acknowledgment. MongoDB 4.4 removed the old plan cache commands, which is unrelated to replication and noted here only because it is the same class of mistake: a command that worked in an old version and silently does nothing in the current one.

2 AM story · as a postmortem

Postmortem: the binlog that filled the disk

The timeline is in phases because the site does not record clock times for it.

Detection: writes started failing. Then the database refused writes entirely. The disk was full.

Diagnosis: the disk was broken down by owner before anything was touched. The binlog was the filler. The purge had not kept up, and the reason was not a dead replica. MySQL purges binlogs by time: binlog_expire_logs_seconds sets the age, 2592000 seconds (30 days) by default, auto-purge is on by default, and expired files go at startup and when the binlog is flushed. A replica that is disconnected holds nothing back. Only a connected replica that has not yet read a file keeps that one file. The dead replica did not pin the binlog history. That is PostgreSQL replication-slot behavior, not MySQL.

Root cause: binlog retention times write rate outgrew the disk, with no bound sized to either. The site does not record the retention value, the write rate, or how long the fill took, so it does not record which of the three usual causes it was: retention set too long for the disk, retention set to 0 or auto-purge off, or a write burst that filled the disk faster than purge could keep up. Check SHOW BINARY LOGS, SHOW VARIABLES LIKE 'binlog_expire_logs_seconds', and the disk usage by owner before naming the cause.

Contributing factors: no alert on disk growth rate, so the fill was discovered at 100 percent, not at 70. Retention was never sized against write rate and disk size, so nobody knew how many days of binlogs the disk could hold. No runbook step for checking replica positions before purging, so a manual purge would have risked error 1236 on any replica that still needed a purged file.

What changed: check every replica position with SHOW REPLICA STATUS, then free space with PURGE BINARY LOGS. Set binlog_expire_logs_seconds to a value the write rate and the disk can actually hold. Alert at 70 percent disk and on disk growth rate, not at 98 percent. Never remove binlog files by hand. A replica that still needs a purged file fails with error 1236 and must be rebuilt from a backup.

Numbers to check: the site records no disk size, no retention value, and no durations for this incident, so none are stated here. Fill them in from the incident record: total disk size and how full the binlog directory was, the binlog_expire_logs_seconds value at the time, the write rate in binlog bytes per day, the age of the oldest binlog file, and how long the fill took from the last healthy disk reading to 100 percent.

Why this postmortem is on this page: a dead replica is not what blocked the purge, and that distinction is the point. The dead replica still matters on this page for a different reason: it is the state that silently degrades semi-sync to async, and a single synchronous standby that dies turns into hung writes. One dead replica, two different failure modes in the replication modes, plus a disk fill with a separate cause. Watch replica health for the replication modes, and size retention against write rate for the disk. The two fixes are different, so keep them in separate runbook steps.

Anti-patterns · and the way out

Anti-patterns and the migration path out

  1. One named sync standby, no quorum. synchronous_standby_names = 's1'. One standby failure stops all writes. Migration: ALTER SYSTEM SET synchronous_standby_names = 'ANY 1 (s1, s2)'; SELECT pg_reload_conf(); Then verify sync_state = 'sync' appears for one of the two.
  2. synchronous_commit = on with no synchronous_standby_names. The commit returns after local flush only, and nothing says so. Migration: set the names, reload, and check pg_stat_replication for a sync row. Add the check to the deploy checklist.
  3. Semi-sync enabled, never checked. The plugin is installed, the variable was set once, and the status flipped OFF weeks ago. Migration: alert on Rpl_semi_sync_source_status, not on the enabled variable. Check it in the weekly review.
  4. A sync standby in the same availability zone, called disaster recovery. One zone event kills the primary and its only copy. Migration: move the synchronous standby to a second AZ. Keep an async replica in a third region for real disaster recovery.
  5. w: 1 for money. The application set nothing and the driver default did the choosing. Migration: set w: "majority" per operation for payments and ledgers, or set the replica set default with setDefaultRWConcern. Then check the rollback directory for a week. Any file there is a write the old setting lost.
  6. AFTER_COMMIT instead of AFTER_SYNC. Other sessions read data a failover loses. Migration: SET GLOBAL rpl_semi_sync_source_wait_point = 'AFTER_SYNC'; It is the default. Verify it, do not assume it.
  7. Failover by hand with no fencing step. The old primary comes back and accepts writes. Migration: Patroni for PostgreSQL, Orchestrator for MySQL, or a written fence step that stops the old primary and confirms it is stopped before any promotion. The built-in election in MongoDB and Group Replication already fences by quorum. Use it.
Uncertainty, stated plainly

Where I am less sure

The fsync and round-trip numbers in section 4 are assumptions, not measurements. Fsync latency on a small WAL record varies from 0.1 ms to 2 ms depending on the disk, and shared cloud disks are worse under contention. Cross-region round trips depend on the region pair. The mechanisms in this page do not depend on those numbers. The serial caps do. Measure them on the actual hardware before quoting them.

Aurora is not covered here. Aurora ships redo to a storage quorum instead of WAL files, so there are no WAL files to fill the disk and the classic checkpoint model does not apply. The sync standby model in this page is the on-prem and RDS model. Aurora deserves its own page.

Patroni failover time is stated as tens of seconds on defaults, dominated by the 30 s leader key expiry. The exact time depends on the distributed consensus store, the failure detection settings, and how much backlog the standby must replay. I have not measured it on this site's hardware.

Appendix: derivations, raw output, benchmark method, source links

Derivations

Added latency per commit, synchronous PostgreSQL:

added latency = RTT + standby fsync
same AZ:       0.3 ms + 0.5 ms = 0.8 ms
cross AZ:      1.5 ms + 0.5 ms = 2.0 ms
cross region: 40.0 ms + 0.5 ms = 40.5 ms

Serial commit cap per session:

cap = 1 / (RTT + standby fsync)
same AZ:       1 / 0.8 ms  = about 1,250 commits/s
cross AZ:      1 / 2.0 ms  = 500 commits/s
cross region:  1 / 40.5 ms = about 24 commits/s

The local fsync overlaps with the standby round trip, so it is not added. If the local disk is slower than the standby round trip, the local fsync becomes the bound instead.

Async loss window:

lost transactions = write rate x replay lag
2,000 commits/s x 5 s = 10,000 transactions
