Decisions

Which database decisions are hard to undo?

You will learn: Ten decisions, each with a side picked, a price named and what breaks when the choice is wrong.

Ten decisions a database engineer has to make. Each page picks a side, names the price, and says what breaks when the choice is wrong. Two decisions are written so far. The rest are planned, in the order I intend to write them.

Each decision page follows the same shape: what the choice is, why it matters, how each engine does it, when to use it, what breaks, the alternatives rejected, how to operate it, and the version notes. The numbers on a decision page are derived from stated assumptions until the Tested on box on that page says otherwise.

The one invariant: COMMIT means the log record is on disk. pg_wal in PostgreSQL, #innodb_redo/#ib_redo0 + mysql-bin in MySQL, journal/WiredTigerLog + the oplog in MongoDB. The data files (base/…, *.ibd, collection-*.wt) are where checkpoints place the result afterwards, on their own schedule. Every guarantee on this page, durability, replication, point-in-time recovery, is a consequence of that ordering, and every number on this page is checkable with the commands given beside it.

PostgreSQL, MySQL/InnoDB, and MongoDB/WiredTiger internals, from physical layout to production failure modes. File names, paths, thresholds, and commands are the production ones.
