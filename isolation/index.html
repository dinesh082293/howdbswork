Lost updates and write skew

Can two correct transactions produce a wrong result?

You will learn: the two concurrency bugs that isolation levels exist to stop, what each engine actually did with them at its default setting, and the fixes.

Isolation levels are usually taught as a table of anomalies. I find it easier to watch them. Every transcript on this page is from Notebook 4, run 2026-11-18 04:27 UTC: two real sessions, interleaved one step at a time, on PostgreSQL 18, MySQL 8.4 and MongoDB 8.0.

Anomaly 1

Lost update: two deposits, one survives

Two sessions read the same balance, 100, and each writes back its own result: 110 and 120. Both deposits should count, for 130. The read-then-write pattern is what loses one.

Which engines keep both deposits, at their default settings?

None of them. PostgreSQL at READ COMMITTED and MySQL at REPEATABLE READ silently kept 120. PostgreSQL at REPEATABLE READ and MongoDB in transactions refused the second write with an error, which keeps 110 and hands the retry to the application.

Common myth

MySQL's REPEATABLE READ prevents lost updates because the snapshot does not change.

The snapshot applies to plain reads. An UPDATE in InnoDB reads the latest committed row, not the snapshot, so the second session overwrote 110 with its stale 120 and got no error. The run above shows it.

Two sessions, one row

The same collision in PostgreSQL and InnoDB, one step at a time. Then tick the box: PostgreSQL shows what REPEATABLE READ changes, and MySQL shows what one forgotten transaction does to everyone behind it.

Two sessions update the same account at the same moment, in PostgreSQL's default isolation level. What happens to the second one?

It waits for the first to commit, then re-reads the row and applies its change on top. Both changes are kept. In REPEATABLE READ it would get an error instead and have to retry.

Anomaly 2

Write skew: two doctors go off call

The rule: at least one doctor on call. Alice and Bob each check that two are on call, then each takes themselves off. They update different rows, so nothing conflicts at the row level, and the rule breaks.

Which engine and level stops this?

Only PostgreSQL at SERIALIZABLE. It tracks what each transaction read, notices the two depend on each other, and fails the second commit. Every other run ended with nobody on call.

PostgreSQL, REPEATABLE READ

## PostgreSQL 18, write skew, REPEATABLE READ
  A: SELECT count(*) WHERE on_call -> 2
  B: SELECT count(*) WHERE on_call -> 2
  A: UPDATE alice off call
  B: UPDATE bob off call
  A: COMMIT -> ok
  B: COMMIT -> ok
  doctors on call at the end: 0  (the rule was: at least 1)

PostgreSQL, SERIALIZABLE

## PostgreSQL 18, write skew, SERIALIZABLE
  A: SELECT count(*) WHERE on_call -> 2
  B: SELECT count(*) WHERE on_call -> 2
  A: UPDATE alice off call
  B: UPDATE bob off call
  A: COMMIT -> ok
  B: COMMIT -> ERROR: could not serialize access due to read/write dependencies among transactions
  doctors on call at the end: 1  (the rule was: at least 1)

The fixes

What I reach for, in order

  1. Make the write relativeUPDATE accounts SET balance = balance + 10 WHERE id = 1, or $inc in MongoDB. The engine applies it to the current value, so there is no stale read to lose. This fixes lost updates, not write skew.
  2. Lock what you readSELECT ... FOR UPDATE in PostgreSQL and MySQL. The second session waits, as the MySQL run above shows. For write skew, lock every row the rule depends on, here both doctors.
  3. Check a version on writeKeep a version column, and write UPDATE ... SET version = version + 1 WHERE id = 1 AND version = 7. Zero rows updated means someone else got there first. This works the same way in all three engines.
  4. Use SERIALIZABLE and retryIn PostgreSQL, SERIALIZABLE caught the write skew. The price is that the application must retry failed transactions, and it must have a retry loop before you switch it on.

Steps 1, 3 and 4 are the standard fixes, and only the FOR UPDATE fix in MySQL and SERIALIZABLE in PostgreSQL are part of the notebook run so far. For the theory behind these anomalies, the transactions chapter of Designing Data-Intensive Applications is where I would start, and the MVCC lab shows why the snapshot is taken at the first query.

Check yourself · 4 questions

Check yourself

Pick an answer. You will see whether it is right, and why.

1. What is PostgreSQL's default isolation level?

MySQL's InnoDB defaults to REPEATABLE READ.

2. MySQL at REPEATABLE READ, two read-then-write deposits on one row. What did the run show?

An InnoDB UPDATE reads the latest committed row, not the snapshot, so the stale value overwrote the first deposit.

3. Which run stopped write skew?

It failed the second commit with a serialization error. The application must retry.

4. What is the simplest fix for a lost update on a counter?

The engine applies it to the current value, so there is no stale read to lose.
