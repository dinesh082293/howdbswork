MongoDB · WiredTiger

This page is about documents and replica sets. I show you where WiredTiger keeps every collection and index, and how two logs split the jobs: journal for crashes, oplog for the replica set. After it you will be able to find any collection's .wt file, read the oplog window, and check whether the cache is under pressure.

MongoDB · WiredTiger: in one line

A document database. JSON-like documents in collections. Built to run as a replica set.

Good at: Records that genuinely differ per item. Catalogues and profiles. Spreading across machines with built-in sharding. Two logs: journal for crashes, oplog for the replica set.

Runs as: mongod processes in a replica set; mongos routers when sharded

The architecture: processes, memory, disk

Same three layers as every engine: process, memory, disk. The layer rule is written once on the PostgreSQL page: name the layer first, then diagnose inside it.

MongoDB · WiredTiger: architecture

Request path

Processesmongod per member · the primary accepts writes, secondaries apply the oplog · mongos routers when sharded
→
MemoryWiredTiger cache (~50% of RAM − 1 GB) holding uncompressed data + the OS filesystem cache
→
Disk: the dbPathcollection-*.wt · index-*.wt · journal/WiredTigerLog.* · the oplog in local.oplog.rs
Who does what: The primary orders all writes into the oplog. WiredTiger checkpoints about every 60 s and makes the .wt files consistent. Secondaries tail the oplog and apply the same operations in the same order.

The log files · one by one

Same pattern as PostgreSQL: five logs, one job each, and every operational budget is a time window. The full version is on the PostgreSQL page.

MongoDB · WiredTiger

Journal

journal/WiredTigerLog.0000000123
Where it sits
The journal/ folder inside the dbPath. A sequence of WiredTigerLog.* files, written by the WiredTiger storage engine.
What it does
WiredTiger's write-ahead log. Data files are only made consistent at checkpoints, roughly every 60 seconds. The journal covers the gap. A write acknowledged with j: true is durable once its journal entry is on disk. On restart mongod replays the journal from the last checkpoint.
What breaks without it
A crash could lose every write since the last checkpoint. Up to about 60 seconds of acknowledged data. The journal exists to close exactly that gap.
Look at it
$ ls /var/lib/mongo/journal/ -- in mongosh: db.serverStatus().storageEngine db.adminCommand({getCmdLineOpts: 1}) -- parsed.storage.journal shows the journal settings
MongoDB

Oplog: the replica set log

local.oplog.rs
Where it sits
Not a file. A capped collection named oplog.rs in the local database, present on every replica set member. Capped means fixed-size. Old entries fall off the front as new ones arrive.
What it does
An ordered record of every write on the primary, each stamped with a timestamp. Secondaries continuously tail it and apply the same operations in the same order. Its size defines the oplog window. That is how far behind a secondary can fall and still catch up.
What breaks without it
No replica set at all. And if a secondary stays down longer than the oplog window, the entries it missed are gone. It must copy everything again (initial sync).
Look at it
// in mongosh: rs.printReplicationInfo() db.getSiblingDB('local').oplog.rs .find().sort({$natural: -1}).limit(1)

ESR: the index order that avoids a sort

Problem. My query filters, sorts, and returns. It runs slow. I run explain. It shows a SORT stage. The index exists. The sort still happens.

Mechanism. A compound index stores keys in field order. Field 1 first. Field 2 inside field 1. Field 3 inside field 2. Put the equality field first. Put the sort field second. Put the range field last. That is ESR.

The equality match narrows the walk to one slice. Inside that slice, the sort field is already in order. The query reads rows in sorted order. The range field sits last. It trims the tail.

Put the fields in the wrong order and the sort breaks. A range field before the sort field breaks it. The index can no longer hand back rows in sort order. MongoDB adds a SORT stage. That stage sorts in memory. The limit is 100 MB. A sort past that limit fails unless the query allows disk use.

ESR: equality, sort, range, in that order

Equality firststatus: collapses to one slice
→
Sort secondcreatedAt: already in order, no SORT stage
→
Range lastamount: trims the tail

Range before sort: the order breaks

Range firstamount: the ordering ends here
→
Sort field afterno longer in order
→
SORT stagein-memory sort, 100 MB limit

MongoDB caches the winning plan for a query shape. I add an index. I drop an index. The cached plan can go stale. I check the cached plans. Then I clear the cache for that collection. The next run picks a fresh plan.

Exact check. Build the index in ESR order. Then explain the query. Then check index use and plan cache.

db.orders.createIndex({ status: 1, createdAt: -1, amount: 1 }); db.orders.find( { status: "shipped", amount: { $gte: 100 } } ).sort({ createdAt: -1 }).explain("executionStats"); db.orders.aggregate([ { $indexStats: {} } ]); db.orders.aggregate([ { $planCacheStats: {} } ]); db.runCommand({ planCacheClear: "orders" });

Read explain for SORT stage. No SORT stage means the index order did the sorting. Read totalDocsExamined next to nReturned. A wide gap means the index is not narrowing the work.

One incident I keep coming back to

One big customer's dashboard timed out. Everyone else was fast.

I checked distribution, not totals. One node was at 100 percent and the rest were idle. A monotonic shard key was sending every new write to the same shard.

The fix was the key, not more shards. Hash-prefix a monotonic shard key, or give the whale tenant its own shard. Choose the shard key from the query pattern before launch.

The one invariant: COMMIT means the log record is on disk. pg_wal in PostgreSQL, #innodb_redo/#ib_redo0 + mysql-bin in MySQL, journal/WiredTigerLog + the oplog in MongoDB.
