Watch an index grow

Why do random UUID keys make inserts slower?

An index is a tree of pages, kept in key order. Insert rows below and watch where each key lands, when a page fills up and splits, and how full the pages stay. Then switch from sequential ids to random UUIDs and do it again.

You insert 300 rows with sequential ids, and 300 with random UUIDs. Which needs more pages, and roughly how many more?

Random UUIDs need about a third more pages, and split far more often in the middle of the tree. Sequential ids only ever split the last page, so every page they leave behind is full. Random keys split pages in the middle, and both halves stay part-empty. Press "Compare all three key types" below to see it.

What to notice

Four things the picture shows

  • Where new keys land. Sequential ids always go into the last page, so one page is busy and stays in memory. Random UUIDs land anywhere, so the last 20 inserts touch up to 20 different pages. On a real table those pages are often not in memory, and each one is a read from disk before the insert can happen.
  • How full the pages stay. When the last page fills, the engine starts a new one and leaves the old one full. When a page in the middle fills, it is split in half and both halves are left part-empty. Random keys end up around 70% full, so the same rows need more pages, more memory and more disk.
  • Time-ordered UUIDs behave almost like sequential ids. UUID v7 starts with a timestamp, and MySQL's UUID_TO_BIN(uuid, 1) moves the time part of a version 1 UUID to the front. Keys arrive roughly in order, so you keep globally unique ids without the random inserts.
  • What the tree is depends on the engine. In InnoDB the tree is the table: the rows live in the leaves, so random keys scatter the rows themselves. In PostgreSQL and MongoDB the rows are stored in arrival order and only the index is scattered, which is why a random primary key hurts InnoDB more.

Real pages are much bigger. Here a page holds 3 to 8 keys so you can see splits happen. A real 8 KB or 16 KB page holds hundreds of keys, so a table of millions of rows is only three or four levels deep. Real engines also leave a little room when they fill the last page: PostgreSQL leaves 10% free by default (fillfactor 90), and InnoDB tries to leave 1/16 of the page free.
