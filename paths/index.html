Path 1

I have an interview

Aim to be able to draw each step on a whiteboard and say what the file is called. That is the level these loops ask for.

  1. Three rules that run every databaseDurability, pages and the log. Everything else hangs off these three.
  2. Follow one insert, end to endThe story you will tell in the first five minutes of any internals question.
  3. Same task, three enginesA write, a crash, a lagging replica and a long transaction. These four come up in almost every loop.
  4. Break a database in the crash labSay what recovery replays, and why a checkpoint shortens it.
  5. The MVCC timeline and the B+ treeSnapshots, row versions, page splits and why index depth stays small.
  6. What a commit waits forThe sync and async trade-off, with the price of each.
  7. Sixteen real failuresPick three. Be ready to say what broke, what fixed it and what you would check first.
  8. Lost updates and write skewIsolation levels, watched instead of memorized. A favourite interview question.
  9. Lab notebooksReal numbers you can quote: what an index, a durable commit and a long transaction cost.
Path 2

I am on call and something is on fire

Read top to bottom. Do not skip the first step. Most of the time spent in an incident is spent looking in the wrong layer.

  1. Name the layer first: process, memory or diskEvery incident lives in one of the three. Naming it first saves ten minutes.
  2. The first five minutes checklistWhat to check, in order, before you touch anything.
  3. Which log answers which questionFive logs run everything. Know which one to open.
  4. The cheat sheetEight rules per engine, short enough to read while paged.
  5. Replica behind?Where the queue builds, and the command that shows it.
  6. Sessions piling up on one row?How fast a pool runs out, and which timeouts to set.
  7. Disk or bloat growing without a reason?A long transaction is the usual cause. Find it first.
  8. Engine commands to runThe commands for PostgreSQL, MySQL and MongoDB.
  9. Slow query with an index?Column order, OFFSET paging and N+1 explain most of these.
Path 3

I am choosing a database

The engine is the last decision to make. First write down the workload: what reads, what writes, how big, and what a lost commit costs.

  1. Database familiesB-tree, LSM, column, in-memory, distributed SQL and more, and the traffic each one suits.
  2. Pick the database from the workloadStart from what the application does, not from fashion.
  3. The three engines, side by sideHow each behaves in the same four situations.
  4. On-prem or cloudWhat changes when someone else runs the database.
  5. Why the bill is huge, and what to cut firstWhere the money goes, and a safe order for cutting it.
  6. When it starts to hurtThe signs that you outgrew a single node, and the options after.

The one invariant: COMMIT means the log record is on disk. pg_wal in PostgreSQL, #innodb_redo/#ib_redo0 + mysql-bin in MySQL, journal/WiredTigerLog + the oplog in MongoDB. The data files (base/…, *.ibd, collection-*.wt) are where checkpoints place the result afterwards, on their own schedule. Every guarantee on this page, durability, replication, point-in-time recovery, is a consequence of that ordering, and every number on this page is checkable with the commands given beside it.
