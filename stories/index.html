Real stories

Every page on this site explains a mechanism. This page shows what happens when the mechanism meets real traffic. Seven stories, all from companies that wrote up what broke. Each one has the numbers, the fix, and the lesson I took from it. The source is linked at the end of each story.

None of these are my incidents. I read them the way I read a postmortem: what broke first, what the numbers were, and what decision would have prevented it.

PostgreSQL · three stories

PostgreSQL: the layout is the cost

Two of these three stories are the same failure wearing different clothes. A physical layout decision, made early, priced later at scale. The third is a planner that had the right index and refused to use it.

PostgreSQL

Uber: one update became four writes, and the WAL crossed an ocean

Uber kept its trip data on one Postgres instance in early 2014. Trip growth ate disk so fast that the team expected to run out of room before the end of the year. The database would stop, not slow down.

One logical update, four physical writes

1 logical UPDATEone row changes
→
new row versionin the heap
index 1rewritten
index 2rewritten
index 12rewritten
primarywrites the WAL
→
physical WAL streamevery extra byte crosses the network
→
replica, other data centerreplays it all

A table with a dozen indexes rewrites all twelve on every update. The cost is physical, not logical.

They were running Postgres 9.2. Every update wrote a brand-new row version, and every secondary index pointed at the row's physical spot on disk. One logical update became 4 or more physical writes. A table with a dozen indexes rewrote all twelve on every update. The WAL stream was physical too, so every extra byte crossed the network to replicas in the other data center. A bug in 9.2 returned duplicate rows on replicas after a timeline switch, and the only fix was a full resync. Long queries on replicas got killed by cleanup. Upgrades needed full downtime, so old instances stayed on 9.2 while 9.5 was current.

The fix was Schemaless, built on MySQL and InnoDB. In InnoDB, a secondary index points at the primary key, not at a disk address. An update touches the row in place and leaves the other indexes alone. Replication is logical, through the binlog, so the stream across data centers is far smaller.

Write amplification went away. Replication got cheaper. Upgrades stopped needing full downtime. The lesson I take is not that Postgres is slow. The lesson is that index layout and replication format are the whole cost at write-heavy scale. One more thing: the post is from July 2016, about Postgres 9.2. Later versions fixed some of the named bugs. The layout difference is still real.

Source: Why Uber Engineering Switched from Postgres to MySQL, Uber Engineering Blog, July 26, 2016.

PostgreSQL

Notion: VACUUM stalled, and the database nearly stopped writing

Notion ran its product on one Postgres monolith. Every paragraph, heading, image, and to-do is a block, and every block is a row in one giant table. By mid-2020, usage had outgrown the single database.

Before and after: one monolith, 480 shards

Before

One Postgres monolith. Every block is a row in one giant table. VACUUM stalls, dead tuples pile up, and transaction ID wraparound threatens to stop all writes.

After

480 logical shards, 32 physical databases. Routing by workspace ID, so one workspace's data stays together.

32 physical databases, 15 logical shards each. The shard key is the whole project.

500 GBCap per table, set by the team before the migration.
10 TBCap per physical database.
60K IOPSCap per physical database.
5 minCutover downtime, after a 3-day backfill on a 96-CPU machine.

The trigger was specific. VACUUM started stalling, so dead tuples stopped being reclaimed and disk space stopped coming back. Behind that sat transaction ID wraparound. Postgres stops all writes rather than overwrite old data. That is not a slowdown. That is the product stopping.

The design was application-level sharding, routing by workspace ID so one workspace's data stays together. They built 480 logical shards spread across 32 physical databases. They set their own caps: 500 GB per table, 10 TB per physical database, 60K IOPS. Logical replication could not keep up with the block table's write volume during the first snapshot, so they moved to an audit-log double-write. The backfill ran 3 days on an m5.24xlarge with 96 CPUs. They used dark reads to verify, and the verification code was written by different people than the migration code. The cutover took 5 minutes of scheduled downtime.

Their own lessons: shard earlier, aim for zero downtime, and use a combined primary key instead of a separate partition key. Mine: the shard key decision is the whole project. Workspace ID kept queries local. Pick the key from the query pattern, and pick it before you are forced to.

Source: Herding elephants: Lessons learned from sharding Postgres at Notion, Notion Blog, October 6, 2021.

PostgreSQL

Notion again: the index existed, and the planner ignored it

Same company, different week. Notion ran one large Postgres database on RDS from 2015 to 2020. A new feature was already 20 percent of the application's query load before it shipped to everyone. One of its queries filtered JSON on space_id and permission.

Same query, two index shapes

GIN index existedon space_id and permission
→
planner skipped itpoor cardinality, stale statistics
→
jsonb_path_ops GINfits containment queries on JSON
Before, default GIN shape
about 5000 ms
After, jsonb_path_ops GIN
about 600 ms

More than 8 times faster. The index existed. The planner ignored it. The fix was the index shape, not a bigger instance.

The check showed a GIN index already existed on those columns. The planner was not using it on the development database. Poor cardinality and stale statistics made the planner skip it. The fix was a different index shape. A GIN index with jsonb_path_ops fits containment queries on JSON better than the default GIN shape.

The query went from about 5000 ms to about 600 ms. That is more than 8 times faster. Staging comparisons showed no mismatches, so it went to production cleanly.

Sourcing note: this one comes from a pganalyze case study, not from Notion's own blog. It quotes named Notion engineers, and the numbers line up with the sharding post's timeline. I keep it because the lesson is checkable. The index existed, the planner ignored it, and the fix was the index shape, not a bigger instance. When a query is slow, read the plan before you buy hardware.

Source: How Notion Runs PostgreSQL at Scale on Amazon RDS with pganalyze, pganalyze, February 27, 2025.

MySQL · four stories

MySQL: failover, upgrades, and the shard key

GitHub shows the two halves of operating MySQL at scale: the failover you automate, and the upgrade you survive. Slack and Shopify show the same lesson from the other side: the shard key decides everything, and the migration only works if you can compare both copies before you trust one.

MySQL

GitHub: the master died, and nobody woke up

GitHub stores its metadata in MySQL. Issues, pull requests, comments, organizations, notifications. One master takes the writes. Replicas serve the reads. A dead master used to mean a human waking up and running a failover by hand. That was too slow for the availability they wanted.

One master, three replicas, one watcher

mastertakes writes
Orchestratorwatches the cluster, asks the replicas what happened
guardrailone automatic failover per cluster, then blocked 30 minutes or until a human says go
replica 1serves reads
replica 2serves reads
replica 3, promotedmaster in 30 seconds or less

Detection plus a flap guard, not just a tool. Automation without a guardrail is a second outage waiting to happen.

They run Orchestrator. It watches the replication topology and runs the failover itself. Their target was detection plus recovery in 30 seconds or less, with minimal loss of hosts. Detection is holistic. It asks the replication cluster what happened instead of trusting one monitor. They tested its decisions for months before they turned on automatic recovery.

The guardrails matter as much as the tool. Flapping is not allowed. Orchestrator runs at most one automatic failover per cluster in a set time period. After a failover, the cluster is blocked from another one for 30 minutes, or until a human acknowledges it. It also handles a dead intermediate master, so a middle layer failing does not strand the replicas below it. Later work added Pseudo-GTID handling for replicas that fall behind or go unreachable.

My take: the failover tool is only half the story. The other half is the policy around it. One failover, then a block, then a human. Automation without a flap guard is a second outage waiting to happen. I check for that guardrail in any failover tool before I trust it.

Source: Orchestrator at GitHub, The GitHub Blog.

MySQL

GitHub: upgrading 1,200 MySQL hosts without dropping a query

The fleet was 1,200-plus MySQL hosts, a mix of Azure VMs and bare metal. They held 300-plus TB of data and served 5.5 million queries per second across 50-plus clusters. MySQL 5.7 was near end of life, so they moved to 8.0. Planning, testing, and the upgrade took over a year.

1,200+ hostsAzure VMs and bare metal, 300+ TB of data, 5.5M queries per second, 50+ clusters.
1+ yearPlanning, testing, and the upgrade. Prep started July 2022.
24 hoursValidation cycle per cluster before the rollback path closed.

The upgrade, in four steps

1

Jul 2022: 8.0 added to CI. 5.7 and 8.0 side by side, so regressions showed up before production.

2

Dual chains. 8.0 replicas online, one data center at a time, behind 5.7 primaries kept as rollback.

3

Promote. An 8.0 replica becomes primary through Orchestrator. No primary was ever upgraded in place.

4

24-hour validation. Then the 5.7 rollback path closes. The collation change, roles, and one replica bug bit along the way.

Prep started in July 2022. They added 8.0 to CI and ran 5.7 and 8.0 side by side, so regressions showed up before production. They never upgraded a primary in place. They brought 8.0 replicas online, one data center at a time, and promoted an 8.0 replica to primary through Orchestrator.

The rollback path was the design, not an afterthought. They kept 5.7 standbys behind the 8.0 primaries, so they could roll back without a disruption. Each cluster got a 24-hour validation cycle before the rollback path closed. The collation change bit them. Version 8.0 defaults to utf8mb4_0900_ai_ci, and 5.7 does not understand it, so backward replication broke. Roles broke replication too. A replica_preserve_commit_order bug, fixed in 8.0.28, was another one. A WHERE IN list with tens of thousands of values crashed MySQL.

My take: the upgrade was a replication project, not a version bump. If you cannot roll back, you cannot upgrade a fleet this size. I would copy the shape. Dual chains, one cluster at a time, a fixed validation window, and the rollback kept alive until the window closes.

Source: Upgrading GitHub.com to MySQL 8.0, The GitHub Blog, December 7, 2023.

Slack: the shard key was the hot spot

Slack started moving its MySQL datastores to Vitess in 2017. By December 2020, 99 percent of all MySQL traffic ran on Vitess. Peak load was 2.3 million queries per second: 2 million reads, 300 thousand writes. Median latency was 2 ms. p99 was 11 ms.

2.3M QPSPeak load. 2M reads, 300K writes. Median 2 ms, p99 11 ms.
99%Of all MySQL traffic on Vitess by December 2020.
+50% in a weekQuery rates in March 2020. They split a busy keyspace live and kept serving.

After: channel ID resharding

Traffic spreads. In March 2020 query rates rose 50 percent in one week. They split a busy keyspace live and kept serving.

write to bothdouble-write backfill
→

Sharding is a routing problem before it is a capacity problem.

The old shape was workspace sharding on active-active MySQL. It worked until a big customer landed on one shard and made it hot while the rest sat idle. Enterprise Grid and Slack Connect broke the model further, because one user's data now spanned workspaces.

The move was a re-shard by channel ID under Vitess. The migration ran on double-write backfill plus double-read diffing. Write to both, read from both, compare, and only then cut over. In March 2020, query rates rose 50 percent in one week. They split a busy keyspace horizontally and kept serving. Without resharding, they wrote, their largest customers would have had downtime.

The extra win came later. The same Vitess clusters now run their International Data Residency product in six regions. My take: sharding is a routing problem before it is a capacity problem. The channel key fixed the hot spot that the workspace key created. Pick the key from the access pattern, and build the migration so you can compare both copies before you trust one.

Source: Scaling Datastores at Slack with Vitess, Slack Engineering, December 1, 2020.

MySQL

Shopify: the verifiers were the project

The Shop app backend is Ruby on Rails on a single MySQL, their managed system called KateSQL. Growth was steep. Disk grew to many terabytes. Schema migrations took weeks. When the database got busy, they throttled background jobs.

The five verifiers, checked before any data moved

✓every query carries the sharding key
✓no transaction crosses databases
✓no transaction crosses shards
✓no write crosses shards
✓no join crosses keyspaces
step 1insert the row in the new shard
→
step 2delete it from the old shard

A commit that lands on one shard and fails on another does not roll back the first. Build the check first, move the data second.

The first fix was federation. GhostFerry moved whole tables onto new databases, and new domains got their own databases. That bought time and limited blast radius. It hit its own wall. Migrations on big tables still took weeks, joins across databases got hard, and the app had to know where every table lived.

The second fix was Vitess, sharded by user_id. User-owned data went into a sharded users keyspace. Everything else went into an unsharded global keyspace. Before moving, they built query verifiers into the app layer. The verifiers caught queries missing the sharding key, transactions crossing databases, transactions crossing shards, writes crossing shards, and queries joining across keyspaces. They removed cross-shard transactions entirely. A commit that lands on one shard and fails on another does not roll back the first. Moving a row across shards became two steps: insert in the new shard, then delete from the old one.

My take: the verifiers were the project. Shopify wrote that if they could credit one thing for the move working, it was the correctness of the verifiers. Sharding without a check that every query carries its key is a data corruption incident on a schedule. Build the check first, move the data second.

Source: Horizontally scaling the Rails backend of Shop app with Vitess, Shopify Engineering, January 17, 2024.
