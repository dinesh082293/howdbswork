1. Inside a data page

Problem

Databases never read or write one row at a time. They move whole pages between disk and memory.

So the page layout decides speed, waste, and how versions are tracked. If you understand the page, you understand most of the rest.

2. B+ tree lookup: finding one key among millions

Problem

A sequential scan of a 10-million-row table reads ~1,250,000 pages. A B+ tree lookup of the same table reads 3.

The derivation is arithmetic, not convention: an 8 KB internal page holds roughly 400 key-pointer pairs (fanout ≈ 400), so depth = log400(rows). 400² = 160,000 rows at depth 2; 400³ = 64 million at depth 3; 400⁴ = 25.6 billion at depth 4. Internal pages hold only guide keys; leaf pages hold keys plus row pointers. That is the entire mechanism, every index behavior on this page, including the ESR rule in the reference atlas, follows from how these pages store keys.
10K rowsScan: 125 pages, 5–20 ms. Passes every test.
1M rowsScan: 12,500 pages, 0.5–2 s. Users start noticing.
500K–2M rowsThe transition zone: scan cost crosses the timeout budget while traffic is also at its highest.
10M rowsScan: ~3–8 s per query. An incident, not a slowdown.

The consequence: at 1 billion rows the tree is about 4 levels deep. That is one additional page read versus 10 million rows. A missing index is not a percentage regression. It is a change of complexity class, from O(log N) page reads to O(N). That is why the same query passes QA at 10K rows and pages the on-call at 10M, with no code change in between.

3. MVCC: two transactions, one row, no waiting

Problem

Transaction B is reading a balance while transaction A changes it. Locking the row would freeze B; overwriting would corrupt B's total.

Fix (MVCC): never overwrite. A creates a new version; B keeps reading the version from its snapshot. Old versions are removed later, by VACUUM in PostgreSQL, by purge of the undo log in InnoDB.

One account balance starts at 100. A changes it to 150. B started reading before A committed. So B should still see 100. Run the steps in order:

Try this order: A BEGIN, B BEGIN, A UPDATE, A COMMIT, B SELECT. B still sees 100. That is snapshot isolation, and it is the default behaviour in all three engines.

Same trick, 3 mechanisms: PostgreSQL stores both tuple versions in the heap file until VACUUM. InnoDB stores the new version in users.ibd and rebuilds the old one from undo records. WiredTiger keeps timestamped versions in its cache.
