PostgreSQL

PostgreSQL, WAL first, commit second

The number, why this mechanism existsA commit costs one sequential fsync: a WAL record of a few hundred bytes. Writing the data instead would mean the heap page plus one page per index, 4 or more random 8 KB writes, each needing its own ordering guarantee. One sequential write at ~0.1-1 ms replaces all of them: commit cost drops from O(pages touched) to O(1).
Problem

The data page cannot be forced to disk on every commit, that is far too slow, yet a committed row must never be lost.

10 MB of WAL/dayAny default survives. Archiving is a nice-to-have.
~1-2 GB/dayArchiving and retention become real jobs; a missed archive is visible within a day.
Transition: 50-100 MB/minCheckpoint and archive throughput become the write ceiling. Requested checkpoints appear in pg_stat_checkpointer.
1+ GB/min at peakWAL generation rate, not table size, not CPU, is the instance's write limit. Sizing is a capacity decision.

Mechanism, derived from the layout

Commit latency becomes one sequential fsync instead of random page writes. WAL generation rate (MB/s) is the real write ceiling of the instance, not table size.

The tradeoff

synchronous_commit = on is the safe default. off buys latency by risking the last ~3× wal_writer_delay of commits on an OS crash, acceptable for staging or rebuildable data, never for payments. local still fsyncs the WAL on the primary and only skips waiting for the standby, so a failover can lose commits that a primary restart would not.

Where it breaks

Root cause: WAL archiving fails, or a dead standby / replication slot holds segments past the reach of every checkpoint.

Blast radius: pg_wal/ grows until the filesystem reaches 100%, at which point the primary panics and stops accepting writes. A durability mechanism becomes the outage, and recovery is blocked until space is freed without deleting held segments by hand.

Mitigation: Alert on pg_wal size and per-slot lag in bytes; drop dead slots; fix archiving before it is an emergency; keep pg_wal on its own filesystem so it cannot starve the data files.

Common staff-level mistake

Sizing max_wal_size by guesswork, or putting pg_wal on the same saturated disk as the data files.

The metric that exposes it first

Requested vs timed checkpoints in pg_stat_checkpointer, plus WAL bytes/s in pg_stat_wal. Requested outnumbering timed means max_wal_size is too small for your write rate.

MySQL · InnoDB

MySQL, redo + binlog must agree (two-phase commit)

The number, why this mechanism existsTwo logs record the same transaction in two vocabularies: redo says these bytes of this page changed, the binlog says this transaction happened. If a crash leaves them disagreeing by even one transaction, the source and every replica hold different data, with no error raised anywhere. Two-phase commit exists so the committed-transaction count in both logs is always identical.
Problem

InnoDB and the binary log are two separate logs; a crash must never leave a row in one and not the other.

Dev / stagingSettings barely matter; crashes are free lessons.
Real traffic, safe settingsflush=1 + sync_binlog=1: full safety, commit cost = 2 fsyncs.
Transition: someone benchmarks with flush=2Throughput looks better in the load test. The config ships.
First OS crash in productionUp to ~1 s of commits missing from one or both logs. Replicas diverge silently; PITR replays a history that never happened.

Situation, the physical organization, drawn for this problem

Mechanism, derived from the layout

Redo rebuilds pages on this server; the binlog rebuilds data on other servers. The internal two-phase commit is what keeps replicas and point-in-time recovery consistent with the engine.

The tradeoff

flush=1 + sync_binlog=1 is the only fully safe pair. flush=2 or sync_binlog=0 trades durability for throughput, the classic silent data-loss setting found in inherited configs.

In Practice, real output, red flags named

What proves health: the variable pair reads 1, 1 and 'Log flushed up to' tracks the sequence number. Red flags: either variable relaxed on a server holding real data; gtid_executed differing between source and replica after a failover, the set difference is exactly the transactions one side has and the other does not.

SHOW ENGINE INNODB STATUS\G -- LOG section SELECT @@innodb_flush_log_at_trx_commit, @@sync_binlog, @@gtid_executed;
Where it breaks

Root cause: Durability settings relaxed for a benchmark or copied from a tuning blog, then never restored.

Blast radius: An OS crash loses up to ~1 second of commits from redo and/or the binlog. Because nothing errors, replicas diverge quietly and the divergence surfaces days later as missing or phantom rows.

Mitigation: flush=1 + sync_binlog=1 on anything holding real data; keep the pair under config management so a benchmark cannot ship it; compare gtid_executed on both sides after every failover.

Common staff-level mistake

Benchmarking with flush=2, shipping it to production, and discovering it during the first real crash.

The metric that exposes it first

Binlog fsync latency and redo write waits under peak load; any gap between gtid_executed on source vs replica after a failover.

MongoDB · WiredTiger

MongoDB, journal is durability, oplog is replication

The number, why this mechanism existsTwo numbers that are constantly confused: journal latency is measured in milliseconds (this node's crash safety); the oplog window is measured in hours (the set's catch-up budget). A write with w: 1 can be journaled in ~1 ms and still be rolled back minutes later in an election. Durability on one node is not durability of the set.
Problem

Two different logs get confused constantly: one protects against a crash on this node, the other keeps the replica set identical.

Single node / dev setJournal alone is the whole story. w:1 feels safe.
Replica set, w:1 writesFirst election rolls back acknowledged writes. The rollback/ directory gets its first files.
Transition: write volume grows 10×Same oplog size, one-tenth the window. Nobody recomputed it.
Window < maintenance durationA member down for routine work returns to a full initial sync, during peak traffic.

Mechanism, derived from the layout

A write can be journaled (safe on this node) yet still roll back in an election if a majority never saw it. Staff-level MongoDB work starts by separating these two guarantees.

The tradeoff

writeConcern { w: 1 } is fast and rollback-prone. { w: 'majority', j: true } costs cross-member latency and is the only setting where acknowledged means survives an election.

What proves health: the window (26.4 h here) exceeds your longest planned maintenance with margin. Red flags: window shrinking month over month at the same oplog size (write rate is eating it); per-member lag in rs.status() growing linearly, that is apply throughput, not network.

db.serverStatus().wiredTiger.log rs.printReplicationInfo() // oplog window rs.status() // per-member lag
Where it breaks

Root cause: Journal and data files share one contended volume, so journal fsyncs queue behind checkpoint writes; or writes are acknowledged with w: 1 and never reach a majority before an election.

Blast radius: Either every j:true write inherits the volume contention (commit latency degrades instance-wide), or acknowledged writes roll back in an election and land in rollback/, application-level data loss on a cluster that reports itself healthy.

Mitigation: Put the journal on its own volume; use { w: 'majority', j: true } for any write that must survive an election; alert on oplog window hours and lag slope, not just lag.

Common staff-level mistake

Treating the oplog as a backup or as the crash log, it is neither; it is a capped replication stream.

The metric that exposes it first

Journal commit latency in serverStatus, plus secondary lag in seconds. Lag growing linearly = apply throughput, not network, is the bottleneck.

Remember: COMMIT means the log record is on disk. Everything else, checkpoints, replicas, backups, is built on that one ordering rule.
Problem

Every page a query needs is either already in RAM (~100 ns to use) or must be read from disk (~80 µs on NVMe, ~10 ms on a hard disk), a 1,000× to 100,000× difference decided entirely by what the cache kept and what it evicted.

PostgreSQL

PostgreSQL, shared_buffers, clock sweep, bgwriter, checkpoints

The number, why this mechanism existsThe arithmetic of a hit ratio: at 10,000 queries/second, 99% hits still means 100 disk reads/second; at 95% it is 500/second and the disk is now the database. A miss is not just slower, if the page evicted to make room is dirty, the miss also pays a write first. Eviction is the only place a read can be forced to do write I/O.
Problem

When a backend needs a page that is not cached, something else must leave, and if the victim is dirty, someone must write it first.

10K rowsThe whole table fits in shared_buffers. Every plan looks fast.
1M rowsWorking set ≈ cache. Hit ratio still above 99%; nothing to see.
Transition: working set crosses total cacheMisses begin; dirty victims make some reads pay a write. Latency develops a sawtooth synced to checkpoints.
10M+ rowsEviction churn dominates: buffers_alloc climbs, unrelated queries slow down because hot pages keep getting evicted by scans.

Mechanism, derived from the layout

Eviction cost lands on foreground queries when background flushing falls behind: the classic sawtooth latency pattern that tracks the checkpoint cycle exactly.

The tradeoff

shared_buffers around 25% of RAM is the usual start. Much larger double-buffers against the OS page cache and makes checkpoints heavier; much smaller forces constant eviction churn.

In Practice, real output, red flags named

What proves health: timed checkpoints dominate, requested are a small share, and buffers_alloc is flat. Red flags: num_requested outnumbering num_timed; latency graphs that spike on the checkpoint interval.

SELECT num_timed, num_requested, buffers_written FROM pg_stat_checkpointer; SELECT buffers_clean, maxwritten_clean, buffers_alloc FROM pg_stat_bgwriter;
Where it breaks

Root cause: The working set outgrew the cache, or checkpoint settings (small max_wal_size, short checkpoint_timeout) force write bursts faster than the bgwriter's steady pace.

Blast radius: Foreground queries pay eviction and dirty-write cost directly: p99 latency sawtooths in sync with checkpoints across the whole instance, including queries that touch none of the hot data.

Mitigation: Size shared_buffers around 25% of RAM; raise max_wal_size to stretch checkpoints; tune bgwriter aggressiveness; verify with buffers_* deltas over a peak hour, not by feel.

Common staff-level mistake

Raising shared_buffers to 70-80% of RAM because more cache must be better.

The metric that exposes it first

num_requested outnumbering num_timed and buffers_alloc climbing fast, the working set does not fit, or max_wal_size forces write bursts.

MySQL · InnoDB

MySQL, buffer pool, redo capacity, and checkpoint age

The number, why this mechanism existsCheckpoint age is a subtraction: redo capacity minus the LSN span of unflushed dirty pages. At ~75% of capacity InnoDB starts flushing aggressively; near 100% it throttles writes until flushing catches up. A 1 GB redo log absorbing 20 MB/s of page changes holds 50 seconds of headroom. That number, not the instance size, is the write-burst budget.
Problem

Dirty pages can only be overwritten in the redo log after they are flushed; if flushing falls behind writes, the log wraps into unwritten work.

Low write rateCheckpoint age sits near zero. Redo size is invisible.
Steady writesAge stabilizes where flush rate equals write rate. Still fine.
Transition: burst length × rate > capacityAge crosses ~75% during every peak. Aggressive flushing begins; write latency rises exactly at peak load.
Sustained overloadAge pinned at capacity: writes stall to flush speed. The database is slowest precisely when the business is busiest.

Mechanism, derived from the layout

Checkpoint age is InnoDB headroom. Near capacity, InnoDB switches to aggressive flushing and write stalls, the database slows down precisely at peak write load.

The tradeoff

Bigger innodb_redo_log_capacity (8.0.30+, up to 512 GiB) smooths write bursts and reduces flush pressure, at the cost of disk space and longer worst-case crash recovery.

In Practice, real output, red flags named

The derived check: checkpoint age ÷ innodb_redo_log_capacity. Under ~50% is headroom; sustained above ~75% means flushing cannot match the write rate. Red flags: 'Modified db pages' large and still growing at constant load; pending writes queuing in the FILE I/O section.

SHOW ENGINE INNODB STATUS\G -- FILE I/O + LOG: 'Checkpoint age', 'Modified db pages', pending writes
Where it breaks

Root cause: Redo capacity sized for the average write rate instead of the peak, or flush throughput (storage) lower than the dirty-page generation rate.

Blast radius: Write latency spikes at peak load, InnoDB deliberately throttles all writers to protect crash recovery. In the worst case, near-stalls on the primary during the highest-value traffic of the day.

Mitigation: Raise innodb_redo_log_capacity (resizable online in 8.0.30+); alert at 75% checkpoint age; if age stays high after resizing, the bottleneck is flush throughput, fix storage, not settings.

Common staff-level mistake

Leaving a small redo log on a write-heavy primary, then tuning everything except the redo log.

The metric that exposes it first

Checkpoint age as a percentage of redo capacity. Sustained above ~75% means flushing cannot keep up with the write rate.

MongoDB · WiredTiger

MongoDB, WiredTiger cache eviction

The number, why this mechanism existsThe WiredTiger cache defaults to 50% of (RAM − 1 GB), and two percentages run it: eviction target 5% dirty, eviction trigger 20% dirty. Below target, background workers evict quietly. Above trigger, application threads are forced to evict before they may proceed, an operation that cost 1 ms now costs a disk write first: 10-100× slower, on every operation, instance-wide.
Problem

Reads and writes happen in the cache; when it fills with dirty pages, eviction, not disk speed, becomes the latency.

Working set fits in cacheEviction is background noise. Dirty bytes hover near target.
Write rate growsDirty bytes oscillate between target and trigger at peak. Still absorbed.
Transition: dirty pinned above the 20% triggerApplication threads start evicting. First multi-second stalls appear while CPU and disk look only moderately busy.
ChronicEvery operation inherits eviction cost. Teams upgrade disks and see no improvement, because the bottleneck was never disk speed.

Mechanism, derived from the layout

The single most common WiredTiger production issue: once application threads are forced to do eviction work, every operation inherits disk latency.

The tradeoff

A larger cacheSizeGB holds more working set but starves the OS filesystem cache that WiredTiger also depends on. Default exists for a reason; change it with evidence.

In Practice, real output, red flags named

"pages evicted by worker threads"     : 9.1M    ← background eviction: healthy

What proves health: dirty bytes under the trigger and application-thread evictions at exactly zero. Red flag: the app-thread eviction counter moving at all, it is the single most diagnostic number in WiredTiger serverStatus output.

db.serverStatus().wiredTiger.cache // read: 'tracked dirty bytes in the cache', // 'pages evicted by application threads'
Where it breaks

Root cause: The working set or the write burst exceeds what the cache can hold and clean at the rate operations dirty it, eviction workers fall behind and the debt is handed to application threads.

Blast radius: Instance-wide multi-second operation stalls while CPU and disk utilisation look unremarkable, the hardest WiredTiger incident to recognise, because every standard dashboard says the hardware is fine.

Mitigation: Reduce dirty-page generation (batch writes, fix the scan that churns the cache), add RAM or shrink the working set; tune eviction threads only with serverStatus evidence; alert on application-thread evictions > 0.

Common staff-level mistake

Blaming slow disks and upgrading storage when the real problem is cache pressure from a working set that outgrew RAM.

The metric that exposes it first

Pages evicted by application threads greater than zero, and tracked dirty bytes sustained above the 20% trigger.

Remember: Size the cache for the working set, then watch who evicts: background threads are healthy, application threads evicting is a latency alarm in all three engines.
Problem

Every index adds one B-tree write to every INSERT and UPDATE on its table, forever; in exchange it cuts a lookup from N pages to about 3. The staff skill is pricing both sides of that trade in numbers, not adjectives.

PostgreSQL

PostgreSQL, index-only scans and the visibility map

The number, why this mechanism existsCount the pages for a 1,000-row lookup. Index scan: ~3 index pages + 1,000 heap pages, one random fetch per row, the index walk is 0.3% of the cost. Index-only scan with a current visibility map: 0 heap pages. The same query drops from ~1,003 page reads to ~10, and the only thing that changed is one bit per page in a side file (16397_vm) that VACUUM maintains.
Problem

A normal index scan still fetches the heap page for every row, mostly to check visibility, random I/O that dwarfs the index walk on big lookups.

Small tableHeap fetches are cached anyway. The distinction is invisible.
Index-only scan adoptedHeap Fetches: 0 in EXPLAIN. The win is real while vacuum keeps up.
Transition: update rate outpaces vacuumVisibility map goes stale page by page. Heap Fetches creep from 0 to hundreds per query, no deploy, no error.
ProductionThe plan still says Index Only Scan. The cost is back to index-scan levels, but the wider index still adds its write to every INSERT and UPDATE.

Mechanism, derived from the layout

A covering index plus a current visibility map turns a lookup into index pages only. This is often the largest single read win available on a hot query.

The tradeoff

Wider indexes cost write I/O, WAL volume, and cache on every insert and update, and the win evaporates if vacuum lets the visibility map go stale.

In Practice, real output, red flags named

  Buffers: shared hit=4  ← 4 pages total for the lookup

  Heap Fetches: 48,213   ← the plan lies by omission: 48k heap fetches behind it

Read the Heap Fetches line, not the scan type. The planner prints 'Index Only Scan' in both cases; only the fetch count separates a 4-page lookup from a 48,000-fetch one. Red flag: Heap Fetches in the hundreds on any top-10 query.

EXPLAIN (ANALYZE, BUFFERS) SELECT …; -- read the 'Heap Fetches: N' line, not just the scan type
Where it breaks

Root cause: Autovacuum is not keeping the visibility map current on an update-heavy table, so the per-page 'all visible' bits are unset and every row needs a heap visit to confirm visibility.

Blast radius: The covering index delivers almost none of its promised win while its full write cost remains, read latency stays high on the hot query and write throughput is permanently lower than before the index was added.

Mitigation: Tune autovacuum per table (lower scale factor on the hot tables) so the visibility map stays current; track Heap Fetches on the top queries; only widen indexes after the map is proven current.

Common staff-level mistake

Adding ever-wider covering indexes to a table whose real problem is vacuum not keeping the visibility map current.

The metric that exposes it first

Heap Fetches per index-only scan on the top queries, and the ratio of index-only to plain index scans in pg_stat_user_indexes.

PostgreSQL

PostgreSQL, HOT updates: change a row without touching any index

The number, why this mechanism existsPrice one UPDATE of a row in a table with 4 indexes. Non-HOT: 1 heap write + 4 index writes, and 5 dead entries left for vacuum. HOT: 1 heap write, 0 index writes, cleaned up by pruning on the next read of that page. At 5,000 updates/second that is 25,000 page writes/second versus 5,000, a 5× write reduction from changing nothing but which columns the UPDATE touches and how full the page is.
Problem

If every UPDATE rewrites every index entry, a hot row with 4 indexes costs 5 writes and floods vacuum with dead index entries.

Low update rateHOT is a curiosity. Bloat is unmeasurable.
Update-heavy table, HOT workinghot_pct above 90%: updates cost one heap write each.
Transition: one indexed column joins the SET listHOT eligibility drops to zero for those updates. No schema change, no error, cost per update jumps 5-10× overnight.
ProductionDead index entries flood vacuum, pages bloat, and the team tunes autovacuum harder to treat a symptom created by the update pattern.

Mechanism, derived from the layout

Heap-Only Tuple updates are why fillfactor and column choice decide update throughput on hot tables like sessions, counters, and queues.

The tradeoff

fillfactor 70-80 leaves room in each page for HOT chains but stores fewer rows per page, more pages, more cache pressure on scans.

What proves health: hot_pct above ~90% on tables whose updates avoid indexed columns. Red flag: hot_pct under 50% on an update-dominated table, before touching autovacuum, check the SET list of the top updater and the table's fillfactor.

Where it breaks

Root cause: An indexed column appears in the UPDATE's SET list, or fillfactor 100 leaves no free space on the page for the new tuple version, either one breaks HOT eligibility.

Blast radius: Update cost on the hottest table multiplies 5-10×, dead index entries multiply vacuum work by the same factor, and bloat accelerates, while every dashboard attributes it to 'growth'.

Mitigation: Set fillfactor 70-80 on update-heavy tables; keep indexed columns out of hot UPDATE statements (split the row if necessary); alert on hot_pct below ~50%.

Common staff-level mistake

Leaving fillfactor at 100 on an update-heavy table, then fighting the resulting bloat with bigger autovacuum.

The metric that exposes it first

HOT percentage below ~50% on a table dominated by updates to non-indexed columns.

MySQL · InnoDB

MySQL, change buffer and adaptive hash index

The number, why this mechanism existsInserting into a secondary index whose leaf page is not in the buffer pool costs one random read (~80 µs-10 ms) just to insert one row. The change buffer records the change in ibdata1 instead, zero reads, and merges it later, in bulk, when the page is next loaded for any reason. The cost is not removed; it is deferred and moved onto the next reader of that page.
Problem

Inserting into a secondary index whose page is not in memory forces a random disk read for every row, unless the change can be deferred.

Indexes fit in the buffer poolChange buffer mostly idle; inserts read pages that are already cached.
Cold secondary indexes, steady insertsIbuf grows; merges happen in the background as pages cycle through.
Transition: write burst, then a read stormEvery read of a cold page first merges its backlog of buffered changes. Read latency spikes with no change to the read queries.
ProductionPost-burst slowdowns get misdiagnosed as 'the reads got slower', and someone disables the change buffer, making the original write problem permanent.

Mechanism, derived from the layout

The change buffer turns random I/O into sequential merge work for non-unique secondary indexes. The adaptive hash index (AHI) silently accelerates repeated exact-match lookups on hot pages.

The tradeoff

Change buffer can consume up to 25% of the buffer pool and its merge cost lands on later reads. AHI costs memory and can become a latch hotspot; it helps point lookups, never range scans. MySQL 8.4 changed both defaults: innodb_adaptive_hash_index is OFF and innodb_change_buffering is none, so on a stock 8.4 server neither does anything until you enable it. Where it breaks

Root cause: The oplog was sized once, as a percentage of disk at install time, and never recomputed after write volume grew, the window is a rate-dependent quantity being managed as a static one.

Blast radius: A routine 4-hour maintenance exceeds a 3-hour window; the member returns to a full initial sync during Monday peak traffic, hours of extra load on the primary and a second full copy of the dataset moving across the network.

Mitigation: Size the oplog so the window exceeds the longest planned maintenance plus margin; resize live with replSetResizeOplog; recompute the window monthly against the current write rate and alert when it falls below your maintenance bound.

Common staff-level mistake

Sizing the oplog by disk percentage at install and never recomputing the window after write volume grows 10×.

The metric that exposes it first

Oplog window in hours, recomputed monthly against write rate, alert when it falls below your longest planned maintenance.

Remember: Scale work is window math: WAL generated per checkpoint, chunks balanced per shard, oplog hours per outage. If you cannot state the window, you do not know your headroom.

2. B+ tree lookup: finding one key among millions

Problem

A sequential scan of a 10-million-row table reads ~1,250,000 pages. A B+ tree lookup of the same table reads 4 buffers: 3 index pages and 1 heap page.

The derivation is arithmetic, not convention: an 8 KB internal page holds roughly 400 key-pointer pairs (fanout ≈ 400), so depth = log400(rows). 400² = 160,000 rows at depth 2; 400³ = 64 million at depth 3; 400⁴ = 25.6 billion at depth 4. Internal pages hold only guide keys; leaf pages hold keys plus row pointers. That is the entire mechanism, every index behavior on this page, including the ESR rule in the reference atlas, follows from how these pages store keys.
10K rowsScan: 1,250 pages (10 MB), 5-20 ms. Passes every test.
1M rowsScan: 125,000 pages (1 GB), 0.5-2 s. Users start noticing.
500K-2M rowsThe transition zone: scan cost crosses the timeout budget while traffic is also at its highest.
10M rowsScan: ~3-8 s per query. An incident, not a slowdown.

The consequence: at 1 billion rows the tree is about 4 levels deep. That is one additional page read versus 10 million rows. A missing index is not a percentage regression. It is a change of complexity class, from O(log N) page reads to O(N). That is why the same query passes QA at 10K rows and pages the on-call at 10M, with no code change in between.

3. MVCC: two transactions, one row, no waiting

Problem

Transaction B is reading a balance while transaction A changes it. Locking the row would freeze B; overwriting would corrupt B's total.

Fix (MVCC): never overwrite. A creates a new version; B keeps reading the version from its snapshot. Old versions are removed later, by VACUUM in PostgreSQL, by purge of the undo log in InnoDB.

One account balance starts at 100. A changes it to 150. Whether B sees 100 or 150 depends on when B's snapshot is taken and on the isolation level. Choose a level for B, then run the steps:

Transaction A: the writer

Transaction B: the reader

B sees: -
Try this order under Repeatable Read: A BEGIN, B BEGIN, B SELECT (sees 100), A UPDATE, A COMMIT, B SELECT again (still 100). Switch B to Read Committed and repeat: the last SELECT sees 150. If B only runs its first SELECT after A commits, B sees 150 under either level, because the snapshot is taken at the first query, not at BEGIN.

Same trick, 3 mechanisms: PostgreSQL stores both tuple versions in the heap file until VACUUM. InnoDB stores the new version in users.ibd and rebuilds the old one from undo records. WiredTiger keeps timestamped versions in its cache.

MongoDBIndexes

Compound index order, the ESR rule

Problem: A combined index silently stops helping if its fields are in the wrong order.

Diagram, one problem, one diagram

Equality fields
→
Sort fields
→
Range fields

Derived, not conventional: a compound B-tree stores keys sorted by field 1, then within equal field-1 values by field 2, then by field 3. Equality on field 1 therefore collapses the scan to one contiguous range (O(log N) to locate); within that range field 2 is already in stored sort order, so no SORT stage is needed; a range predicate ends the usable ordering, so range fields must come last or they destroy the sort guarantee for everything after them. Equality → Sort → Range (ESR) is the only order preserving all three. Full derivation in 'Reading the evidence' above.

Tradeoff: One compound index serves a family of queries only in ESR order; the wrong order silently serves half the query.

What breaks & the check: Index exists but explain shows a COLLSCAN or huge docsExamined. Detect: explain('executionStats'), index used yet totalDocsExamined >> nReturned.

Try: db.users.find(…).explain('executionStats'), check totalDocsExamined ÷ nReturned

MySQLSafety

Undo log & purge

Problem: Readers need old row versions, and failed transactions need to be undone, both come from the same place.

Diagram, one problem, one diagram

UPDATE
→
Undo record in undo_001
→
Purge when no read view needs it

InnoDB writes undo records (in undo_001/undo_002 tablespaces) before modifying a row. A reader's snapshot rebuilds old versions from them; rollback replays them in reverse. The purge thread deletes undo only when no open transaction can still need it, one long transaction makes undo grow without bound.

Tradeoff: Undo enables consistent reads without locking, priced as purge debt that one long transaction can make unbounded.

What breaks & the check: History list length in the millions. Detect: SHOW ENGINE INNODB STATUS, TRANSACTIONS section; oldest entry in information_schema.innodb_trx.

Problem: When two transactions touch the same rows, someone must decide what each is allowed to see.

Diagram, one problem, one diagram

→

→
Anomalies allowed vs retries paid

Levels trade surprises for speed: Read Committed (fresh snapshot per statement), Repeatable Read (one snapshot per transaction), Serializable (as if transactions ran one at a time; PostgreSQL may abort one to keep that promise). Know your engine's default before debugging 'weird reads'.

Streaming replication ships WAL bytes, the standby must be the same version and ends up byte-identical. Logical replication decodes WAL into per-table row changes, use it for major-version upgrades and selective copies.

Diagram, one problem, one diagram

→

→

Redo (#innodb_redo/#ib_redo0-31; ib_logfile0/1 before 8.0.30) replays page changes after a crash. The doublewrite buffer (#ib_16384_*.dblwr) writes each flushed page to a safe area first, then to its real place; on recovery a torn page is restored from the doublewrite copy.
