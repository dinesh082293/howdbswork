Something is slow or broken

What do I check first, and what is it usually?

Pick the symptom that matches what you see. Each one lists the causes I would check, most common first, the first safe move, and the commands to run for your engine. Most commands only read. The few that change something (refreshing statistics, clearing a plan cache, turning on the profiler) are safe to run and say so in a comment.

Too many connections

What you see. New connections fail with "too many connections" (MySQL, PostgreSQL) or the app's pool times out waiting for one. Often right after a deploy, a failover or a traffic spike.

Likely causes, most common first

  1. Each app instance opens its own pool, and instances × pool size went past the server limit. A deploy that doubles instances for a few minutes is enough.
  2. Connections are held while idle in a transaction, so the pool runs dry while the database is mostly idle.
  3. Queries got slower, so each connection is busy longer and more are needed for the same traffic.
  4. Clients reconnect all at once after a failover or restart.

First move. Find who holds the connections before raising the limit. Raising max_connections on PostgreSQL costs memory per process and can make a slow server slower. Kill sessions idle in a transaction for minutes.

Run these first

PostgreSQL
SHOW max_connections;
SELECT usename, application_name, state, count(*)
FROM pg_stat_activity GROUP BY 1, 2, 3 ORDER BY 4 DESC;
-- sessions holding a transaction open while doing nothing
SELECT pid, now() - xact_start AS open_for, query
FROM pg_stat_activity WHERE state = 'idle in transaction'
ORDER BY open_for DESC LIMIT 10;
MySQL
SHOW VARIABLES LIKE 'max_connections';
SHOW GLOBAL STATUS WHERE Variable_name IN
  ('Threads_connected', 'Threads_running', 'Max_used_connections');
SELECT user, command, count(*) FROM performance_schema.processlist
GROUP BY 1, 2 ORDER BY 3 DESC;
MongoDB
db.serverStatus().connections   // current, available, totalCreated
db.currentOp(true).inprog.length
// who is connected, by app name
db.aggregate([{ $currentOp: { allUsers: true, idleConnections: true } },
  { $group: { _id: "$appName", n: { $sum: 1 } } }, { $sort: { n: -1 } }])

CPU at 100%

What you see. The database CPU is pinned and everything is slower. Often no single query looks slow on its own.

Likely causes, most common first

  1. A query that runs thousands of times a second lost its index or changed plan.
  2. A new feature added a query without an index: each call scans.
  3. Many short queries with high per-call overhead, such as one query per row in a loop.
  4. Sorting or hashing large results in memory.

First move. Rank queries by total time, not by the slowest single run. The query to fix is usually a fast one that runs very often.

Run these first

PostgreSQL
-- needs the pg_stat_statements extension
SELECT calls, round(total_exec_time) AS total_ms,
       round(mean_exec_time::numeric, 2) AS mean_ms, left(query, 80)
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
SELECT state, wait_event_type, wait_event, count(*)
FROM pg_stat_activity GROUP BY 1, 2, 3 ORDER BY 4 DESC;
MySQL
-- the sys schema, sorted by total latency
SELECT query, exec_count, total_latency, rows_examined_avg
FROM sys.statement_analysis LIMIT 10;
SELECT * FROM sys.statements_with_full_table_scans LIMIT 10;
MongoDB
db.currentOp({ active: true, secs_running: { $gte: 1 } })
db.setProfilingLevel(1, { slowms: 50 })   // changes a setting: logs ops over 50 ms
db.system.profile.find().sort({ millis: -1 }).limit(5)
// planSummary "COLLSCAN" means no index was used

The disk is filling up

What you see. Free space is falling faster than the data is growing, or an alert fired at 85%.

Likely causes, most common first

  1. Log files are being kept: a PostgreSQL replication slot whose reader is gone, MySQL binlogs kept for 30 days by default, a MongoDB oplog sized large.
  2. Dead rows or old versions are not being cleaned up, so tables grow without growing in rows.
  3. A large temporary sort or index build.
  4. Real growth that nobody projected.

First move. Find out which of data, logs or temp files is growing before deleting anything. Never delete WAL, redo or binlog files by hand.

Run these first

PostgreSQL
SELECT slot_name, active,
  pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_kept
FROM pg_replication_slots;
SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) AS size
FROM pg_statio_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 10;
MySQL
SHOW BINARY LOGS;
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';
SELECT table_schema, table_name,
  round((data_length + index_length + data_free) / 1024 / 1024) AS mb
FROM information_schema.tables ORDER BY mb DESC LIMIT 10;
MongoDB
db.stats(1024 * 1024)            // sizes in MB
rs.printReplicationInfo()          // oplog size and window
db.orders.stats().wiredTiger["block-manager"]["file bytes available for reuse"]

A replica is far behind

What you see. Reads from replicas return old data, or the lag alert fired. A failover now would lose more, or take longer.

Likely causes, most common first

  1. One large transaction on the primary: a big DELETE or UPDATE replays as one long unit.
  2. The replica applies changes with fewer threads than the primary writes them.
  3. Long queries on the replica block or delay replay.
  4. The replica has a slower disk, or is busy with backups or reports.

First move. Check whether the replica is receiving changes or applying them; the fix is different. Do not fail over to a lagging replica unless you have accepted the loss.

Run these first

PostgreSQL
-- on the primary
SELECT client_addr, state, write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
-- on the standby
SELECT now() - pg_last_xact_replay_timestamp() AS behind;
MySQL
SHOW REPLICA STATUS\G
-- Seconds_Behind_Source, Replica_SQL_Running_State,
-- Retrieved_Gtid_Set against Executed_Gtid_Set
SHOW VARIABLES LIKE 'replica_parallel_workers';
MongoDB
rs.printSecondaryReplicationInfo()
rs.status().members.map(m => [m.name, m.stateStr, m.optimeDate])

The drill: incident 3. Side by side: a replica falls behind.

Queries waiting on locks, or timing out

What you see. Requests hang, then fail with lock wait timeouts or deadlock errors. CPU may be low: things are waiting, not working.

Likely causes, most common first

  1. One transaction holds a row or table lock and is not finishing: a slow job, or an app that opened a transaction and went off to call another service.
  2. A schema change waiting for a lock, with everything else queued behind it.
  3. Two code paths lock the same rows in different orders: deadlocks.
  4. Hot rows: many sessions updating one counter or one inventory row.

First move. Find the session at the head of the chain, the blocker, not the hundreds waiting behind it. Ending the blocker usually clears the rest.

Run these first

PostgreSQL
SELECT pid, pg_blocking_pids(pid) AS blocked_by, wait_event_type,
       now() - query_start AS waiting, left(query, 60)
FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;
-- then look at the blocker's pid in pg_stat_activity
MySQL
SELECT * FROM sys.innodb_lock_waits\G
SELECT * FROM performance_schema.metadata_locks
WHERE lock_status = 'PENDING';
SHOW ENGINE INNODB STATUS\G   -- LATEST DETECTED DEADLOCK
MongoDB
db.currentOp({ waitingForLock: true })
db.currentOp({ active: true, secs_running: { $gte: 5 } })

The drill: incident 2. The theory: Lost updates and write skew.

One query suddenly got slow

What you see. A query that took milliseconds yesterday takes seconds today. The code did not change.

Likely causes, most common first

  1. The planner picked a different plan: statistics went stale after a big load or delete.
  2. The data crossed a threshold, so a plan that was right for small tables is wrong now.
  3. A parameter value with very different selectivity: one customer with a million rows.
  4. An index was dropped, or became invalid after a failed build.

First move. Get the actual plan with real timings, then compare it with what you expect. Refreshing statistics is cheap and often the fix.

Run these first

PostgreSQL
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
SELECT relname, last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables ORDER BY n_mod_since_analyze DESC LIMIT 10;
ANALYZE orders;   -- changes: refreshes statistics
MySQL
EXPLAIN ANALYZE SELECT ...;
SELECT table_name, index_name, cardinality
FROM information_schema.statistics WHERE table_name = 'orders';
ANALYZE TABLE orders;   -- changes: refreshes statistics
MongoDB
db.orders.find({ ... }).explain("executionStats")
// compare totalDocsExamined with nReturned
db.orders.getPlanCache().clear()   // changes: forgets cached plans

Everything is slow and the disk is busy

What you see. Read latency is up across many queries. Disk reads per second climbed, and CPU waits on I/O.

Likely causes, most common first

  1. The data that is read often no longer fits in memory, so pages are read from disk again and again.
  2. A new report or job scans large tables and pushes hot pages out of the cache.
  3. A backup, vacuum or compaction is competing for the disk.
  4. The cloud volume ran out of burst credits or provisioned IOPS.

First move. Compare cache reads with disk reads now against last week. If the cache share fell, the working set grew or something new is scanning.

Run these first

PostgreSQL
SELECT datname, blks_hit, blks_read,
  round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS hit_pct
FROM pg_stat_database WHERE datname = current_database();
SELECT * FROM pg_stat_io WHERE reads > 0 ORDER BY reads DESC LIMIT 10;
MySQL
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
-- Innodb_buffer_pool_reads (from disk) against _read_requests
SELECT * FROM sys.io_global_by_file_by_latency LIMIT 10;
MongoDB
db.serverStatus().wiredTiger.cache["bytes currently in the cache"]
db.serverStatus().wiredTiger.cache["pages read into cache"]
db.serverStatus().wiredTiger.cache["maximum bytes configured"]

Out of memory, or the server restarted

What you see. The database process was killed by the operating system, or restarted on its own. Clients saw connection errors.

Likely causes, most common first

  1. Too many connections, each with its own memory for sorts and hashes (work_mem in PostgreSQL is per operation, not per connection).
  2. A buffer pool or cache set too close to the machine's total memory.
  3. A large query building a huge hash or sort in memory.
  4. Something else on the same machine using memory: a backup, an agent, another service.

First move. Check the operating system log for the out-of-memory killer first. Then leave headroom: the cache should not take the whole machine.

Run these first

PostgreSQL
SHOW shared_buffers; SHOW work_mem; SHOW max_connections;
SHOW maintenance_work_mem;
-- the OS side: dmesg -T | grep -i -E "killed process|out of memory"
MySQL
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SELECT * FROM sys.memory_global_by_current_bytes LIMIT 10;
-- the OS side: dmesg -T | grep -i -E "killed process|out of memory"
MongoDB
db.serverStatus().mem              // resident and virtual, MB
db.serverStatus().wiredTiger.cache["maximum bytes configured"]
// the OS side: dmesg -T | grep -i -E "killed process|out of memory"

Writes and commits are slow

What you see. Reads are fine, but inserts and updates take longer. Commit latency rose while CPU is low.

Likely causes, most common first

  1. Every commit waits for a disk flush, and the log disk is slow or shared.
  2. Synchronous replication: each commit waits for a standby that is far away or overloaded.
  3. Too many indexes: every insert updates every one of them.
  4. Hot pages or rows that many sessions write at once.

First move. Look at what commits are waiting on. A wait for the log flush points at the disk; a wait for the standby points at replication.

Run these first

PostgreSQL
SELECT wait_event_type, wait_event, count(*)
FROM pg_stat_activity WHERE state = 'active'
GROUP BY 1, 2 ORDER BY 3 DESC;
-- WALSync or WALWrite: the disk. SyncRep: the standby.
SHOW synchronous_commit; SHOW synchronous_standby_names;
MySQL
SHOW VARIABLES WHERE Variable_name IN
  ('innodb_flush_log_at_trx_commit', 'sync_binlog');
SHOW GLOBAL STATUS LIKE 'Rpl_semi_sync_source_%';
SELECT * FROM sys.waits_global_by_latency LIMIT 10;
MongoDB
db.serverStatus().opLatencies.writes
rs.printSecondaryReplicationInfo()   // majority writes wait for this
db.getMongo().getWriteConcern()

What a commit waits for: Synchronous replication and failover.

Tables grow but rows do not

What you see. Table size keeps rising while the row count is flat. Scans get slower over weeks.

Likely causes, most common first

  1. Old row versions are not being removed because a long transaction or a forgotten replication slot holds them.
  2. Cleanup cannot keep up with the update rate on one hot table.
  3. Space freed inside the files is reused, not given back to the operating system, which is normal.

First move. Find the oldest open transaction first. Cleanup cannot remove anything that transaction might still need to see.

Run these first

PostgreSQL
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;
SELECT pid, now() - xact_start AS open_for, state
FROM pg_stat_activity WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC LIMIT 5;
MySQL
SELECT count FROM information_schema.innodb_metrics
WHERE name = 'trx_rseg_history_len';
SELECT trx_id, trx_started, trx_mysql_thread_id
FROM information_schema.innodb_trx ORDER BY trx_started LIMIT 5;
MongoDB
db.orders.stats().wiredTiger["block-manager"]["file bytes available for reuse"]
db.currentOp({ active: true, secs_running: { $gte: 60 } })

After it is fixed

Three things I do once it is quiet

  1. Write down what you saw, what you ran and what fixed it, while it is fresh. The commands that helped become the start of a runbook.
  2. Add the alert that would have caught it earlier: connections at 80% of the limit, lag over a threshold, disk at 75%, the oldest transaction older than an hour.
  3. Fix the cause, not only the symptom: the missing index, the pool size, the slot nobody reads.
