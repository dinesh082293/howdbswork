PostgreSQL

PostgreSQL — in one line

A relational database: rows in tables, one data directory, correctness first.

Good at: money, orders, bookings — anything with joins, constraints, and questions nobody has thought of yet. One log (the WAL) does both crash recovery and replication.

Runs as: one postmaster + a backend process per connection

The architecture of each — processes, memory, disk

Read each column top to bottom: a request enters at the process layer, is served from the memory layer when possible, and is made permanent in the disk layer. When something is slow or broken on-prem, it is slow or broken in exactly one of these three layers — naming the layer is the first diagnostic step.

PostgreSQL — architecture

Request path

Processespostmaster + 1 backend per connection · checkpointer · bgwriter · WAL writer · autovacuum workers
→
Memoryshared_buffers (~25% of RAM) + per-operation work_mem, on top of the OS page cache
→
Disk — one data directorybase/ (table + index files) · pg_wal/ · pg_xact/ · global/pg_control
Who does what: backends execute queries; the checkpointer flushes dirty pages; the WAL writer fsyncs the log; autovacuum removes dead row versions. One process dying is survivable — the postmaster restarts it.

The parameters DBAs actually touch during outages

Not the full configuration reference — the short list that comes up in real incidents. Each row states what the parameter does and the outage rule for it: safe live lever (change it during the incident), planned change (needs a restart or a window — do not improvise it mid-incident), or do not touch (changing it converts the incident into data loss or a longer outage).

PostgreSQL Outage parameters

ParameterWhat it doesDuring an outage
shared_buffersSize of the page cache (start ~25% of RAM).Planned change. Requires a restart — never the mid-incident lever. If the working set outgrew it, that is next week's change, sized from pg_stat_bgwriter evidence.
work_memMemory per sort/hash operation — per operation, not per connection, so total use is work_mem × operations × connections.Safe live lever, per session: SET work_mem='256MB' for the one reporting query that is spilling. A global raise mid-incident is an OOM risk at full concurrency.
max_connectionsHard cap on backend processes; each costs memory and bookkeeping.Do not raise to fix "pool exhausted" — it admits more load into an already overloaded server and needs a restart anyway. The fix is a pooler (PgBouncer) and killing idle-in-transaction sessions.
wal_levelHow much information the WAL carries: minimal / replica / logical.Do not touch. Restart-required, and replicas plus logical subscribers are built on the current level. Changing it mid-incident breaks the copies you may be about to fail over to.
max_wal_sizeWAL volume that triggers a checkpoint (default 1 GB).Safe live lever (reload, no restart) when checkpoints_req shows size-triggered checkpoint storms: raise it and reload.
checkpoint_timeoutTime trigger for checkpoints (default 5 min); whichever of size/time fires first wins.Safe live lever (reload) alongside max_wal_size. Lengthening spreads the flush I/O; the price is longer crash recovery.
autovacuum_*naptime, max workers, and per-table vacuum/analyze scale factors — how aggressively dead tuples and stale stats are cleaned.Safe live lever for bloat: raise workers, lower the scale factor on the one hot table (ALTER TABLE … SET). Never disable autovacuum to "help" — that is how bloat and wraparound start.

Files on disk · what ls actually shows

Situation: there is no hidden state. Every table, index, and log discussed on this page is a file in one directory, owned by one process, inspectable with ls and du while the server runs. When disk fills in production — and the failure is always a specific file class, never "the database" in the abstract — this tree is how you identify which one in under a minute. Paths below are the common Linux defaults; the command under each tree asks the server for its own.

PostgreSQL — the data directory
$ ls /var/lib/postgresql/16/main
PG_VERSION        # "16" — which version owns this dir
base/             # one subfolder per database
global/           # cluster-wide tables + pg_control,
                  # the file startup reads first
pg_wal/           # THE WAL — 16 MB segment files:
  000000010000000000000003
  000000010000000000000004
pg_xact/          # which transactions committed
pg_multixact/  pg_logical/  pg_stat/
postgresql.conf  pg_hba.conf
                  # (on Debian/Ubuntu the .conf files
                  # live in /etc/postgresql/16/main/)

$ ls base/16384/   # database oid 16384
16397             # ← table "users" is THIS file
16397_fsm  16397_vm # free-space + visibility maps
16405             # ← index "users_pkey": also a file
Find any table's file: SELECT pg_relation_filepath('users'); → base/16384/16397. File names are numbers (relfilenodes), not table names — the catalog maps them.
The log files · one by one

Every durability, replication, and recovery guarantee on this page reduces to one of five logs. For each: the exact file name, where it sits, the mechanism, the failure mode when it is undersized, misplaced, or allowed to fill — and the command that shows you its current state. The pattern to hold: a log's size divided by the write rate is a time window, and every operational budget on this page (recovery time, replica downtime tolerance, checkpoint headroom) is one of those windows.

PostgreSQL

Write-Ahead Log (WAL)

pg_wal/000000010000000000000003
Where it sits
The pg_wal/ folder inside the data directory. A chain of segment files, 16 MB each by default, with hex names: timeline + log + segment.
What it does
Every change is written here before the data file is allowed to change — that's the "write-ahead". COMMIT only returns after the WAL record is forced to disk (fsync). The same stream feeds replicas and, when archived, point-in-time recovery.
What breaks without it
No crash safety at all: a power cut could leave half-written pages and silently lost commits. No streaming replication either — replicas have nothing to replay.
Look at it
$ ls $PGDATA/pg_wal $ pg_waldump pg_wal/000000010000000000000003 -- in psql: SELECT pg_current_wal_lsn();

The one invariant: COMMIT means the log record is on disk — pg_wal in PostgreSQL, ib_logfile0 + mysql-bin in MySQL, journal/WiredTigerLog + the oplog in MongoDB. The data files (base/…, *.ibd, collection-*.wt) are where checkpoints place the result afterwards, on their own schedule. Every guarantee on this page — durability, replication, point-in-time recovery — is a consequence of that ordering, and every number on this page is checkable with the commands given beside it.
