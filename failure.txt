## Redis
### 1. The process is killed (kill -9) while one client writes, then restarted
  AOF on, appendfsync everysec:                acknowledged  30550, present after restart  30550, lost      0
  AOF off, snapshots on the default schedule:  acknowledged  32629, present after restart      0, lost  32629
  Redis 7.4.12, one client, one SET per round trip: about 6110 writes a second
  Read it this way: a killed process does not lose what it already handed to the operating system.
  The AOF is written to the file before the reply, and only the fsync waits up to a second, so only
  a machine crash or power loss can lose that last second. With snapshots only, everything since the
  last snapshot is gone: the default schedule had not taken one yet.

### 2. Failover to an asynchronous replica: the primary is killed, the replica is promoted
  plain SET, replication is asynchronous:            acknowledged  27854, on the promoted replica  27854, lost    0, median write 0.175 ms
  SET then WAIT 1 1000 (one replica must confirm):   acknowledged  12467, on the promoted replica  12467, lost    0, median write 0.395 ms
  Read it this way: without WAIT, the writes in flight to the replica when the primary died were
  acknowledged and are gone. WAIT makes the client wait for the replica, which closes that gap for
  this client at the cost of a round trip to the replica on every write. It does not make Redis a
  consensus system: a replica that confirmed can still be the one that is not promoted.
