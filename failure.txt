## Redis
### 1. The process is killed (kill -9) while one client writes, then restarted
  AOF on, appendfsync everysec:                acknowledged  40200, present after restart  40200, lost      0
  AOF off, snapshots on the default schedule:  acknowledged  42269, present after restart      0, lost  42269
  Redis 7.4.12, one client, one SET per round trip: about 8040 writes a second
  Read it this way: a killed process does not lose what it already handed to the operating system.
  The AOF is written to the file before the reply, and only the fsync waits up to a second, so only
  a machine crash or power loss can lose that last second. With snapshots only, everything since the
  last snapshot is gone: the default schedule had not taken one yet.

### 2. Failover to a lagging replica
  The replica is frozen (docker pause) for one second to stand in for a slow network or a busy
  replica. The primary is killed during that second, then the replica is unfrozen and promoted.
  plain SET, replication is asynchronous:              acknowledged  29981, on the promoted replica  27764, lost 2217. Median write 0.132 ms
  SET then WAIT 1 500, count only confirmed writes:    acknowledged   9894,    1 of them reported unconfirmed by WAIT; confirmed and lost: 0. Median write 0.299 ms
  Read it this way: the primary acknowledges a write before any replica has it. Writes acknowledged
  while the replica was behind are gone after the promotion. WAIT does not stop that, but it tells the
  client which writes no replica confirmed, so the application can retry them or report them. It does
  not make Redis a consensus system.
