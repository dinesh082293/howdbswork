What changed, for operators

What in the latest releases changes how I run the database?

Release notes list hundreds of items. These are the ones that change defaults, break an upgrade or change what you should monitor, for the current major releases. Each list links to the official notes; read those before you upgrade.

Show
PostgreSQL

PostgreSQL 18 (September 2025)

Released September 25, 2025. The items that matter most when you run it:

Changes that can break an upgrade

  • Data checksums are on by default for new clusters. pg_upgrade needs matching settings, so to upgrade an old cluster without checksums, create the new one with initdb --no-data-checksums (or enable checksums on the old one first).
  • MD5 passwords are deprecated: setting one now warns, and support will be removed in a future release. Move users to SCRAM-SHA-256.
  • VACUUM and ANALYZE now process inheritance children of a parent table; use ONLY for the old behaviour.
  • Full text search now uses the cluster's default collation provider; reindex full text and pg_trgm indexes after upgrading clusters with a non-libc provider.

Faster, with nothing to change

  • Asynchronous I/O (io_method) for sequential scans, bitmap heap scans and vacuum. New view pg_aios.
  • pg_upgrade keeps planner statistics (not extended statistics), so the slow first hour after an upgrade mostly goes away.
  • Skip scan lets a multicolumn B-tree index be used when the first column has no condition.

New things worth using

  • uuidv7() for time-ordered UUID keys.
  • Virtual generated columns, now the default kind of generated column.
  • NOT NULL ... NOT VALID, so adding NOT NULL to a big table no longer needs one long locking check.
  • RETURNING old.*, new.* in INSERT, UPDATE, DELETE and MERGE.
  • Temporal constraints: WITHOUT OVERLAPS on primary and unique keys.
  • OAuth authentication.
  • EXPLAIN ANALYZE includes BUFFERS by default.

Vacuum and monitoring

  • Normal vacuums can freeze some all-visible pages early (vacuum_max_eager_freeze_failure_rate), spreading out the big anti-wraparound vacuums.
  • autovacuum_worker_slots lets you raise autovacuum_max_workers without a restart.

Source: PostgreSQL 18 release notes.

MySQL

MySQL 8.4 LTS (April 2024)

The long-term support release: about five years of premier support and three of extended support. MySQL 8.0 reached end of life in April 2026, so 8.4 is where most fleets are going. 9.x releases are short-lived innovation releases.

Changes that can break an upgrade

  • mysql_native_password is disabled by default. Old client libraries and users created with it cannot log in until you move them to caching_sha2_password or load the plugin explicitly.
  • Replication statements use SOURCE and REPLICA: CHANGE REPLICATION SOURCE TO, SHOW REPLICA STATUS. The old MASTER and SLAVE forms are gone, so scripts and tools must be updated.
  • mysqlpump is removed; use MySQL Shell's dump utilities. FLUSH HOSTS is removed.
  • Foreign keys must reference a unique key in the parent (controlled by restrict_fk_on_non_standard_key).
  • AUTO_INCREMENT on FLOAT or DOUBLE columns is an error.

InnoDB defaults that changed

  • innodb_adaptive_hash_index: ON to OFF.
  • innodb_change_buffering: all to none.
  • innodb_io_capacity: 200 to 10000.
  • innodb_flush_method: fsync to O_DIRECT where supported.
  • innodb_log_buffer_size: 16 MB to 64 MB. Read, purge and page cleaner thread counts now scale with the CPU count.
  • If you set these explicitly, your values still apply; if you relied on the old defaults, test the new ones.

New things worth using

  • Automatic histogram updates: ANALYZE TABLE ... UPDATE HISTOGRAM ... AUTO UPDATE.
  • GTID tags, to label groups of transactions such as a migration's.

Source: What is new in MySQL 8.4; the InnoDB default changes, by Frédéric Descamps.

MongoDB

MongoDB 8.0 (October 2024)

The current major release, which also contains the 7.1 to 7.3 rapid releases. Upgrade one major version at a time, with featureCompatibilityVersion set to 7.0 first.

Changes that affect how you run it

  • Transparent Huge Pages: the advice flipped. 8.0 uses a new TCMalloc with per-CPU caches, and on x86_64 and ARM64 the production notes now say to enable THP (always, with defrag set to defer+madvise). Earlier versions said to disable it, so check your host tuning.
  • TCMalloc returns memory to the OS in the background by default; new tcmalloc metrics appear in serverStatus.
  • Majority writes are acknowledged once a majority has written the oplog entry, so a read from a secondary right after may miss it unless you use causal consistency.
  • Check the release notes for kernel compatibility before upgrading hosts, and stay on the latest 8.0 patch: several early patches had critical advisories.

New things worth using

  • defaultMaxTimeMS: a cluster-wide default time limit for reads, so a runaway query cannot run forever.
  • Query settings (setQuerySettings) replace index filters, which are deprecated, to pin or reject query shapes without code changes.
  • moveCollection and unshardCollection for unsharded collections, much faster resharding, and config shards (a config server that also holds data).
  • bulkWrite across several collections in one command.
  • Queryable Encryption supports range queries.

Source: MongoDB 8.0 release notes; TCMalloc performance and THP.

Before any upgrade

The same checklist every time

  • Read the incompatibilities section of the official notes, not only the highlights.
  • Rehearse on a restored copy with real data, and compare the plans of your top queries. See Major version upgrades.
  • Check client drivers and tools: authentication changes and renamed commands break them first.
  • Keep a way back until the new version has run a full business cycle.
