MySQL · InnoDB

MySQL · InnoDB — in one line

A relational database where each table file is its primary-key index.

Good at: high-volume websites — lookups by ID, simple queries at huge scale, operationally simple read replicas. Two logs: redo for crashes, binlog for replicas.

Runs as: one mysqld process, a thread per connection

The architecture of each — processes, memory, disk

Read each column top to bottom: a request enters at the process layer, is served from the memory layer when possible, and is made permanent in the disk layer. When something is slow or broken on-prem, it is slow or broken in exactly one of these three layers — naming the layer is the first diagnostic step.

MySQL · InnoDB — architecture

Request path

Processesone mysqld · a thread per connection · page cleaner threads · purge thread · log writer threads
→
MemoryInnoDB buffer pool (most of the RAM budget) + redo log buffer + change buffer inside it
→
Disk — the datadir*.ibd per table · ib_logfile0/1 or #innodb_redo/ · mysql-bin.* · undo_001/002 · ibdata1
Who does what: connection threads execute; page cleaners flush dirty pages to the .ibd files; the purge thread deletes undo records no reader still needs. Threads share one process — a crash takes all of them, and redo rebuilds the state.

The parameters DBAs actually touch during outages

Not the full configuration reference — the short list that comes up in real incidents. Each row states what the parameter does and the outage rule for it: safe live lever (change it during the incident), planned change (needs a restart or a window — do not improvise it mid-incident), or do not touch (changing it converts the incident into data loss or a longer outage).

MySQL · InnoDB Outage parameters

ParameterWhat it doesDuring an outage
innodb_buffer_pool_sizeSize of the page cache — the single most important MySQL setting (typically 70–80% of RAM on a dedicated server).Planned change. Resizable online in 8.0 (SET GLOBAL), but resizing under load is slow and competes with the workload; verify headroom first, and watch Innodb_buffer_pool_resize_status.
innodb_redo_log_capacityTotal redo log size (8.0.30+); bounds checkpoint age headroom.Safe live lever (dynamic) when checkpoint age is pinned near capacity and writes are stalling: raise it, then confirm age falls.
max_connectionsCap on concurrent connections; each thread costs memory.Short bridge only. Dynamic, so a modest raise can stop "too many connections" errors while you fix the cause — but the cause is almost always missing pooling (ProxySQL) or leaked connections, and a big raise converts a connection incident into a memory incident.
innodb_flush_log_at_trx_commitThe durability dial: 1 = redo fsynced at every commit (safe); 2 = written to OS, fsynced ~1/s; 0 = ~1/s entirely.Do not relax mid-outage to buy speed unless the business explicitly accepts losing up to ~1 s of commits per crash. You would be trading tonight's latency incident for a future data-loss incident.

Files on disk · what ls actually shows

Situation: there is no hidden state. Every table, index, and log discussed on this page is a file in one directory, owned by one process, inspectable with ls and du while the server runs. When disk fills in production — and the failure is always a specific file class, never "the database" in the abstract — this tree is how you identify which one in under a minute. Paths below are the common Linux defaults; the command under each tree asks the server for its own.

The log files · one by one

Every durability, replication, and recovery guarantee on this page reduces to one of five logs. For each: the exact file name, where it sits, the mechanism, the failure mode when it is undersized, misplaced, or allowed to fill — and the command that shows you its current state. The pattern to hold: a log's size divided by the write rate is a time window, and every operational budget on this page (recovery time, replica downtime tolerance, checkpoint headroom) is one of those windows.

MySQL · InnoDB

Redo log

ib_logfile0 · ib_logfile1
Where it sits
In the datadir, written as a circular pair of files. MySQL 8.0.30+ moved them into a #innodb_redo/ folder as #ib_redo* files — same log, new home. Total size is set by innodb_redo_log_capacity.
What it does
InnoDB's write-ahead log: a physical record of every page change, written before the page itself. On startup after a crash, InnoDB replays it to rebuild every page that was dirty in the buffer pool.
What breaks without it
InnoDB refuses to start without a valid redo log — and with good reason: without it, a committed transaction could vanish in a crash and dirty pages would be unrecoverable.
Look at it
$ ls -lh /var/lib/mysql/ib_logfile* -- in mysql: SHOW ENGINE INNODB STATUS\G -- read the "LOG" section: Log sequence number
MySQL

Binary log (binlog)

mysql-bin.000001 · mysql-bin.index
Where it sits
In the datadir (path set by log_bin). Numbered files that roll over as they fill; mysql-bin.index lists the ones that exist. Each event can carry a GTID — a permanent, unique ID for the transaction.
What it does
A logical record of every committed change ("insert this row", not "change these bytes"). Replicas replay it to stay identical. It is also the second half of point-in-time recovery: restore a backup, then replay the binlog up to the second before the mistake.
What breaks without it
No replication, and no point-in-time recovery — you can only restore whole backups, losing everything since the last one.
Look at it
-- in mysql: SHOW BINARY LOGS; SHOW BINLOG EVENTS IN 'mysql-bin.000001'; $ mysqlbinlog mysql-bin.000001 | less
