MySQL · InnoDB

Why is a MySQL table also its primary key, and what are the two logs for?

This page is about one file per table. I show you how InnoDB stores a table as its own primary-key index, and how two logs split the jobs: redo for crashes, binlog for replicas. After it you will be able to find any table's .ibd file, read checkpoint age, check binlog retention, and tell whether undo is piling up.

MySQL · InnoDB: in one line

A relational database. Each table file is its primary-key index.

Good at: High-volume websites. Lookups by ID. Simple queries at huge scale. Operationally simple read replicas. Two logs: redo for crashes, binlog for replicas.

Runs as: one mysqld process, a thread per connection
Common myth

The binlog is how MySQL recovers from a crash.

Crash recovery uses the InnoDB redo log. The binlog is the logical record that replicas replay and that point-in-time recovery uses. On commit the two are kept in agreement with a two-phase commit, which is why they look like one thing from outside.

The architecture: processes, memory, disk

Process, memory, disk: a request enters at the process layer, memory serves it when it can, and disk makes it permanent. Name the layer first, then diagnose inside it. The full rule is on the PostgreSQL page: name the layer first, then diagnose inside it.

MySQL · InnoDB: architecture

Request path

Processesone mysqld · a thread per connection · page cleaner threads · purge thread · log writer threads
→
MemoryInnoDB buffer pool (most of the RAM budget) + redo log buffer + change buffer inside it
→
Disk: the datadir*.ibd per table · #innodb_redo/#ib_redo0-31 · mysql-bin.* · undo_001/002 · ibdata1
Who does what: Connection threads run queries. Page cleaners flush dirty pages to the .ibd files. The purge thread deletes undo records no reader still needs. Threads share one process. A crash takes all of them. Redo rebuilds the state.

The parameters DBAs actually touch during outages

Same three outage rules as PostgreSQL: Safe live lever, Planned change, Do not touch. What each one means is written once on the PostgreSQL page.

MySQL · InnoDB Outage parameters

ParameterWhat it doesDuring an outage
innodb_buffer_pool_sizeSize of the page cache. The single most important MySQL setting. Typically 70 to 80% of RAM on a dedicated server.Planned change. It is resizable online in 8.0 (SET GLOBAL), but resizing under load is slow and competes with the workload. Verify headroom first. Watch Innodb_buffer_pool_resize_status.

You would be trading tonight's latency incident for a future data-loss incident.

The log files · one by one

Same pattern as PostgreSQL: five logs, one job each, and every operational budget is a time window. The full version is on the PostgreSQL page.

MySQL · InnoDB

Redo log

#ib_redo0 · #ib_redo31
Where it sits
In #innodb_redo/ in the datadir: 32 files, #ib_redo0 to #ib_redo31, each 1/32 of innodb_redo_log_capacity, written as a ring. Before 8.0.30 they were a pair of files, ib_logfile0/1, in the datadir root. Same log, new home.
What it does
InnoDB's write-ahead log. A physical record of every page change, written before the page itself. On startup after a crash, InnoDB replays it to rebuild every page that was dirty in the buffer pool.
What breaks without it
InnoDB refuses to start without a valid redo log. With good reason. Without it, a committed transaction could vanish in a crash and dirty pages would be unrecoverable.
Look at it
$ ls -lh /var/lib/mysql/#innodb_redo/ -- in mysql: SHOW ENGINE INNODB STATUS\G -- read the "LOG" section: Log sequence number
MySQL

Binary log (binlog)

mysql-bin.000001 · mysql-bin.index
Where it sits
In the datadir (path set by log_bin). Numbered files that roll over as they fill. mysql-bin.index lists the ones that exist. Each event can carry a GTID. That is a permanent, unique ID for the transaction.
What it does
A logical record of every committed change. "Insert this row", not "change these bytes". Replicas replay it to stay identical. It is also the second half of point-in-time recovery. Restore a backup, then replay the binlog up to the second before the mistake.
How old files go away
By time, not by replica. binlog_expire_logs_seconds sets the age, 2592000 seconds (30 days) by default, with auto-purge on by default. Expired files go at startup and when the binlog is flushed. A connected replica that has not yet read a file keeps that one file. A disconnected replica holds nothing back.
What breaks without it
No replication, and no point-in-time recovery. You can only restore whole backups, losing everything since the last one.
Look at it
-- in mysql: SHOW BINARY LOGS; SHOW BINLOG EVENTS IN 'mysql-bin.000001'; $ mysqlbinlog mysql-bin.000001 | less

The optimizer's selectivity decision

Problem. I add an index. The query ignores it. I run EXPLAIN first. It says full scan. That feels wrong. It is often right.

Mechanism. An index lookup reads pages one at a time, in key order. Those pages sit scattered across the .ibd file. Each one is a random read. A full scan reads the same file front to back, in one pass. One sequential pass can beat thousands of random reads. The planner compares those two costs. It picks the cheaper one. It skips the index when the query must return a large share of the table.

The planner estimates row counts from statistics. A bulk load can leave those statistics stale. The planner then guesses wrong. ANALYZE TABLE refreshes the statistics. Run it after a bulk load. Then read EXPLAIN again.

A secondary index does not hold the row. It holds the primary key value. Each match needs a second read into the clustered index. That read fetches the row from users.ibd. This is the bookmark lookup. One match costs two reads. A thousand matches cost two thousand reads.

Secondary index lookup: two reads per match

Every secondary entry carries a copy of the primary key. A long string key makes every secondary entry longer. Longer entries mean more pages per index. Keep the primary key short. Use an integer id when you can.

Exact check. Run EXPLAIN. Then refresh statistics. Then check what the index holds.

EXPLAIN SELECT id, email FROM users WHERE status = 'active'; ANALYZE TABLE users; SELECT INDEX_NAME, COLUMN_NAME, CARDINALITY FROM information_schema.statistics WHERE TABLE_SCHEMA = 'shop' AND TABLE_NAME = 'users';

One incident I keep coming back to

Writes started failing. Then the database refused writes entirely.

I broke the disk down by owner before touching anything. The binlog was the filler, and the first assumption is usually wrong: a dead replica does not hold binlogs back, because MySQL purges by time (see How old files go away above). So I check three numbers before naming a cause: the retention value, the write rate, and the oldest file in SHOW BINARY LOGS. Retention times write rate larger than the disk, retention set to 0, auto-purge off, and a burst that outran purge all look the same from the application.

The fix is the purge, not the replica. Check every replica position with SHOW REPLICA STATUS, then free space with PURGE BINARY LOGS. Never rm old binlog files by hand. Set binlog_expire_logs_seconds to a value your write rate and disk can actually hold, and alert at 70 percent, not 98 percent. A replica that still needs a file you purged fails with error 1236 and must be rebuilt from a backup, which is why positions come first.

Real versions of this story: GitHub automated the failover with Orchestrator, then upgraded 1,200 hosts the same way, and Slack and Shopify both moved to Vitess. All four are on the Stories page. How to host MySQL on-prem, on EC2, in Kubernetes, or managed is on the Cloud page.

Your turn

You add an index on email to a large InnoDB table whose primary key is a UUID stored as CHAR(36). The new index is much bigger than the emails alone. Why, and what would you have done differently?

Write your answer down first. Then open mine.

Show my answer

Why: in InnoDB, every secondary index entry stores the primary key as its pointer to the row. Each email entry carries the 36-character UUID with it. A lookup by email finds the primary key in the secondary index, then walks the clustered index to get the row.

The other cost: random UUIDs land all over the clustered index, so inserts split pages and the buffer pool holds more pages than it needs to.

What I would do: store the UUID as BINARY(16) with UUID_TO_BIN(uuid, 1), which also reorders a version 1 UUID by time. Or use a BIGINT auto-increment primary key and keep the UUID as a unique secondary column for the outside world. Every secondary index gets smaller either way.

Check yourself · 4 questions

Check yourself

Pick an answer. You will see whether it is right, and why.

1. How are rows ordered inside an InnoDB table file?

The table is a clustered index on the primary key: the rows live in the leaves of that B+ tree.

2. Which log does crash recovery replay?

Redo rebuilds the data pages. The binlog is for replicas and point-in-time recovery.

3. One snapshot stays open while other sessions update rows. Which number grows?

Purge cannot remove undo records the old snapshot might need. In Notebook 1 it went from 11 to 20,006.

4. Why do random UUID primary keys slow inserts down?

Each insert dirties a different page, and every secondary index stores the 16-byte key too. Time-ordered keys go to the end.
