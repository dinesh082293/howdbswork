Same task, three engines

What does each engine do when the same thing happens to it?

I keep coming back to four events when I compare engines, because each one exposes how an engine is built. Four everyday events: a write, a crash, a lagging replica, and a long transaction. For each, the three engines side by side, with the file names, the order of events, and a command to see it yourself.

Scenario 1 of 4

I commit one row. What touches disk, and when?

The same INSERT in all three engines. Each one writes the log first and the data file later. They differ in how many logs there are and in what "acknowledged" means.

PostgreSQL

  1. The row version is written into an 8 KB page in shared_buffers. The page is now dirty.
  2. A WAL record describing the change goes into the WAL buffers.
  3. COMMIT flushes the WAL to pg_wal/ and calls fsync. Only then does the client get its answer.
  4. The dirty page reaches base/ later, written by the checkpointer or the background writer.
See it
SHOW synchronous_commit;
SELECT pg_current_wal_lsn();
-- run an INSERT, then the line above again.
-- The position moved.

The priceAn UPDATE writes a whole new row version. The old one stays in the page until VACUUM removes it.

MySQL · InnoDB

  1. The row changes in a 16 KB page in the buffer pool. The old version goes to the undo log.
  2. A redo record goes into the log buffer.
  3. COMMIT flushes redo to #innodb_redo/ and writes the binlog. The two are committed together, with a two-phase commit, so they agree after a crash.
  4. The dirty page reaches users.ibd later, through the doublewrite files, written by the page cleaner threads.
See it
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW VARIABLES LIKE 'sync_binlog';
-- both 1 is the fully durable setting

The priceTwo logs mean two syncs per commit. Group commit shares them across concurrent transactions, which is why the cost is smaller than it sounds.

MongoDB · WiredTiger

  1. The document change is applied in the WiredTiger cache. On a replica set, the oplog entry is written in the same transaction.
  2. A journal record is written to journal/WiredTigerLog.*, flushed about every 100 ms, or at once for j: true.
  3. The acknowledgment depends on the write concern. w: 1 returns after the primary applied the write. w: "majority" waits until most members have it in their journal.
  4. A checkpoint, about every 60 seconds, writes the cache to collection-*.wt.
See it
rs.conf().writeConcernMajorityJournalDefault
db.getSiblingDB('local').oplog.rs.find().sort({$natural: -1}).limit(1)

The priceA write acknowledged at w: 1 but not yet replicated can be rolled back if the primary fails.

All three write the log first. The real difference is what the client was told, and when. Check the write concern or the commit setting before you trust an acknowledgment.

Measured: Notebook 2 times the durable setting against the fast one. Go deeper: follow one insert, end to end, or what a commit waits for.

Scenario 2 of 4

The server is killed in the middle of traffic. What does the restart do?

A power cut or a kill -9. Memory is gone. What survives is the log and whatever the last checkpoint wrote. The restart is the log being replayed.

PostgreSQL

  1. global/pg_control names the last checkpoint and where the redo should start.
  2. The startup process replays WAL forward from that point and puts the missing changes into the data pages.
  3. Transactions that never committed need no undo. Their row versions stay invisible, and VACUUM removes them later.
  4. The server accepts connections when the replay finishes.
See it
-- in the server log after a crash:
-- database system was not properly shut down; automatic recovery in progress
-- redo starts at ...
-- redo done at ...

The priceRecovery time follows how much WAL sits after the last checkpoint. That is set by checkpoint_timeout and max_wal_size.

MySQL · InnoDB

  1. Torn pages, half-written by the crash, are repaired from the doublewrite files first.
  2. InnoDB finds the last checkpoint in the redo log and applies every redo record after it.
  3. Transactions that were open at the crash are rolled back using the undo log. After startup, this continues in the background.
  4. Transactions caught between prepare and commit are settled against the binlog.
See it
-- in the error log after a crash:
-- InnoDB: Starting crash recovery.
-- InnoDB: Applying a batch of ... redo log records

The priceRolling back one huge in-flight transaction can take a long time. A crash does not hide that cost. It moves it to startup.

MongoDB · WiredTiger

  1. WiredTiger restores the last checkpoint, a consistent copy of the data about 60 seconds old.
  2. It replays the journal records written after that checkpoint.
  3. On a replica set, the member then catches up from the oplog. If another member became primary meanwhile, writes it had but the majority did not are rolled back.
  4. While it catches up, the member reports RECOVERING. When it is done, it reports SECONDARY.
See it
rs.status().members.map(m => m.name + ' ' + m.stateStr)

The priceA write that only the old primary had acknowledged at w: 1 is the one that gets rolled back.

Recovery is the same idea three times: start from the last known good point, replay the log, and discard what never committed. What differs is where the unfinished work goes, and how much log you have to replay.

Scenario 3 of 4

A replica falls behind. Why, and how do I see it?

Lag is a queue. Changes arrive faster than the replica applies them. Each engine has a different place where that queue builds up.

PostgreSQL

  1. The standby receives WAL over the network and replays it with one recovery process.
  2. A burst of writes can arrive faster than one process replays it.
  3. A long query on the standby can conflict with replay. Replay waits, up to max_standby_streaming_delay (30 s by default), then cancels the query.
  4. With synchronous replication, lag stops being a delay and becomes commit latency.
See it
-- on the primary
SELECT client_addr, state, write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
-- on the standby
SELECT now() - pg_last_xact_replay_timestamp();

The priceThe standby holds WAL the primary cannot recycle if a replication slot is tied to it, so a stuck replica can fill the primary disk.

MySQL · InnoDB

  1. The replica copies the binlog into its relay log with the I/O thread.
  2. The applier threads replay it. This is usually where the queue builds up.
  3. One large transaction replays as one unit, so a big batch delete on the source becomes a long stall on the replica.
  4. Parallel replay (replica_parallel_workers) helps when the source workload is spread across many transactions.
See it
SHOW REPLICA STATUS\G
-- read Seconds_Behind_Source, Replica_IO_Running,
-- Replica_SQL_Running. Treat the seconds as a hint.

The priceThe binlog on the source must be kept long enough for a slow replica to catch up, or the replica needs a rebuild.

MongoDB · WiredTiger

  1. The secondary tails the primary oplog and applies the entries in batches.
  2. If writes outpace it, the secondary falls further behind the primary.
  3. The oplog is a capped collection. If the secondary falls behind by more than the oplog window, the entries it needs are gone, and it needs a full resync.
  4. Flow control, on by default, slows the primary down when the majority commit point lags too far.
See it
rs.printSecondaryReplicationInfo()
rs.printReplicationInfo()  // the oplog window

The priceSize the oplog for the longest outage you want a secondary to survive, not for the average day.

Lag is write rate minus apply rate, accumulated over time. Whatever the engine, the question is the same: what is the apply rate, and what is the limit on how far behind the log is kept?

Scenario 4 of 4

One transaction stays open for an hour. What does it cost?

Nothing is wrong with the transaction itself. The cost is everything the database must keep so that its snapshot still makes sense.

PostgreSQL

  1. The transaction holds a snapshot. Every row version that died after the snapshot was taken must be kept.
  2. VACUUM runs, but it cannot remove those versions, in any table in the database.
  3. Tables and indexes grow (bloat), and queries read more pages for the same rows.
  4. If the session is "idle in transaction", it also holds its locks the whole time.
See it
SELECT pid, state, now() - xact_start AS age
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY age DESC LIMIT 5;

The priceSet idle_in_transaction_session_timeout so a forgotten session cannot hold the cleanup back for hours.

MySQL · InnoDB

  1. The old read view needs old row versions, so the purge thread cannot delete the undo records for them.
  2. The history list grows, and the undo tablespaces grow with it.
  3. Reads of recently changed rows walk longer chains of old versions, so they slow down.
  4. Locks held by the transaction block other writers until it ends.
See it
SELECT trx_id, trx_started, trx_rows_modified
FROM information_schema.innodb_trx
ORDER BY trx_started LIMIT 5;
SHOW ENGINE INNODB STATUS\G  -- History list length

The priceUndo tablespaces are truncated only once they pass innodb_max_undo_log_size and purge has caught up, so the extra space can linger after the transaction ends.

MongoDB · WiredTiger

  1. A multi-document transaction is limited by transactionLifetimeLimitSeconds, 60 seconds by default. After that it is aborted.
  2. A long read cursor or snapshot keeps older versions of documents in the WiredTiger cache.
  3. The cache fills with history, and eviction starts to compete with the workload.
  4. Writers can see more retries from write conflicts if the transaction held documents.
See it
db.currentOp({ active: true, secs_running: { $gt: 60 } })

The priceMongoDB limits the problem with a hard timeout. The other two let it grow until you notice.

A long transaction is a debt: the database has to remember the past for as long as the transaction is open. PostgreSQL shows it as bloat, MySQL as undo, and MongoDB as cache pressure.

The one invariant: COMMIT means the log record is on disk. pg_wal in PostgreSQL, #innodb_redo/#ib_redo0 + mysql-bin in MySQL, journal/WiredTigerLog + the oplog in MongoDB. The data files (base/…, *.ibd, collection-*.wt) are where checkpoints place the result afterwards, on their own schedule. Every guarantee on this page, durability, replication, point-in-time recovery, is a consequence of that ordering, and every number on this page is checkable with the commands given beside it.
