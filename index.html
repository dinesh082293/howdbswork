Real databases, explained with real files.

The number that runs this pageOne lookup in a 10-million-row table takes 0.4 ms with the right index — or 8 seconds without one. Same data, same hardware, same query. The difference is entirely physical: which pages get read, and how many.
3 page readsAn index lookup at 10M rows: root → internal → leaf. At 1 billion rows it is 4. Tree depth grows logarithmically; scan cost grows linearly. That asymmetry is the whole subject of this page.
1,250,000 pagesThe same lookup with no index: a sequential scan of a 10 GB table file at 8 KB per page. At 3 GB/s of NVMe throughput that is 3.3 seconds of pure I/O before a single row is evaluated.
1 fsyncWhat a commit actually costs: one sequential write of the log record, forced to disk. Not the data page — the log. pg_wal, ib_logfile0, WiredTigerLog.*. Everything else is deferred.

This page teaches PostgreSQL, MySQL, and MongoDB the way they exist on a production server: a process, a bounded block of memory, and a directory of files. Every topic follows the same structure — Situation (how the mechanism is physically organized) → The Problem (the failure modes, with the data volume at which each one becomes an incident) → Mechanism (derived from the physical layout, never stated as convention) → In Practice (exact commands, real output, red flags named) → Where It Breaks (root cause, blast radius, mitigation). No claim on this page is qualitative where a number exists.

1

Durability is an ordering rule, not a feature

The log record reaches disk before the data page is required to. That single ordering constraint is why a commit survives a power cut that destroys everything in memory: recovery is replay, and replay needs only the log.

PG: pg_wal/ · MySQL: ib_logfile0 (redo) · MongoDB: journal/WiredTigerLog.*
2

Lookup cost is page count, nothing else

Rows live in fixed-size pages: 8 KB in PostgreSQL, 16 KB in InnoDB. An index is a sorted structure that reduces a lookup from N pages to ~logfanout(N) pages — at fanout ~400, one extra tree level per ~400× of data.

PG: base/16384/16397 · MySQL: shop/users.ibd · MongoDB: collection-*.wt
3

MVCC trades disk for non-blocking reads

Old row versions are retained until no open snapshot can reference them, so readers never wait for writers. The cost is deferred, not eliminated: every retained version is cleanup debt, collected by VACUUM, purge, or WiredTiger reconciliation — and one long transaction can block all three.

PG: old tuples + VACUUM · MySQL: undo_001/undo_002 · MongoDB: timestamped versions in cache

The three engines on this page solve the same three problems with three different physical layouts. The layout is the behavior: once you know where the bytes sit, the performance characteristics follow.

PostgreSQL

Best when correctness matters most.

One data directory. Each table and each index is its own file of 8 KB pages. Updates write a brand-new row version; VACUUM cleans the old ones.

Log: WAL in pg_wal/ · Data: base/<db>/<file> · Memory: shared_buffers

MySQL · InnoDB

Best for fast websites where most lookups are by ID.

Each table is one .ibd file that is the primary-key index — rows stored in ID order, 16 KB pages. Two logs: redo for crashes, binlog for copies.

Logs: ib_logfile0/1 + mysql-bin.* · Data: shop/users.ibd · Memory: buffer pool

MongoDB · WiredTiger

Best when every record looks a bit different.

Documents instead of rows. Each collection and index is its own compressed .wt file. Copies follow the oplog, a special collection in the local database.

Logs: journal/WiredTigerLog.* + local.oplog.rs · Data: collection-*.wt · Memory: WiredTiger cache

Six terms. Every one of them is a file, a size, or a number.

PageThe fixed-size chunk a database reads and writes. Never one row at a time — always a whole page.PostgreSQL: 8 KB · InnoDB: 16 KB · WiredTiger: variable blocks, compressed

What each database actually is — before any internals

Three programs, one job: keep data in files on disk, serve it from memory, and prove that a commit survived. They differ in exactly three physical choices — how the data file is organized, how many logs there are, and where old row versions live — and every behavior difference in the rest of this page follows from those three choices. Start with the one plain line per engine; the architecture, the log files, the people, and the outage parameters follow.

PostgreSQL — in one line

A relational database: rows in tables, one data directory, correctness first.

Good at: money, orders, bookings — anything with joins, constraints, and questions nobody has thought of yet. One log (the WAL) does both crash recovery and replication.

Runs as: one postmaster + a backend process per connection

MySQL · InnoDB — in one line

A relational database where each table file is its primary-key index.

Good at: high-volume websites — lookups by ID, simple queries at huge scale, operationally simple read replicas. Two logs: redo for crashes, binlog for replicas.

Runs as: one mysqld process, a thread per connection

MongoDB · WiredTiger — in one line

A document database: JSON-like documents in collections, built to run as a replica set.

Good at: records that genuinely differ per item (catalogues, profiles), and spreading across machines with built-in sharding. Two logs: journal for crashes, oplog for the replica set.

Runs as: mongod processes in a replica set; mongos routers when sharded

The architecture of each — processes, memory, disk

Read each column top to bottom: a request enters at the process layer, is served from the memory layer when possible, and is made permanent in the disk layer. When something is slow or broken on-prem, it is slow or broken in exactly one of these three layers — naming the layer is the first diagnostic step.

Who manages what, on-prem

On-prem, three teams touch the same server. Most 2 AM arguments are boundary disputes, so the boundaries are stated plainly: the DBA owns everything the database process does; the sysadmin owns the machine it runs on; storage owns the bytes underneath both.

Database administrator (DBA)

  • Installs and configures the engine; owns every parameter in the tables below
  • Schema, indexes, and query performance; reviews plans for new queries
  • Backups, point-in-time recovery, and restore tests
  • Replication topology, lag, failover decisions
  • Users, roles, and access inside the database
  • Cleanup health: autovacuum / purge / checkpoint tuning

Sysadmin / OS team

  • The machine or VM: CPU, RAM, OS patching, kernel limits (open files, huge pages)
  • Filesystems mounted with the right options; the data directory exists and is owned by the DB user
  • Process supervision (systemd), NTP/time sync, DNS
  • Network between app, primary, and replicas; firewall rules
  • Host-level monitoring: CPU steal, memory pressure, I/O wait

Storage team

  • The volumes themselves: RAID / SAN / cloud disks, IOPS and throughput provisioning
  • Separate volumes where it matters: log files (WAL / redo / journal) vs data files
  • Snapshots at the storage layer, and their retention
  • Disk expansion when the DBA's growth forecast says so
  • Latency evidence when the DBA says "the disk is slow": device-level stats to prove or disprove it

The seams, where incidents actually live: a full disk is a storage problem until the cause is WAL the DBA's archiving failed to move; a "slow database" is a DBA problem until device latency shows the volume is saturated. The runbook below assigns each check to its owner implicitly — run the check in your layer first, with numbers, before escalating across the seam.

The standard outage runbook — same steps, every engine

Engines differ; the order of operations does not. These eight steps are the checklist section's triage, expanded into the full incident arc — the step most often skipped is step 7, which is why emergency parameter values are still in production years later.

1

Declare and timestamp. Name an incident lead, note the start time, and check what changed in the last hour — deploy, config push, batch job, marketing send. A majority of outages correlate with a change; find it before touching the database.

2

Ask what is running right now. pg_stat_activity / SHOW FULL PROCESSLIST / db.currentOp({active:true}). One query eliminates half of all incident classes before any dashboard is opened.

3

Find the blocker and the oldest transaction. Lock chains have a head; cleanup horizons have an owner. Kill the runaway report or the idle-in-transaction session — after confirming it is not a payment mid-flight.

4

Take the three vitals. Connections by state, replication lag, and disk broken down by owner (data files vs log files). Three numbers, three incident classes ruled in or out, under a minute.

5

Apply the smallest lever that matches the evidence. Kill the blocker, fail over, shed reads to replicas, or raise the one reloadable parameter the evidence names (max_wal_size, redo capacity, oplog size). Restarting is the last resort, not the first — a restart replays the log and often returns the same load to a colder cache.

6

Verify recovery with numbers, not relief. Lag draining toward zero, error rate falling, checkpoint age / history list length / dirty bytes moving the right direction. State the values out loud in the incident channel.

7

Record every change you made. Old value, new value, why, and a scheduled time to revisit. Emergency settings left in place become next quarter's mystery configuration — the flush=2 that ships is always one that was "temporary".

8

Postmortem within days. Root cause, blast radius, and the one alert that would have caught it at minute one — then actually add that alert. An incident without a new alert is scheduled to repeat.

Best Practices in MySQL · InnoDB

8 rules for lookups by ID at huge scale — the table file is the index, and there are two logs, not one

1Two logs, two different jobs

Redo rebuilds pages after a crash. The binlog feeds replicas and point-in-time recovery. Losing either one breaks a different promise.

Deep dive ↓ Level 0 · Redo + binlog two-phase commit

One commit, written twice — on purpose

COMMIT→ib_logfile0 · redo · physical page changesmysql-bin.000042 · logical row changes

Crash recovery replays redo. A replica replays the binlog. Two-phase commit is what keeps the two in agreement.

2The table file IS the primary-key index

Rows live inside users.ibd in primary-key order. A lookup by ID is a walk down the file's own B+ tree — there is no separate heap.

Deep dive ↓ Level 2 · Change buffer & clustered index

shop/users.ibd — 16 KB pages, keys in order

root page · keys 1…1M→internal page→leaf page = the row itself ✓

Consequence: a secondary index stores the primary key, not a row pointer — so a wide PK is paid for in every index you add.

3The buffer pool is the database

Almost every read is served from the InnoDB buffer pool. Size it to the working set — typically 70–80% of RAM on a dedicated server.

Deep dive ↓ Level 1 · Buffer pool & checkpoint age

Where a read actually goes

buffer pool hit · ~0.1 msmiss → read 16 KB page from .ibd · 10–100× slower

Watch it: Innodb_buffer_pool_reads ÷ read_requests — physical reads should stay a small fraction of logical ones.

4Checkpoint age near capacity = writes stall

Redo is a ring. When uncheckpointed changes fill it, InnoDB stops accepting writes and flushes pages until there is room.

Deep dive ↓ Level 1 · Redo capacity & checkpoint age

Checkpoint age, as a share of redo capacity

age < 50% · writes flow ✓age → 100% · forced flush, write stalls ✗
SHOW ENGINE INNODB STATUS\G ← LOG section: "Log sequence number" minus "Last checkpoint"

5History list length is cleanup debt, in one number

Old versions live in undo until purge deletes them. A long-running transaction pins them all — and every read walks a longer version chain.

Deep dive ↓ Level 3 · Undo, purge & the history list

One row, three versions deep

users.ibd · current row→undo_001 · previous version→undo_002 · older still · purge blocked ✗

History list length in SHOW ENGINE INNODB STATUS: hundreds is normal, millions is an incident — find the oldest open transaction.

6The change buffer defers secondary-index writes

Inserts into a secondary index whose page is not in memory are recorded in the change buffer and merged later — writes get faster, cold reads pay the merge.

Deep dive ↓ Level 2 · Change buffer & adaptive hash

Write now, merge when the page is next read

INSERT→change buffer · "merge later"→page read → merge applied → index current

Wins on write-heavy, non-unique secondary indexes. It never applies to the clustered index or unique indexes — uniqueness must be checked now, not later.

7Binlog retention must beat your longest outage

A replica that is down longer than the binlog is kept cannot catch up — it must be rebuilt from a backup. Retention is a recovery decision.

Best Practices in MongoDB

8 rules for documents at scale — journal for crashes, oplog for the replica set, everything timestamped

1Journal is durability, oplog is replication

j:true waits for the journal on disk. The oplog is a separate, ordered record that secondaries tail — two logs, two promises.

Deep dive ↓ Level 0 · Journal vs oplog

One write, two destinations

insert on primary→journal/WiredTigerLog.0000000123 · crash safetylocal.oplog.rs · secondaries tail this

Delete the journal and you lose the last ~60 s since checkpoint. Fall out of the oplog window and a secondary must resync from scratch.

2ESR: Equality, Sort, Range — in that order

Every operation · end to end, like the insert

The other three journeys: read, update, delete — and a crash

Same path as the insert — parse, index, page, log — with the invariant stated precisely: writes append to the log before they modify any page; reads append to no log at all; and crash recovery is a function of exactly one input, the log written since the last checkpoint. A checkpoint 5 minutes old at 50 MB/s of WAL generation means up to 15 GB of replay before the server accepts a connection. That number, not the crash itself, sets your recovery time.

SELECT — reading one row

Problem: Find row 42 without reading the whole table file, and without seeing a half-written row.

SELECT * FROM users WHERE id = 42;
1

Parse + plan. The planner checks the catalog and picks a route: index lookup on users_pkey (~3 page reads) beats scanning the whole table file. EXPLAIN shows this decision.

2

Index walk. Root page → internal page → leaf page of the index: key 42 → pointer “data page 7, slot 3”. No other pages are touched.

3

Page from memory if possible. Hit in shared_buffers / buffer pool / WiredTiger cache = instant. Miss = read that one page from the data file (base/…/16397 / users.ibd / collection-*.wt) once and cache it.

4

Visibility check (MVCC). Is this row version committed, and was it live at your snapshot? If a newer version exists, follow to the version your snapshot should see.

5

Row returned. Nothing was written: no WAL record, no redo, no binlog event, no journal entry, no oplog entry. Reads leave no trace in any log file.

End state: log files — unchanged · data files — unchanged · indexes — unchanged · replica — unchanged. A SELECT writes nothing. Its cost is exactly the pages it read: 3–4 on an index hit, the full table on a miss of the planner's estimate. There is no third outcome.

UPDATE — changing row 42's name

Problem: Change a row without anyone ever seeing a half-changed row, and without locking readers out.

UPDATE users SET name='Asha K.' WHERE id=42;
1

Find the row first — exactly like SELECT steps 1–3: index walk → page into memory.

2

Lock just that row so two updates can't collide. Readers don't take this lock — they read snapshots instead.

3

Log FIRST. PostgreSQL writes a WAL record with the new tuple. InnoDB writes redo for the page change plus an undo record holding the old values. WiredTiger writes a journal entry.

4

New version created. PostgreSQL: a brand-new tuple in the heap file, old one marked dead. InnoDB: row updated in place in users.ibd, old version rebuildable from undo. MongoDB: new version in the WiredTiger cache.

5

Indexes fixed only if needed. The id index is untouched — id didn't change. An index on name gets its 'Asha' entry replaced with 'Asha K.'.

6

COMMIT → log forced to disk → visible. The old version stays until no snapshot needs it, then VACUUM / purge removes it. The replica replays the same change from the WAL / binlog / oplog.

Compare to INSERT: same road, one extra idea — the old version must survive until old readers finish.

DELETE — removing row 42

Problem: Remove a row instantly for new readers, but not while an old reader still needs it.

DELETE FROM users WHERE id = 42;
1

Find + lock the row via the index, same as UPDATE steps 1–2.

2

Log FIRST. The delete is recorded — WAL record / redo + binlog event / journal + oplog entry — including enough of the old row to undo it or replay it on a replica.

3

The row is only marked deleted — not erased. PostgreSQL stamps xmax on the tuple. InnoDB sets a delete flag on the record. WiredTiger removes it from the visible version chain. The bytes are still in the file.

4

COMMIT → log on disk → new readers see nothing. A search for 42 returns “not found”. Readers who started earlier still see the row — correctly, from their snapshot.

5

The replica replays the delete from its WAL stream / binlog / oplog and marks its copy the same way.

6

Much later: real erasure. When no snapshot can still see it, VACUUM / purge / the next WiredTiger checkpoint removes the row bytes and its index entries.

This is why a DELETE of 10 million rows returns in seconds and the file does not shrink by one byte: step 3 writes one stamp per row, and step 6 — the physical removal — is deferred to a background process whose throughput, not the DELETE's, determines when the space comes back. A table that is deleted from heavily and never vacuumed/purged grows monotonically while its live row count stays flat.

CRASH + RESTART — the log files earn their keep

Problem: Power cuts mid-work. Some transactions said “saved”, some were half-done. Sort it out perfectly on restart.

-- power cut -- → restart the database
1

Memory is gone. Every dirty page that never reached its data file is lost — shared_buffers, buffer pool, WiredTiger cache, all empty. This is expected, and fine.

2

Find the last checkpoint. PostgreSQL reads global/pg_control for the checkpoint's WAL position. InnoDB finds the checkpoint LSN in the redo log. WiredTiger reads its metadata in WiredTiger.wt. Everything before that point is already in the data files.

3

Replay (redo) the log after the checkpoint, in order: pg_wal segments / ib_logfile0/1 / journal/WiredTigerLog.*. Every committed change is rebuilt, page by page.

4

Undo the unfinished. InnoDB rolls back uncommitted transactions from its undo records. PostgreSQL simply never marks them committed in pg_xact, so their tuples stay invisible. Either way: no COMMIT record in the log = it never happened.

5

Open for business. Committed = present, uncommitted = gone, nothing half-way. Only now are new connections accepted.

6

Replicas re-sync from wherever they stopped: WAL LSN (PostgreSQL), GTID (MySQL), oplog timestamp (MongoDB).

The rule that makes all of this work is INSERT step 5: the log reaches disk before the data page ever needs to.

The log files · one by one

Five logs run everything. Know these five.

Every durability, replication, and recovery guarantee on this page reduces to one of five logs. For each: the exact file name, where it sits, the mechanism, the failure mode when it is undersized, misplaced, or allowed to fill — and the command that shows you its current state. The pattern to hold: a log's size divided by the write rate is a time window, and every operational budget on this page (recovery time, replica downtime tolerance, checkpoint headroom) is one of those windows.

PostgreSQL

Write-Ahead Log (WAL)

pg_wal/000000010000000000000003
Where it sits
The pg_wal/ folder inside the data directory. A chain of segment files, 16 MB each by default, with hex names: timeline + log + segment.
What it does
Every change is written here before the data file is allowed to change — that's the "write-ahead". COMMIT only returns after the WAL record is forced to disk (fsync). The same stream feeds replicas and, when archived, point-in-time recovery.
What breaks without it
No crash safety at all: a power cut could leave half-written pages and silently lost commits. No streaming replication either — replicas have nothing to replay.
Look at it
$ ls $PGDATA/pg_wal $ pg_waldump pg_wal/000000010000000000000003 -- in psql: SELECT pg_current_wal_lsn();
MySQL · InnoDB

Redo log

ib_logfile0 · ib_logfile1
Where it sits
In the datadir, written as a circular pair of files. MySQL 8.0.30+ moved them into a #innodb_redo/ folder as #ib_redo* files — same log, new home. Total size is set by innodb_redo_log_capacity.
What it does
InnoDB's write-ahead log: a physical record of every page change, written before the page itself. On startup after a crash, InnoDB replays it to rebuild every page that was dirty in the buffer pool.
What breaks without it
InnoDB refuses to start without a valid redo log — and with good reason: without it, a committed transaction could vanish in a crash and dirty pages would be unrecoverable.
Look at it
$ ls -lh /var/lib/mysql/ib_logfile* -- in mysql: SHOW ENGINE INNODB STATUS\G -- read the "LOG" section: Log sequence number
MySQL

Binary log (binlog)

mysql-bin.000001 · mysql-bin.index
Where it sits
In the datadir (path set by log_bin). Numbered files that roll over as they fill; mysql-bin.index lists the ones that exist. Each event can carry a GTID — a permanent, unique ID for the transaction.
What it does
A logical record of every committed change ("insert this row", not "change these bytes"). Replicas replay it to stay identical. It is also the second half of point-in-time recovery: restore a backup, then replay the binlog up to the second before the mistake.
What breaks without it
No replication, and no point-in-time recovery — you can only restore whole backups, losing everything since the last one.
Look at it
-- in mysql: SHOW BINARY LOGS; SHOW BINLOG EVENTS IN 'mysql-bin.000001'; $ mysqlbinlog mysql-bin.000001 | less
MongoDB · WiredTiger

Journal

journal/WiredTigerLog.0000000123
Where it sits
The journal/ folder inside the dbPath. A sequence of WiredTigerLog.* files written by the WiredTiger storage engine.
What it does
WiredTiger's write-ahead log. Data files are only made consistent at checkpoints, roughly every 60 seconds; the journal covers the gap. A write acknowledged with j: true is durable once its journal entry is on disk, and on restart mongod replays the journal from the last checkpoint.
What breaks without it
A crash could lose every write since the last checkpoint — up to ~60 seconds of acknowledged data. The journal exists to close exactly that gap.
Look at it
$ ls /var/lib/mongo/journal/ -- in mongosh: db.serverStatus().storageEngine db.adminCommand({getParameter: 1, storageGlobalArgs: 1})
MongoDB

Oplog — the replica set log

local.oplog.rs
Where it sits
Not a file — a capped collection named oplog.rs in the local database, present on every replica set member. Capped means fixed-size: old entries fall off the front as new ones arrive.
What it does
An ordered record of every write on the primary, each stamped with a timestamp. Secondaries continuously tail it and apply the same operations in the same order. Its size defines the oplog window: how far behind a secondary can fall and still catch up.
What breaks without it
No replica set at all. And if a secondary stays down longer than the oplog window, the entries it missed are gone — it must copy everything again (initial sync).
Look at it
// in mongosh: rs.printReplicationInfo() db.getSiblingDB('local').oplog.rs .find().sort({$natural: -1}).limit(1)
All 3

The pattern behind all five

log first → data file later
The rule
Two kinds of log appear above. Physical logs (WAL, redo, journal) record what changed in which page — they exist for crash recovery on the same server. Logical logs (binlog, oplog) record what operation happened — they exist so other servers can redo the same operations.
Why two kinds
A replica can't apply "bytes 40–88 of page 7 changed" unless its pages are byte-identical — streaming WAL replication does exactly that. A logical log is portable across versions and layouts, at the cost of re-executing each operation.
The commit rule
In all three engines, COMMIT means one thing: the log record is on disk. The data file catching up is housekeeping (the checkpoint). If you remember one sentence from this page, make it that one.

2 — B+ tree lookup: finding one key among millions

Problem

A sequential scan of a 10-million-row table reads ~1,250,000 pages. A B+ tree lookup of the same table reads 3.

The derivation is arithmetic, not convention: an 8 KB internal page holds roughly 400 key-pointer pairs (fanout ≈ 400), so depth = log400(rows). 400² = 160,000 rows at depth 2; 400³ = 64 million at depth 3; 400⁴ = 25.6 billion at depth 4. Internal pages hold only guide keys; leaf pages hold keys plus row pointers. That is the entire mechanism — every index behavior on this page, including the ESR rule in the reference atlas, follows from how these pages store keys.

3 — MVCC: two transactions, one row, no waiting

Problem

Transaction B is reading a balance while transaction A changes it. Locking the row would freeze B; overwriting would corrupt B's total.

Fix (MVCC): never overwrite. A creates a new version; B keeps reading the version from its snapshot. Old versions are removed later — by VACUUM in PostgreSQL, by purge of the undo log in InnoDB.

}

The ratio is the diagnostic: totalDocsExamined ÷ nReturned = 1.0 here. At 10×, the index is scanning ten documents for every one returned — poor selectivity, usually a low-cardinality leading field. At 1,000×, the index is decorative. A SORT stage in the winning plan means the index does not cover the sort: results are buffered and sorted in memory, and the query aborts outright at the 100 MB in-memory sort limit (Sort exceeded memory limit of 104857600 bytes). COLLSCAN as the winning stage means no usable index exists for the filter at all — at 10M documents of ~2 KB, that is ~20 GB read to return what may be a single document.

Derivation — why ESR is a theorem, not a conventionA compound index stores keys lexicographically: sorted by field 1, then within equal field-1 values by field 2, then within equal (field 1, field 2) pairs by field 3. Three consequences follow mechanically. Equality first: an equality predicate on field 1 collapses the scan to one contiguous key range, located in O(log N). Sort second: within that contiguous range, field-2 keys are already stored in sort order, so the scan emits rows sorted — no SORT stage, no 100 MB abort. Range last: a range predicate on a field terminates the usable ordering — every key after the range boundary must still be visited for subsequent fields, so a range field placed before the sort field destroys the sort guarantee. Reverse the order and the equality condition degrades from an O(log N) seek to a scan of every key inside the range — on a range covering 80% of the index, the index is 80% of a full scan. ESR is the only ordering that preserves all three properties simultaneously, because of how the keys are physically stored. Nothing about it is stylistic.

3 real problems, 3 different answers

Architecture is a matching problem: each workload below has a dominant cost (correctness under concurrency, read volume, write distribution), and each engine's layout prices those costs differently. The settings named are the ones that move the number, verified against the internals sections above.

Payments — handling money

Problem: Never lose or double-count a single payment.

Answer: PostgreSQL. Strongest correctness defaults, and any question can be asked of the data later.

  • Append-only ledger table; never UPDATE a posted entry
  • UNIQUE constraint on the payment reference, so a retry can't double-charge
  • Synchronous standby: synchronous_commit = on + a sync replica in pg_stat_replication
  • Base backups + WAL archiving, and restore tests on a schedule

Product catalogue — lots of browsing

Problem: 200,000 people browsing at once, almost nobody buying.

Answer: MySQL + read replicas, or MongoDB if every product has totally different attributes.

  • Covering indexes for the top 5 queries — check for “Using index” in EXPLAIN
  • Reads served from replicas replaying mysql-bin.*; a few seconds of lag is acceptable for browsing
  • Sequential product IDs so inserts append neatly in the .ibd files
  • Cache hot pages in the buffer pool: size innodb_buffer_pool_size first

User profiles — users in 40 countries

Problem: Data must be fast and close to each user, all over the world.

Answer: MongoDB, sharded by region. Each region's shard holds its own users' documents.

  • Shard key = { region: 1, _id: 1 }, so a profile lookup routes to exactly one shard
  • Writes with writeConcern: { w: 'majority', j: true } — majority + journal before “saved”
  • One document per profile, shaped like the profile screen reads it
  • Watch the oplog window (rs.printReplicationInfo()) before any planned downtime

Real world · symptom first

When the app starts hurting

The application reports symptoms in its own vocabulary: p99 latency, pool exhaustion, sporadic 500s. The database holds the cause in exactly three places — what is running now (pg_stat_activity / SHOW PROCESSLIST / db.currentOp()), what is slow in aggregate (pg_stat_statements / slow log / profiler), and why one query costs what it costs (EXPLAIN ANALYZE / explain("executionStats")). Each card below follows that order: symptom, mechanism, the suggestion that treats the symptom, and the check that identifies the cause — with the growth curve that turned a latent defect into tonight's incident.

All 3 · most common

1 · Pages that were fast are now slow — no deploy, no traffic spike

App sees: p99 goes 60 ms → 3 s. Timeouts on product / checkout pages. DB CPU high, app CPU normal.

Inside the DB: Usually a missing or unused index. The planner stops using the B+ tree and scans the whole table file — base/…, users.ibd, or collection-*.wt — page by page, evicting hot pages from shared_buffers / buffer pool / WiredTiger cache. The growth curve is the tell: at 10K rows the scan was 5–20 ms and invisible; at 1M rows it is 0.5–2 s; the transition to incident happens between 500K and 2M rows, with no deploy and no code change — only data volume crossed a threshold. Or stats went stale after a bulk load, so the planner thinks a scan is cheaper. Blast radius: the scan does not only slow its own query — every page it reads evicts a cached page another query needed, so unrelated endpoints degrade simultaneously.

DBAs usually suggest

“Add CPU / bigger instance.” “Restart it.” “Add an index on every column in the WHERE.” All three mask it for a day and make writes slower.

What to actually check

Find the top query first, then read its plan. Look at rows examined vs rows returned — 1,000,000 examined for 1 returned = missing index.
-- PG SELECT query, calls, mean_exec_time FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10; EXPLAIN (ANALYZE, BUFFERS) SELECT …; -- MySQL SHOW FULL PROCESSLIST; EXPLAIN SELECT …; -- rows + Extra // MongoDB db.users.find({email:"…"}) .explain("executionStats") // totalDocsExamined vs nReturned

Fix that lasts: Add the one index the plan asks for (or refresh stats: ANALYZE), verify the plan flips to an index scan, drop unused indexes. Prevent: slow-query log on from day one, alert on pg_stat_statements mean time, review plans in code review for new queries.

All 3

2 · “Connection pool exhausted” — app queues, DB looks idle

App sees: Requests hang waiting for a connection, then 500. DB CPU is low. Restarting the app “fixes” it for an hour.

Inside the DB: Every connection costs a process/thread + memory + bookkeeping. A few long or leaked transactions hold connections while doing nothing (idle in transaction). The DB is not busy — the app is starved of slots, or the DB is drowning in thousands of mostly-idle connections.

DBAs usually suggest

“Raise max_connections to 5,000.” That increases memory and lock contention and makes a real overload worse.

What to actually check

Count connections by state. Lots of idle-in-transaction = app leak / missing commit, not a sizing problem.
-- PG: who is holding what? SELECT state, count(*) FROM pg_stat_activity GROUP BY state; SELECT pid, now()-xact_start AS age, query FROM pg_stat_activity WHERE state='idle in transaction' ORDER BY age DESC; -- MySQL SHOW PROCESSLIST; -- long Sleep / Query SELECT COUNT(*) FROM information_schema.processlist; -- MongoDB db.serverStatus().connections db.currentOp({active:true})

Fix that lasts: Put a pooler in front (PgBouncer / ProxySQL / driver maxPoolSize), set statement + idle-transaction timeouts, fix the code path that leaks transactions. Size the pool from DB cores, not app instances. Prevent: alert on connections by state, not just total.

All 3

3 · Random failures: deadlocks and lock waits

App sees: Sporadic “deadlock detected, retry” errors, or one request hangs for 30 s then succeeds. Worse at peak, fine in tests.

Inside the DB: Two transactions lock the same rows in opposite order (A locks row 1 then 2, B locks 2 then 1), or one long transaction holds a row lock while everyone else queues. The engine correctly kills one victim — the app must retry. This is MVCC's boundary: writers do lock rows.

DBAs usually suggest

“Increase the lock timeout” or “set isolation to the weakest level.” Longer waits just make the queue longer.

What to actually check

Find the blocker, not the blocked. One PID is usually at the head of every chain.
-- PG: blocker → blocked pairs SELECT pid, pg_blocking_pids(pid) AS blocked_by, query, wait_event_type FROM pg_stat_activity WHERE wait_event_type='Lock'; -- MySQL: read the last deadlock in full SHOW ENGINE INNODB STATUS\G -- section: LATEST DETECTED DEADLOCK SELECT * FROM performance_schema.data_lock_waits; -- MongoDB db.currentOp({waitingForLock:true})

Fix that lasts: Always lock rows in the same order (sort IDs before updating), keep transactions short, add the index so the update touches fewer rows, retry deadlocks in the app with jitter. Prevent: log lock waits over 1 s, alert on deadlock rate.

All 3

4 · Stale reads: “I saved it, refreshed, and it's old”

App sees: User edits a profile, saves, reloads — old value. A minute later it's correct. Support calls it “data loss.” It isn't.

Inside the DB: Writes go to the primary, reads go to a replica. The replica replays the log — WAL stream / mysql-bin.* / local.oplog.rs — and is seconds behind under load. The read hit a replica that hasn't replayed that commit yet.

DBAs usually suggest

“Send all reads to the primary.” Correct and wasteful — it throws away the replicas you bought for scale.

What to actually check

Measure lag at the moment of the complaint, and check why: write burst, long query on the replica, or single-threaded apply.
-- PG SELECT client_addr, state, replay_lag, pg_size_pretty(pg_wal_lsn_diff( pg_current_wal_lsn(), replay_lsn)) AS behind FROM pg_stat_replication; -- MySQL SHOW REPLICA STATUS\G -- Seconds_Behind_Source, Replica_SQL_Running -- MongoDB rs.status() // optime lag per member rs.printSecondaryReplicationInfo()

Fix that lasts: Read-your-own-write routing: after a write, read that user's data from the primary (or wait for a token/LSN/GTID) for a few seconds; replicas serve browsing and search where staleness is fine. Fix the lag cause if it's structural. Prevent: alert on lag > 2 s, never route “just wrote it” reads to replicas blindly.

5 · Everything slows down over days — disk grows, rows don't

App sees: Gradual slowdown all week. Table has the same live rows but the file is 5× bigger. A restart or a quiet weekend doesn't help.

Inside the DB: Bloat from a pinned snapshot. One long / idle transaction stops cleanup: PostgreSQL VACUUM can't remove dead tuples newer readers might still need, so the heap file bloats; InnoDB purge can't drop undo, so the history list grows and every read walks a longer version chain. Inside the DB: Three usual fillers: logs that can't be purged (WAL / binlog kept because a replica is down or archiving is failing), bloat (card 5), or a genuinely unbounded table (events, audit, sessions never deleted). Deleting log files by hand corrupts recovery — the engine must release them.

DBAs usually suggest

“rm the old WAL / binlog files to free space now.” Never do this — you can destroy crash recovery and replication in one command.

Design doc · which app sits where

Pick the database from the workload, not the fashion

“Which database?” is an ill-posed question; “which workload, at what volume, with what correctness requirement?” is the answerable one. Each workload below is stated with the property that decides it — access pattern, consistency requirement, retention shape. When two workloads with incompatible properties share one engine, the failure does not appear at launch; it appears in the incident cards above, at the volume where the properties start to conflict.

Problem

One database forced to serve OLTP, analytics, search, and cache workloads degrades all four — measurably, and in a predictable order.

The analytical scan evicts the OLTP working set first (incident #1), then its long snapshot pins cleanup (incident #5), then its result set pressures the pool (incident #2). Match each workload to its natural home first; argue about vendors second.

OLTP — orders, payments, bookings, accounts

→ PostgreSQL or MySQL (relational, ACID)

Many small reads/writes, strict correctness, joins across entities, constraints that must hold under concurrency. This is the home workload of everything in the internals sections above.

Real examples: checkout & ledger, airline reservations, SaaS billing. Start here for almost every product.

Analytics — dashboards, reports, BI

→ A warehouse / columnar store (or a replica, if small)

Scans billions of rows, sums a few columns, tolerates minutes-old data. Columnar storage + a separate replica keeps scans off the OLTP primary — running them on the primary is incident #1 and #5 waiting to happen.

Real examples: revenue dashboards, funnel reports. Small scale: read replica + partitioning. Large: sync OLTP → warehouse by WAL/binlog CDC.

Full-text search — “find products like…”

→ Elasticsearch / OpenSearch — or Postgres FTS if modest

Search needs an inverted index (word → documents), ranking, typos, facets. A B+ tree on a text column is not that. Postgres tsvector + GIN is genuinely fine until ranking/facets get serious.

Real examples: product search, log search, support-ticket search. Source of truth stays in the OLTP DB; the search index is derived and rebuildable.

Cache & sessions — sub-millisecond, disposable

→ Redis / Memcached — never the source of truth

Session tokens, rate-limit counters, hot product pages. In-memory, TTL on everything, loss is an inconvenience not a disaster. If losing it loses money or users, it doesn't belong here alone.

Real examples: login sessions, shopping-cart cache, leaderboard (Redis sorted sets).

Queues & background jobs

→ A real queue (SQS, Kafka, Redis Streams) — Postgres can do small scale

Jobs need at-least-once delivery, retries, and ordering trade-offs. Postgres SELECT … FOR UPDATE SKIP LOCKED is a legitimate queue up to thousands of jobs/min and saves an extra system. Beyond that, or for event streaming, use the dedicated tool.

Real examples: email sending, image processing, event pipelines (Kafka when many consumers replay the same events).

Time series — metrics, IoT, events over time

→ Partitioned Postgres / TimescaleDB / a TSDB

Append-mostly, queries are always “last N hours / by day”, old data compresses or drops. Time partitioning makes retention a file drop, not a billion-row DELETE (which is bloat, card 5).

Real examples: sensor readings, clickstream, application metrics. Key design point: partition + retention policy on day one.

Documents — catalogues, profiles, content

→ MongoDB — or Postgres JSONB if the rest is relational

Records whose fields genuinely differ per item, read whole as one aggregate. If you constantly join documents back together, you wanted relational. If only some fields vary, JSONB in Postgres often beats a second database.

Real examples: product catalogue with per-category attributes, user profiles, CMS content.

Graph — relationships are the query

→ Neo4j / a graph store — recursive SQL if shallow

“Friends of friends who bought X”, fraud rings, dependency trees. Traversals that are 1 query in a graph store are recursive joins in SQL. Depth 2–3: Postgres recursive CTE is fine. Deep, constant traversal: dedicated graph DB.

Real examples: recommendations, fraud detection, org/permission hierarchies.

Same app, three answers: an online store

One store — products, orders, payments, seller dashboard. All three engines can run it. Here's when each is the right call, honestly stated.

Pick PostgreSQL when…

Correctness and questions-you-haven't-asked-yet matter most.

Why it fits
Orders + payments + inventory in one ACID database, rich SQL for the seller dashboard, JSONB for the few product attributes that vary — no second DB needed early.
You get
Strongest constraints, best planner, partitioning and logical replication when you outgrow one box.
Watch out
Connection counts (front with PgBouncer), autovacuum on the hot orders table.

The workload is mostly lookups by ID at very large web scale.

Why it fits
Product page = PK lookup in products.ibd, read replicas are operationally simple, and the Vitess path exists if you ever need true sharding.
You get
Huge operational ecosystem, fast simple reads, GTID replication.

When to split across two databases

Splitting is not failure — forcing one engine to do a job it's shaped wrong for is. The rule that keeps splits safe: one source of truth; every other copy is derived and rebuildable.

OLTP + Search

Postgres/MySQL holds orders and products (truth). Elasticsearch holds the search index, fed by WAL/binlog change capture. Search can lag seconds and can be rebuilt from the source at any time.

Split when: search needs ranking, facets, typo tolerance beyond FTS.

OLTP + Analytics

Transactions on the primary; a replica or warehouse takes dashboards and reports. Analysts can run a 10-minute scan without causing incident #1 on checkout.

Split when: the first dashboard query slows a customer-facing page — not before.

Any DB + Redis

Sessions, rate limits, and the 20 hottest pages live in Redis; the relational/document DB stays the truth. Redis dying means a slow minute, not lost data.

Split when: the same read repeats thousands of times per minute and tolerates being seconds stale.

Don't split on day one, and don't split on a benchmark: every additional database adds a backup regime, a monitoring surface, a deploy pipeline, and a synchronization path with its own lag and failure modes. The split is justified by a measured number — a dashboard query demonstrably evicting the checkout working set, a search requirement FTS measurably cannot meet — never by anticipation.

What to check before go-live — and in the first 5 minutes of an incident

Before go-live

Connections are pooled and capped

App pool sized from DB capacity, pooler in place (PgBouncer / ProxySQL), timeouts set for idle-in-transaction and long statements.

-- PG: SELECT count(*), state FROM pg_stat_activity GROUP BY state; -- MySQL: SHOW VARIABLES LIKE 'max_connections'; SHOW PROCESSLIST; -- Mongo: db.serverStatus().connections

Slow-query capture is ON

You cannot fix what you never recorded. Enable it before launch, with a threshold (100 ms–1 s) and a review habit.

-- PG: log_min_duration_statement = 1000 + pg_stat_statements -- MySQL: slow_query_log=ON, long_query_time=1 (+ pt-query-digest) -- Mongo: db.setProfilingLevel(1, {slowms: 100})

Indexes match the real queries — and unused ones are dropped

Run the app's top 20 queries through EXPLAIN. Then find indexes nobody reads: they still tax every write.

-- PG: SELECT relname, idx_scan FROM pg_stat_user_indexes WHERE idx_scan = 0; -- MySQL: SELECT * FROM sys.schema_unused_indexes; -- Mongo: db.users.aggregate([{$indexStats:{}}])

Replication lag is measured and alerted

Know normal lag (usually < 1 s), alert at 2–5 s, and know the oplog/binlog/WAL window: how long a replica can be down and still catch up.

-- PG: SELECT replay_lag FROM pg_stat_replication; -- MySQL: SHOW REPLICA STATUS\G (Seconds_Behind_Source) -- Mongo: rs.printReplicationInfo(); rs.status()

Disk, bloat, and log retention are bounded

Log retention set by time and size, autovacuum/purge verified working, disk alert at 70% with a growth-rate view, retention jobs for events/sessions tables.

-- PG: SELECT relname, n_dead_tup FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 5; -- MySQL: SHOW BINARY LOGS; (check binlog_expire_logs_seconds) -- Mongo: db.stats(); db.serverStatus().wiredTiger.cache

Backup exists — and a restore has actually been tested

An untested backup is a hope, not a backup. Restore to a scratch server, time it, and verify point-in-time recovery (backup + log replay) reaches a chosen minute.

-- PG: pg_basebackup + WAL archive → restore & recovery_target_time test -- MySQL: XtraBackup / mysqldump → restore + mysqlbinlog replay to a timestamp -- Mongo: mongodump / snapshot → mongorestore to a test replica set

When something breaks — first 5 minutes, in order

1 · What is running right now?

Before logs, before dashboards: ask the database what it is doing this second. One query answers half of all incidents.

-- PG: SELECT pid, state, wait_event_type, now()-query_start AS age, query FROM pg_stat_activity WHERE state != 'idle' ORDER BY age DESC; -- MySQL: SHOW FULL PROCESSLIST; -- Mongo: db.currentOp({active:true, secs_running:{$gt:5}})

2 · Is someone blocking everyone else?

Find the head of the lock chain and the oldest transaction. Killing the blocker is often the whole fix — then fix why it ran long.

-- PG: SELECT pid, pg_blocking_pids(pid) FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0; -- MySQL: SELECT * FROM performance_schema.data_lock_waits; SHOW ENGINE INNODB STATUS\G -- Mongo: db.currentOp({waitingForLock:true})

3 · Vitals: connections, lag, disk

Three numbers rule out three incident classes in under a minute: pool/connections saturated? replica lag spiking? disk about to fill?

-- Connections: pg_stat_activity count / SHOW PROCESSLIST count / serverStatus().connections -- Lag: pg_stat_replication / SHOW REPLICA STATUS\G / rs.status() -- Disk: df -h + biggest relations (see go-live list)

4 · What changed?

Deploys, a new report, a marketing email, a batch job that “only runs monthly.” Correlate the slowdown start time with the slow log's first bad entries and the top query by total time.

-- PG: SELECT query, calls, total_exec_time FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5; -- MySQL: pt-query-digest on the slow log around the start time -- Mongo: db.system.profile sorted by ts around the start time

5 · Read one bad plan before changing anything

Pick the single worst query from step 4 and explain it. Seq scan on a big table, rows examined ≫ rows returned, or a sort spilling to disk — the plan names the fix.

-- PG: EXPLAIN (ANALYZE, BUFFERS) <query>; -- MySQL: EXPLAIN FORMAT=TREE <query>; -- Mongo: db.coll.find(…).explain("executionStats")

6 · Fix the cause, write down the check

After the fire: the lasting fix (index, pool, timeout, routing, partition) plus one alert that would have caught it at minute one. An incident without a new alert will repeat.

The cloud side · same engines, different owner

On-prem vs cloud: the physics stays, the 3 AM work moves

A managed database does not repeal anything on this page. A commit on Aurora still waits for log writes; an Atlas oplog window is still size ÷ write rate; autovacuum still runs — and still falls behind — on RDS. What changes is the ownership boundary from the Start here section: the provider absorbs the sysadmin and storage layers wholesale, part of the DBA layer, and none of the query layer. Price that boundary precisely, per engine.

6 copies, 3 AZsAurora's storage layer keeps six copies of every log record and data page across three availability zones, and grows in 10 GB increments up to 128 TB. Storage provisioning — a storage-team job on-prem — simply stops existing as a task.
~60–120 sTypical RDS Multi-AZ failover time: the standby is promoted and the endpoint's DNS flips. On-prem, the same failover is your script, your monitoring, and your pager — measured in minutes if it is rehearsed, hours if it is not.
35 daysMaximum automated-backup retention on RDS — point-in-time recovery to any second inside that window, with no archive scripting. The on-prem equivalent is a base backup plus a WAL/binlog archive you built, monitor, and restore-test yourself.

PostgreSQL RDS for PostgreSQL · Aurora PostgreSQL · Cloud SQL · Azure Database

The problem cloud solves: provisioning, patching, backup plumbing, and failover mechanics for the most correctness-sensitive engine — the work that is identical at every company and expert at none of them by default. Why it is easy to maintain: automated backups with PITR, one-click Multi-AZ, parameter groups instead of config files, and minor-version upgrades scheduled by the provider.

The cloud takes over

  • Provisioning, OS and engine patching, hardware failure
  • Automated backups + PITR (up to 35 days on RDS); storage scaling
  • Multi-AZ failover mechanics (~60–120 s, endpoint unchanged)
  • Aurora: the storage layer itself — 6 copies across 3 AZs, up to 128 TB
  • Monitoring plumbing (Performance Insights, enhanced monitoring)

The DBA still owns

  • Schema, indexes, query plans — every incident in "When it hurts" still applies
  • Autovacuum health: it runs, it can still fall behind, and wraparound is still possible
  • Parameter group tuning: shared_buffers is set as a fraction of instance RAM; some parameters are locked outright
  • Connection pooling (RDS Proxy or your own PgBouncer) and lag monitoring
  • Restore tests — the button is theirs, the verification is yours

Tradeoffs: no superuser and no host — you cannot read pg_wal files, run pg_waldump, install an unlisted extension, or set parameters the provider locks. Failover timing and maintenance windows are the provider's schedule. Cost is a per-hour instance + per-GB + per-I/O rent that beats on-prem at small scale and can exceed it at large, steady scale.

MySQL · InnoDB RDS for MySQL · Aurora MySQL · Cloud SQL for MySQL

The problem cloud solves: the operational machinery around InnoDB — backups, replica provisioning, failover — for an engine whose typical deployment is many similar web workloads. Why it is easy to maintain: read replicas in minutes, automated snapshots plus binlog-based PITR, and on Aurora a shared storage layer that makes replica lag mostly a non-event because replicas read the same storage the writer writes.

The cloud takes over

  • Provisioning, patching, snapshot backups + PITR
  • Replica creation and Multi-AZ failover mechanics
  • Binlog retention management within the window you configure
  • Aurora: redo-driven storage layer — replicas share storage, failover is fast, storage auto-grows
  • Parameter delivery via parameter groups

The DBA still owns

  • Queries, indexes, and the purge/history-list problem — a long transaction pins purge on RDS exactly as on-prem
  • Buffer pool sizing, via parameter group, inside instance-class limits
  • Primary-key discipline: random UUID PKs fragment Aurora and RDS tables the same way
  • Replica lag on binlog-based replicas, and GTID consistency at failover
  • Durability settings: flush/sync choices still exist in the parameter group — and can still be set wrong

Tradeoffs: no SUPER privilege and no filesystem — ib_logfile0 and the binlog files are unreachable; binlog access is through stored procedures and retention settings, and some InnoDB internals (change buffer behavior, redo sizing on Aurora) are managed for you whether you like their values or not. Sharding remains your problem (Vitess runs on top, not inside).

MongoDB · WiredTiger MongoDB Atlas (and compatible managed offerings)

The problem cloud solves: replica-set and sharded-cluster operations — elections, member replacement, balancer supervision, backup consistency across shards — which are the easiest parts of MongoDB to run badly by hand. Why it is easy to maintain: a replica set or a sharded cluster is a configuration choice in a console, snapshots and continuous backup are built in, and members are replaced by the platform instead of by a runbook.

The cloud takes over

  • Provisioning replica sets and sharded clusters; member replacement after failure
  • Elections happen on managed infrastructure with tested automation
  • Snapshots + continuous backup with PITR; cross-region cluster options
  • Patching and version upgrades as rolling operations
  • Monitoring and alerting plumbing (including oplog window visibility)

The DBA still owns

  • Schema design and indexing — the ESR rule and COLLSCAN economics are unchanged
  • The shard key: still chosen by you, still near-permanent, jumbo chunks still possible
  • Read/write concerns per application — Atlas cannot choose your durability
  • The oplog window math: Atlas shows the window; sizing the tier so the window fits your maintenance is your decision
  • Tier sizing and cost: an oversized cluster is the most common Atlas incident, and it is a billing incident

Tradeoffs: no host and no dbPath — journal/ files, WiredTiger.wt, and the rollback directory are not yours to inspect; logs come through the UI/API, and only a subset of setParameter knobs are exposed. Network design (peering, private endpoints) becomes part of the database's latency profile. In exchange, the entire on-prem ownership table from Start here — sysadmin, storage, most of operations — collapses into the provider's column.

The decision rule that survives every vendor: cloud removes operational work whose difficulty is the same everywhere (patching, failover mechanics, backup plumbing) and removes none of the work whose difficulty is specific to your data (schema, indexes, shard keys, cleanup health, the window math). If your incidents are mostly the first kind, managed wins. If they are mostly the second kind — and the eight cards in "When it hurts" say they usually are — the cloud changes who holds the pager, not whether it rings.

The one invariant: COMMIT means the log record is on disk — pg_wal in PostgreSQL, ib_logfile0 + mysql-bin in MySQL, journal/WiredTigerLog + the oplog in MongoDB. The data files (base/…, *.ibd, collection-*.wt) are where checkpoints place the result afterwards, on their own schedule. Every guarantee on this page — durability, replication, point-in-time recovery — is a consequence of that ordering, and every number on this page is checkable with the commands given beside it.
