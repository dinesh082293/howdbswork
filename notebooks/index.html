Notebook 1 · run 2026-11-18 04:25 UTC

What one open transaction costs

I held one transaction open in each engine and kept writing from a second session. This is the experiment behind Compare, scenario 4.

PostgreSQL: 100,000 rows, a snapshot held open, then 500,000 row updates. How many dead row versions can VACUUM remove while the snapshot is open?

None of the 500,000. VACUUM says so itself: "500000 are dead but not yet removable". Once the snapshot is released, the same VACUUM removes all of them, and the file stays at 29 MB.

## PostgreSQL 18: a REPEATABLE READ snapshot held open while 5 x 100,000 rows are updated
table size at start: 5784 kB
session A: BEGIN ISOLATION LEVEL REPEATABLE READ; SELECT count(*) -> 100000
session B: 5 x UPDATE nb_accounts SET balance = balance + 1  (500,000 new row versions)
table size now: 29 MB
session B: VACUUM (VERBOSE) nb_accounts while A is still open:
  pages: 0 removed, 2655 remain, 2655 scanned (100.00% of total), 0 eagerly scanned
  tuples: 0 removed, 600000 remain, 500000 are dead but not yet removable
  removable cutoff: 757, which was 5 XIDs old when operation ended
dead tuples (pg_stat_user_tables): 700000
session A: ROLLBACK  (the snapshot is released)
session B: VACUUM (VERBOSE) nb_accounts again:
  pages: 0 removed, 2655 remain, 2655 scanned (100.00% of total), 0 eagerly scanned
  tuples: 500000 removed, 100000 remain, 0 are dead but not yet removable
  removable cutoff: 762, which was 0 XIDs old when operation ended
  index "nb_accounts_pkey": pages: 1099 in total, 0 newly deleted, 0 currently deleted, 0 reusable
table size after VACUUM: 29 MB  <- VACUUM made the space reusable; the file did not shrink

## MySQL 8.4: a consistent snapshot held open while 5 x 100,000 rows are updated
History list length at start: 6
session A: START TRANSACTION WITH CONSISTENT SNAPSHOT; SELECT COUNT(*) -> 100000
session B: 5 x UPDATE nb_accounts SET balance = balance + 1
History list length after 5 big UPDATEs: 11  <- it counts transactions waiting for purge, not rows
session B: 20,000 single-row UPDATEs, each its own transaction (12 s)
History list length while A is still open: 20006
session A: COMMIT  (the old read view is released)
   2s after COMMIT, History list length: 0

## MongoDB 8.0: a multi-document transaction left open past the lifetime limit
transactionLifetimeLimitSeconds default: 60 | set to 10 for this run
session A: startTransaction; updateOne({_id: 1}, {$inc: {balance: 10}})
session A: waits 25 s without committing
session A: commitTransaction -> OperationFailure: Transaction with { txnNumber: 2 } has been aborted.
serverStatus().transactions.totalAborted: before 0 after 1
balance now: 100

What I take from it

  • PostgreSQL: the table grew from 5.8 MB to 29 MB while one idle snapshot was open, and VACUUM could not remove a single dead version until it closed. After that, the space became reusable, but the file did not shrink.
  • MySQL: the History list length counts transactions waiting for purge, not rows. Five updates of 100,000 rows each added 5. Twenty thousand one-row updates added 20,000. Two seconds after the old snapshot closed, purge had cleared it to 0.
  • MongoDB: the engine does not let the problem grow. Past transactionLifetimeLimitSeconds the transaction is aborted, the commit fails, and the write is gone. It is 60 seconds by default, and I lowered it to 10 for the run.

Notebook 2 · run 2026-11-18 04:26 UTC

What waiting for the log costs per commit

Two thousand single-row inserts, one commit each, with the durable setting on and then off. I ran the durable setting twice, before and after, to see whether the number holds.

How much faster are commits when they do not wait for the log flush: 10 percent, 2 times, or 10 times?

On this machine, about 1.7 times in PostgreSQL and about 2.3 times in MySQL and MongoDB. On a disk where a flush costs more, such as network-attached storage, the gap is larger. Measure on your own disk before you decide.

## PostgreSQL 18: synchronous_commit on vs off
  synchronous_commit = on     4238 commits/s  0.236 ms per commit
  synchronous_commit = off    7607 commits/s  0.131 ms per commit
  synchronous_commit = on     4131 commits/s  0.242 ms per commit

## MySQL 8.4: innodb_flush_log_at_trx_commit and sync_binlog
  innodb_flush_log_at_trx_commit = 1, sync_binlog = 1    1770 commits/s  0.565 ms per commit
  innodb_flush_log_at_trx_commit = 2, sync_binlog = 0    4013 commits/s  0.249 ms per commit
  innodb_flush_log_at_trx_commit = 1, sync_binlog = 1    1798 commits/s  0.556 ms per commit

## MongoDB 8.0 (single-node replica set): write concern j: true vs j: false
  w: 1, j: true     1048 commits/s  0.954 ms per commit
  w: 1, j: false    2716 commits/s  0.368 ms per commit
  w: 1, j: true     1121 commits/s  0.892 ms per commit

What I take from it

  • The durable setting cost 0.29 ms per commit in PostgreSQL, 0.63 ms in MySQL with both logs synced, and 0.92 ms in MongoDB with j: true. The faster settings trade that time for a window of acknowledged commits that a crash can lose.
  • MySQL with both settings at 1 syncs two logs per commit, the redo log and the binlog. Turning both down more than doubled its commit rate.
  • The repeated runs agree within a few percent, so the difference is the setting, not noise. The absolute numbers belong to this runner, not to your server.

Notebook 4 · run 2026-11-18 04:27 UTC

Two sessions, interleaved step by step

Two classic concurrency bugs, lost update and write skew, run in each engine with the default settings and then with the fix. Every step is real, in the order shown. The Isolation page explains each one.

Two sessions each read a balance of 100 and add to it, +10 and +20. With the default settings, does PostgreSQL keep both deposits?

No. At READ COMMITTED, the default, the final balance is 120, and the +10 is lost. At REPEATABLE READ, PostgreSQL refuses the second update instead.

## PostgreSQL 18, lost update, READ COMMITTED (the default)
  A: SELECT balance -> 100
  B: SELECT balance -> 100
  A: UPDATE balance = 110; COMMIT
  B: UPDATE balance = 120; COMMIT -> ok
  final balance: 120  (expected 130 if both deposits count)

## PostgreSQL 18, lost update, REPEATABLE READ
  A: SELECT balance -> 100
  B: SELECT balance -> 100
  A: UPDATE balance = 110; COMMIT
  B: UPDATE balance = 120 -> ERROR: could not serialize access due to concurrent update
  final balance: 110  (expected 130 if both deposits count)

## MySQL 8.4, lost update, REPEATABLE READ (the default)
  A: SELECT balance -> 100
  B: SELECT balance -> 100
  A: UPDATE balance = 110; COMMIT
  B: UPDATE balance = 120; COMMIT -> ok
  final balance: 120  (expected 130 if both deposits count)

## MySQL 8.4, lost update fixed with SELECT ... FOR UPDATE
  A: SELECT balance FOR UPDATE -> 100
  B: SELECT balance FOR UPDATE -> still waiting after 1.5 s: True
  A: UPDATE balance = 110; COMMIT
  B: ... the SELECT FOR UPDATE returns -> 110
  B: UPDATE balance = 130; COMMIT -> ok
  final balance: 130  (expected 130 if both deposits count)

## MongoDB 8.0, lost update, inside two transactions
  A: findOne -> balance 100
  B: findOne -> balance 100
  A: updateOne balance = 110; commitTransaction
  B: updateOne balance = 120 -> OperationFailure: Caused by :: Write conflict during plan execution and yielding is disabled. :: Please retry your operation or multi-document transaction.
  final balance: 110  (expected 130 if both deposits count)

## PostgreSQL 18, write skew, REPEATABLE READ
  A: SELECT count(*) WHERE on_call -> 2
  B: SELECT count(*) WHERE on_call -> 2
  A: UPDATE alice off call
  B: UPDATE bob off call
  A: COMMIT -> ok
  B: COMMIT -> ok
  doctors on call at the end: 0  (the rule was: at least 1)

## PostgreSQL 18, write skew, SERIALIZABLE
  A: SELECT count(*) WHERE on_call -> 2
  B: SELECT count(*) WHERE on_call -> 2
  A: UPDATE alice off call
  B: UPDATE bob off call
  A: COMMIT -> ok
  B: COMMIT -> ERROR: could not serialize access due to read/write dependencies among transactions
  doctors on call at the end: 1  (the rule was: at least 1)

## MySQL 8.4, write skew, REPEATABLE READ (the default)
  A: SELECT COUNT(*) WHERE on_call -> 2
  B: SELECT COUNT(*) WHERE on_call -> 2
  A: UPDATE alice off call
  B: UPDATE bob off call
  A: COMMIT -> ok
  B: COMMIT -> ok
  doctors on call at the end: 0  (the rule was: at least 1)

## MongoDB 8.0, write skew, inside two transactions
  A: countDocuments({on_call: true}) -> 2
  B: countDocuments({on_call: true}) -> 2
  A: updateOne alice off call
  B: updateOne bob off call
  A: commitTransaction -> ok
  B: commitTransaction -> ok
  doctors on call at the end: 0  (the rule was: at least 1)

What I take from it

  • The defaults do not protect a read-then-write pattern. PostgreSQL at READ COMMITTED and MySQL at REPEATABLE READ both lost a deposit without any error.
  • PostgreSQL at REPEATABLE READ and MongoDB inside transactions refused the second write. The application has to catch that error and retry.
  • Write skew got past PostgreSQL at REPEATABLE READ, MySQL at its default, and MongoDB inside transactions. Only PostgreSQL SERIALIZABLE stopped it.
  • The fix I ran, SELECT ... FOR UPDATE in MySQL, kept both deposits: the second session waited for the first, then read 110. The other common fix is to make the update relative, SET balance = balance + 10, so that it never writes a stale value.

Notebook 6 · run 2026-11-18 21:22 UTC

The rules the design docs rely on

The design docs say "let the database enforce the rule". This notebook checks four of those rules on real servers: the last item in stock, a retried payment, an overlapping booking, and a query that forgets its tenant filter.

Sixteen clients try 1,600 purchases of an item with 1,000 in stock. Each one reads the stock, and if it is above zero, writes the stock minus one. How many sales go through?

All 1,600, in every engine, and the stock still shows hundreds left. The conditional update, UPDATE ... WHERE available >= 1, sold exactly 1,000 and left 0.

## 1. The last item: 1000 units, 16 clients each trying 100 purchases at once (1600 attempts)
  PostgreSQL, read, then write the new value:    sold 1600 of 1000, stock left  869, 0.5 s
  PostgreSQL, UPDATE ... WHERE available >= 1:   sold 1000 of 1000, stock left    0, 0.3 s
  MySQL,      read, then write the new value:    sold 1600 of 1000, stock left  888, 0.4 s
  MySQL,      UPDATE ... WHERE available >= 1:   sold 1000 of 1000, stock left    0, 0.6 s
  MongoDB,    read, then $set the new value:     sold 1600 of 1000, stock left  799, 0.6 s
  MongoDB,    updateOne({available: {$gte: 1}}, $inc): sold 1000 of 1000, stock left    0, 0.3 s

## 2. A retried payment with an idempotency key (PostgreSQL)
  attempt 1, key pay-abc: committed
  attempt 2, same key (a client retry): rolled back: duplicate key value violates unique constraint "nb_idem_pkey"
  ledger rows: 2 | sum of amounts: 0 | alice: -500

## 3. Two bookings for the same room and overlapping times
  PostgreSQL, room 7, 14:00-16:00 -> booked
  PostgreSQL, room 7, 15:00-17:00 -> conflicting key value violates exclusion constraint "nb_room_bookings_room_id_during_excl"
  PostgreSQL, room 7, 16:00-18:00 -> booked
  MySQL, event 99, seat A12, booking 1 -> booked
  MySQL, event 99, seat A12, booking 2 -> Duplicate entry '99-A12' for key 'nb_seat_bookings.PRIMARY'

## 4. A query that forgets WHERE tenant_id = ... (PostgreSQL row-level security)
  as the application role, tenant 2, SELECT count(*) FROM nb_projects -> 10
  same role, the rows it sees, by tenant -> [(2, 10)]
  as postgres (a superuser), same query -> 30  <- superusers bypass row-level security

What I take from it

  • The last item: read-then-write sold 1,600 units of a 1,000-unit stock in PostgreSQL, MySQL and MongoDB alike, and left the counter wrong too (869, 888 and 799 remaining). The conditional, relative update sold exactly 1,000 in all three.
  • A retried payment: the second attempt with the same idempotency key hit the unique constraint and rolled back as a whole. The ledger kept two rows that sum to zero.
  • An overlapping booking: the PostgreSQL exclusion constraint rejected 15:00 to 17:00 against 14:00 to 16:00, and accepted 16:00 to 18:00, which only touches it. In MySQL the primary key on (event, seat) rejected the second booking of seat A12.
  • A forgotten tenant filter: with row-level security, the application role saw only its tenant's 10 rows out of 30. The postgres superuser saw all 30, which is why the application must not connect as one.

ClickHouse holds 10,000,000 order lines. A revenue report filters on one month and sums two columns. How many rows does it read?

870,400 rows and about 15 MB, in 8 ms. The table is partitioned by month and sorted by SKU and time, so ClickHouse skipped every part that could not match and read only the columns the query names.

What I take from it

  • Redis: a 100,000-player leaderboard took 9.6 MB of memory. One ZINCRBY round trip took 0.07 ms, and both the top 10 and one player's rank came back in under 0.2 ms. The rate limit allowed 5 requests, rejected the 6th and 7th, and the key expired on its own.
  • ClickHouse: columns with few distinct values compressed 100 to 200 times (qty, sku, note). Unique or timestamp-like columns barely compressed. 200 single-row inserts made 200 parts on disk; one insert of 200 rows made one part. That is why the design docs say batch.
  • Cassandra: the latest 20 messages of one conversation came from one partition in 2.4 ms. A query by sender_id, which is not part of the key, was rejected outright unless you add ALLOW FILTERING. Cassandra makes you design tables around the queries.

The one invariant: COMMIT means the log record is on disk. pg_wal in PostgreSQL, #innodb_redo/#ib_redo0 + mysql-bin in MySQL, journal/WiredTigerLog + the oplog in MongoDB. The data files (base/…, *.ibd, collection-*.wt) are where checkpoints place the result afterwards, on their own schedule. Every guarantee on this page, durability, replication, point-in-time recovery, is a consequence of that ordering, and every number on this page is checkable with the commands given beside it.
