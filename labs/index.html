Make a guess before you open the answer, then break things and see whether you were right. Two more labs live on the Staff Path: a B+ tree and an MVCC timeline. Lab 1 · crash recovery

Pull the plug, then watch the restart

Commit a few transactions. Take a checkpoint at some point. Open a transaction and leave it. Then crash the server and restart it. The restart replays only the log written after the last checkpoint.

You turn the log-flush box off, commit three transactions, and crash before a second passes. How many of the three survive?

None, unless a checkpoint or the one-second flush ran in between. All three were acknowledged to the client. That is the trade synchronous_commit = off and innodb_flush_log_at_trx_commit = 0 make: a short window of acknowledged commits can disappear in a crash.


    
Try this: turn the log-flush box off, commit three times, crash, and read which commits were lost. They were acknowledged to the client, so the application believed they were safe. Then run it again with the box on.

Lab 2 · replica lag

  
Writes arrive faster than the replica applies them

  
Lag is a queue. Set the write rate and the apply rate and see how big the queue gets, how long the replica is behind, and whether it can ever catch up.

  
Writes arrive at 1,500 per second and the replica applies 1,200. After 10 minutes, how far behind is it?
300 a second for 600 seconds is 180,000 transactions behind, about two and a half minutes of work at 1,200 a second. It keeps growing for as long as the overload lasts, and it only shrinks once writes drop below 1,200.

Lab 3 · lock pile-up

  
One transaction holds one hot row

  
A single transaction takes a lock on a row that many requests want. Every request that needs that row waits, and every waiting request holds a connection. Watch how long it takes for the pool to run out.

  
40 requests a second need the same row, one transaction holds its lock for 5 seconds, and the pool has 100 connections. Does the pool survive?
No. 40 times 5 is 200 waiting sessions. The pool is gone after 2.5 seconds, and from then on every request waits, including the ones that never touch that row.

Lab 4 · page count

  
Scan every page, or walk the index

  
The same lookup, two ways. A scan reads every page of the table. An index lookup reads a handful. The squares are the table, scaled to fit.

  
10 million rows of 200 bytes in 8 KB pages. How many pages does a scan read, and how many does an index lookup read?
About 250,000 pages for the scan. About 4 for the index lookup: 3 index pages and the table page that holds the row.
