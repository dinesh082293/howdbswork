Labs

What happens if I pull the plug, or flood a replica, or lock one row?

Four small simulations. Each one is a model of the behavior, not a benchmark, so the numbers are round on purpose. Break things and watch where the damage lands. Two more labs live on the Staff Path: a B+ tree and an MVCC timeline.

Lab 1 · crash recovery

Pull the plug, then watch the restart

Commit a few transactions. Take a checkpoint at some point. Open a transaction and leave it. Then crash the server and restart it. The restart replays only the log written after the last checkpoint.


    
Try this: turn the log-flush box off, commit three times, crash, and read which commits were lost. They were acknowledged to the client, so the application believed they were safe. Then run it again with the box on.

Lab 3 · lock pile-up

  
One transaction holds one hot row

  
A single transaction takes a lock on a row that many requests want. Every request that needs that row waits, and every waiting request holds a connection. Watch how long it takes for the pool to run out.

The bars show waiting sessions over the time the lock is held. Red bars are past the pool size. This is the most common shape of an outage that starts as "one slow query".

The one invariant: COMMIT means the log record is on disk. pg_wal in PostgreSQL, #innodb_redo/#ib_redo0 + mysql-bin in MySQL, journal/WiredTigerLog + the oplog in MongoDB. The data files (base/…, *.ibd, collection-*.wt) are where checkpoints place the result afterwards, on their own schedule. Every guarantee on this page, durability, replication, point-in-time recovery, is a consequence of that ordering, and every number on this page is checkable with the commands given beside it.
