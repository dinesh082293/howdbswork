Cassandra

How does Cassandra take so many writes, and why is it so picky about queries?

This page is about a database built for writes spread across many machines, with no primary. I show you where a write goes (commit log, memtable, SSTable), how the partition key decides which machines hold your data, and why deletes and queries the key cannot answer cause most of the trouble. After it you will be able to design a table from its queries, pick a consistency level, and read nodetool's view of the cluster.

Cassandra: in one line

A wide-column database: rows grouped into partitions by a key, partitions spread across a ring of equal nodes, every write appended and never updated in place.

Good at: Huge write rates, data that grows forever, several data centres, no single node that must stay up. Time series, messages, event history.

Runs as: one Java process per node; every node is equal; replication per keyspace, consistency per query
Common myth

Cassandra is eventually consistent, so it loses data.

Consistency is chosen per query. With three replicas, write at QUORUM and read at QUORUM, and a read always sees the latest acknowledged write, because any two nodes out of three overlap with any other two. What Cassandra does not give you, until the Accord transactions in 6.0, is a transaction across partitions.

The architecture: a ring of equal nodes

There is no primary and no failover. Any node can take a request and pass it to the nodes that own the data.

Diskcommitlog/ segments · data/<keyspace>/<table>/ SSTables (Data.db, an index, Filter.db, Statistics.db) · hints/
Who does what: The coordinator hashes the partition key to a token and sends the request to the replicas that own that token. Each replica appends to the commit log, adds the write to its memtable and acknowledges. Memtables flush to immutable SSTables, and compaction merges SSTables and finally drops deleted data.

A replica is down and you write at QUORUM with three replicas. Does the write succeed?

Yes. Two of three is a quorum. The coordinator keeps a hint for the missing replica. At consistency ALL the same write would fail. Tick the box in the widget to step through it.

The failures I would plan for

Where it fits in a design

Endless writes, read by key

Use it for

  • Message history: Chat and messaging
  • Telemetry and events: IoT and telemetry, Audit and event logs
  • Timelines at very large scale: Social feed
  • Any table read by one key and a time range, written by many machines at once

Not for

  • Money with transactions across rows: Payments and ledgers
  • Ad hoc queries and reports: Analytics
  • Small datasets: one PostgreSQL is simpler
  • Joins, or unique constraints across rows
Check it yourself

The commands I run first

nodetool status                         # every node: up or down, load, ownership
nodetool tablestats chat.messages       # SSTables, partition sizes, tombstones per read
nodetool tablehistograms chat messages  # SSTables per read, partition size percentiles
nodetool compactionstats                # compactions running and pending
nodetool tpstats                        # thread pools, dropped messages, hints
nodetool repair -pr chat                # repair this node's primary ranges
cqlsh> CONSISTENCY QUORUM;
cqlsh> TRACING ON;                      # then run a query: where it spent its time, replica by replica

Your turn

A chat app stores messages with PRIMARY KEY (channel_id, sent_at). One channel has 50 million messages, and reads for it are slow on the same few nodes. What is wrong, and what would you change?

Write your answer down first. Then open mine.

Show my answer

What is wrong: the partition key is channel_id alone, so the whole channel is one partition on the same three replicas. At about 300 bytes a message that is roughly 15 GB in one partition: one hot set of nodes, long compactions, and reads that walk a huge partition.

What I would change: add a time bucket, PRIMARY KEY ((channel_id, day), sent_at), or month for quieter channels, so each partition stays well under 100 MB. The app reads the latest bucket first and walks back.

And: old buckets can expire with a TTL and TimeWindow compaction, so retention is files being dropped, not millions of tombstones.

Check yourself · 4 questions

Check yourself

Pick an answer. You will see whether it is right, and why.

1. What decides which nodes store a row?

The partition key is hashed to a token, and the token range decides the replicas.

2. Three replicas. You write at QUORUM and read at QUORUM. Does the read see the write?

Two plus two is more than three, so at least one node in the read has the write.

3. What is a tombstone?

Deletes are writes too. The marker stays for gc_grace_seconds so every replica learns about the delete.

4. Why must repair run within gc_grace_seconds?

Once the tombstone is gone, a replica that never saw the delete looks like the newest copy.
